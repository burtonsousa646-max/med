# Дизайн: справочные подсказки Suggestion

## Обзор

[Требования](requirements.md) и [ADR 0004](../../architecture/adr/0004-suggestion-service.md) согласованы человеком. Suggestion — отдельный NestJS-сервис без PostgreSQL. Три приложения используют публичные операции Gateway; Gateway выполняет распределённое ограничение, затем вызывает четыре типизированных RPC. Сервис проверяет ввод, читает необязательный Redis-кеш и обращается к выбранному источнику. Реализация покрывает R1–R9; интерфейсы экранов не входят в поставку.

**Внешняя зависимость:** техническая основа Gateway, фича `002-api-gateway-foundation`, подготовлена в ветке `chore/api-gateway`, коммит `d7d390b`, включая ADR 0003, общие пакеты `config`, `logger`, `health` и стандартный gRPC healthcheck. В текущей базе этих файлов и реализации пока нет. T1 фиксирует проверку готовности зависимости; разработчик не создаёт параллельную основу и не выполняет merge без отдельного согласования. Ниже определены все расширения этой основы для Suggestion. Документ не меняет дизайн другой фичи.

## Взаимодействие

### Поиск (R1–R7, R9)

```mermaid
sequenceDiagram
  participant C as Лендинг / кабинет / бэкофис
  participant G as Gateway
  participant R as Redis ограничителя
  participant S as Suggestion
  participant K as Redis кеша
  participant D as Выбранный источник
  C->>G: POST /api/<app>/v1/suggestions/<kind>
  G->>R: Атомарный допуск по IP и подтверждённому пользователю
  alt Лимит превышен
    G-->>C: 429 + Retry-After
  else Ограничитель недоступен или восстанавливается
    G-->>C: 503
  else Запрос допущен
    G->>G: Ограничение тела, JSON и OpenAPI, trim
    G->>S: Unary RPC + deadline, x-request-id
    alt Длина 0–2
      S-->>G: items: [] без кеша и источника
    else Длина 3–150
      S->>K: GET по безопасному ключу
      alt Актуальный корректный ответ найден
        K-->>S: Типизированные варианты
      else Промах или отказ кеша
        S->>D: query, count: 10; таймаут и отмена
        D-->>S: Справочные варианты
        S->>S: Разбор и маппинг первых 10
        S->>K: SET с TTL, ошибка записи не меняет результат
      end
      S-->>G: Типизированные варианты
    end
    G-->>C: 200 + Cache-Control: no-store
  end
```

1. Gateway создаёт request ID, выбирает зарегистрированную операцию. Для подсказок признак `x-suggestion-rate-limit: true` обязателен и сверяется с binding на старте. Нельзя подключить обходной NestJS-маршрут без реестра.
2. До чтения тела определяется доверенный адрес клиента и вызывается ограничитель. Он применяется также к ошибочным запросам на известные операции; неизвестные маршруты обрабатывает существующая политика 404. Проверка заголовков Content-Length/Content-Type может отказать раньше, без upstream. Сырой JSON подсказок ограничен 16384 байтами, включая chunked-тело; это ограничение строже общего лимита Gateway и не изменяет другие операции.
3. Затем выполняется JSON-parser и валидация исходного OpenAPI. Только тело `{ query: string }`; неизвестные свойства, query-параметры, фильтры, count/limit запрещены. Строка нормализуется `String.prototype.trim()`, длина — число кодовых точек Unicode (`Array.from(query).length`), внутренние пробелы сохраняются. Регистр и Unicode-нормализация не меняются.
4. Pattern в `SuggestionRequest` проверяет предел 150 после trim, а не длину сырой строки. Строки с пробелами по краям не отклоняются по сырому `maxLength: 150`. Примеры обязательных проверок: 150 букв допускаются, 151 — 400, 150 букв с пробелами по краям допускаются в пределах размера тела, 150 emoji считаются 150 кодовыми точками. Суррогатные пары не делятся.
5. Gateway передаёт нормализованную строку в соответствующий RPC; сервис повторяет нормализацию и инварианты независимо от HTTP. Для 0–2 символов он сразу возвращает пустую выдачу, без кеша и источника. Ограничитель Gateway уже учёл запрос.
6. RPC использует `GrpcCallExecutor` основы Gateway: deadline — минимум оставшегося HTTP-бюджета и `GRPC_CALL_TIMEOUT_MS`. Отключение HTTP-клиента отменяет RPC; служебные заголовки запроса не копируются в metadata. Передаётся только серверный `x-request-id`. Персонализации ответов нет.
7. На стороне сервиса контекст unary-вызова связывается с `AbortController`: учитываются уже наступившая отмена, событие `cancelled` у `ServerUnaryCall` и дедлайн; обработчики удаляются в `finally`. Завершение обычного RPC не считается отменой. Источник и операции кеша получают сигнал; сетевые команды, уже выполненные Redis, не откатываются.
8. Gateway собирает только разрешённые поля ответа, удаляет представления отсутствующих proto-полей и возвращает контракт. Все ответы, включая ошибки, имеют `Cache-Control: no-store` и `X-Request-Id`. Нельзя возвращать сырой gRPC-объект или JSON DaData.

### Ограничение RPS (R8, R9.5)

Gateway получает `ClientIdentity` через `ClientIdentityResolver`: `{ canonicalIp, verifiedUser?: { realm, subject } }`. Адрес определяет Gateway, пользователь — только адаптер подтверждённой сессии. Пока система входа не реализована, рабочий `VerifiedIdentityReader` возвращает отсутствие пользователя; запросы из обеих зон проходят как посетители. Реальные cookie не разбираются фиктивным способом. В тестах порт подменяется подтверждённой идентичностью; production-переключателя для поддельной сессии нет. Подключение будущего адаптера входа не меняет API Suggestion.

**Адрес:** без доверенных прокси используется `socket.remoteAddress`. При наличии CIDR в `GATEWAY_TRUSTED_PROXY_CIDRS` цепочка `X-Forwarded-For` анализируется справа налево от TCP-peer до первого недоверенного узла; левее него адреса игнорируются. Если peer недоверенный, весь заголовок игнорируется. Разрешается максимум 16 адресов и 2048 байт заголовка; неверная цепочка от доверенного peer — 400 без upstream. Нормализация адресов использует стандартные Node.js `net.isIP` и `net.SocketAddress.parse` и собственное сравнение байтов/CIDR в адаптере; отдельная библиотека не вводится. IPv4-mapped IPv6 приводится к IPv4. В конфигурации запрещены универсальные сети `/0`. Для production список должен соответствовать фактическим прокси, которые удаляют/перезаписывают входящий XFF; прямой доступ к Gateway закрыт сетевым правилом. CORS остаётся выключенным: frontend и соответствующий `/api/<app>` доступны через один origin.

**Ключи:** `suggestion-rate:<scope>:ip:<hmac>` и при наличии сессии `suggestion-rate:<scope>:user:<hmac>`. HMAC-SHA-256 берётся от канонической идентичности с разделением пространств `ip` и `user:<realm>`; одинаковые realm/subject во всех приложениях дают один пользовательский ключ. Scope, секрет и RPS одинаковы у всех экземпляров. App и kind в ключе отсутствуют. Сетевое ограничение применяется всегда; NAT делит сетевой бюджет согласно ADR 0004.

**Атомарная операция Redis:** один статический Lua-скрипт через `EVAL`, ключи и параметры передаются отдельно; исходники скрипта не строятся из строки клиента. Первая топология — standalone Redis без eviction. Скрипт выполняет:

1. Берёт Redis TIME в миллисекундах. Проверяет общий marker `suggestion-rate:<scope>:gate` без TTL. Он содержит версию политики, отпечаток конфигурации (RPS и хеш HMAC-секрета) и `blockedUntilMs`.
2. Если marker отсутствует после запуска/потери состояния, создаёт его с `blockedUntilMs = now + 1000` и возвращает `warming_up`; все экземпляры в течение этого полного окна получают 503. При несовпадении отпечатка — `configuration_mismatch`, тоже 503, без сброса чужого состояния. Несогласованное обновление экземпляров не должно раздавать дополнительные бюджеты.
3. Удаляет в каждом затронутом sorted set записи со score `<= now - 1000`. Интервал учёта — `(now - 1000, now]`. Score — время Redis, member — уникальный request ID, созданный Gateway.
4. Если хотя бы один счётчик уже равен RPS, возвращает `limited` и время до освобождения места: максимум ожиданий для исчерпанных ключей. В этой ветке ни один счётчик не расходуется и его TTL не продлевается.
5. Иначе атомарно добавляет событие в оба нужных счётчика и ставит им TTL 1100 мс. Marker не истекает, поэтому простой не запускает новое окно восстановления. Скрипт возвращает `allowed`.

`limited` преобразуется в 429 с `Retry-After = max(1, ceil(waitMs/1000))`; warming/config mismatch/сбой Redis — в 503. Пустой ввод, ошибка валидации после допуска, разрыв клиента и последующий отказ источника не возвращают израсходованный бюджет. Успешно выполненный скрипт не повторяется при потере его ответа.

Redis-клиент не хранит offline-очередь команд и не повторяет незавершённые команды после разрыва. Команды ограничены `SUGGESTION_REDIS_TIMEOUT_MS`, уже отправленная команда может успеть учесть запрос после локального таймаута — это допустимый консервативный отказ. Восстановление соединения фоновое, с одной попыткой подключения одновременно и интервалом 1000 мс; бизнес-запрос не ждёт очередь восстановления.

**Изменение RPS/секрета:** остановить допуск подсказок на всех Gateway, дождаться завершения текущих операций, обновить env всех экземпляров, удалить только namespace `suggestion-rate:<scope>:` на выделенном Redis и запустить Gateway. Первый Lua-вызов создаст общее защитное окно. Нельзя очищать этот namespace или менять scope на работающих экземплярах. Изменение не требует сборки, но перезапуск нужен; rolling update со смешанным RPS в этой версии не поддерживается. Потеря соединения с Redis не выключает другие операции Gateway и не меняет его readiness.

### Источники и маппинг

`dadata-cloud` вызывает POST по `new URL(kind, DADATA_CLOUD_URL)`, где kind — фиксированное `party`, `address`, `bank` или `email`, с телом `{ query, count: 10 }`, заголовками JSON/Accept и `Authorization: Token <key>`. В env указывается базовый путь, заканчивающийся `/suggest/`, например официальный путь `https://suggestions.dadata.ru/suggestions/api/4_1/rs/suggest/`. Redirect запрещён; TLS проверяется. Таймаут включает получение и разбор тела. Ответ ограничен 2097152 байтами при потоковом чтении, даже без Content-Length; превышение — ошибка источника. Нельзя выполнять дополнительный запрос обогащения выбранного варианта: возвращаются только доступные сведения.

| Модель платформы | Поле DaData / преобразование |
|---|---|
| Party.value | `value`, наименование; обязательная непустая строка |
| Party.inn/kpp/ogrn | `data.inn/kpp/ogrn`; строки цифр по схемам OpenAPI; КПП не выдумывается |
| Party.address | `data.address.unrestricted_value`, иначе `data.address.value` |
| Party.status | `data.state.status`: ACTIVE/LIQUIDATING/LIQUIDATED/REORGANIZING/BANKRUPT → соответствующие lower_snake_case; неизвестная непустая строка → `unknown`; отсутствующий статус не передаётся |
| Address.value | `unrestricted_value`, иначе `value`, полный адрес |
| Address.region/district/city/settlement/street | `data.region_with_type/area_with_type/city_with_type/settlement_with_type/street_with_type` |
| Address.house | `data.house` |
| Address.block/flat | непустые `data.block_type + data.block`, `data.flat_type + data.flat`, с одним разделительным пробелом; если номера нет, поле отсутствует |
| Address.postalCode/fiasId | `data.postal_code/fias_id`, только соответствующие схеме |
| Address.coordinates | пара `data.geo_lat/geo_lon`: обе непустые строки преобразуются в конечные числа в пределах широты/долготы; иначе объект отсутствует; нулевые координаты допустимы |
| Bank.value/bic/correspondentAccount | `value`, `data.bic/correspondent_account` |
| Bank.address | `data.address.unrestricted_value`, иначе `data.address.value` |
| Email.value | `value`, без подтверждения существования ящика |

Для display-значения обязательна строка 1–4096 символов; нет валидного display или массив `suggestions` отсутствует — весь ответ считается некорректным (503), а не пустым поиском. Обрабатываются первые 10 элементов в исходном порядке; дополнительной сортировки, дедупликации и фильтрации по статусу нет. Дополнительные поля источника игнорируются. Необязательные поля с `null`, пустыми, неверными типами или значениями вне контрактной схемы опускаются, событие качества агрегируется без значений; допустимая подсказка остаётся в выдаче. Сырые ответы и протокол не выходят в домен.

`stub` реализует порт источника прямо синтетическими доменными объектами. `dadata-onprem-stub` использует тот же cloud-adapter/mapper с in-process `DadataTransport`, который возвращает синтетический облачный envelope; отдельного HTTP-сервера не поднимает. Имя провайдера различается в ключе кеша. Оба режима запрещены в production.

Минимальный синтетический набор: организация «ООО Пример Тест» с ИНН `0000000000`, ИП «ИП Пример Тест» с ИНН `000000000000` без КПП, адрес «Тестовый регион, г Пример, ул Тестовая, д 1», банк «Банк Пример Тест» с БИК `000000000`, email `qa@example.test`. Числовые идентификаторы не выдают за реальные проверенные реквизиты. Поиск stub — подстрока в нижнем регистре по display и идентификаторам вида; неподходящая строка даёт `[]`. Расширенные тестовые наборы задаются зависимостью в тестах, а не публичным параметром.

## Контракты

### OpenAPI

Корни: [landing.yaml](../../../api/openapi/landing.yaml), [cabinet.yaml](../../../api/openapi/cabinet.yaml), [backoffice.yaml](../../../api/openapi/backoffice.yaml). Единственный `servers.url` каждого — `/api/<app>`. Общие path items и схемы — [suggestions.yaml](../../../api/openapi-shared/suggestions.yaml); этот файл не является самостоятельным OpenAPI-документом и не попадает в перечень целей генератора. Все ссылки локальные внутри `api/`, runtime получает bundle и исходные зависимости из сборки Gateway.

| Операция во всех трёх приложениях | operationId | Требования |
|---|---|---|
| `POST /v1/suggestions/parties` | `suggestParties` | R1, R5–R9 |
| `POST /v1/suggestions/addresses` | `suggestAddresses` | R2, R5–R9 |
| `POST /v1/suggestions/banks` | `suggestBanks` | R3, R5–R9 |
| `POST /v1/suggestions/emails` | `suggestEmails` | R4, R5–R9 |
| `GET /v1/feature-flags` | `getFeatureFlags` | инфраструктурная зависимость ADR 0001, R6.5 |

Все операции имеют явное `security: []`. Схема `FeatureFlags` пуста и закрыта; контроллер основы Gateway возвращает `{}`. Внутри приложения operationId уникальны; повтор между приложениями разрешается реестром по `(appId, operationId)`. Feature-flags не расходует бюджет подсказок и сохраняет инфраструктурную политику Gateway.

Запрос — `{ query: string }`, ответ — `{ items: <тип вида>[] }`. Отсутствующие сведения опускаются, `null` не возвращается. Коды ошибок: 400 `invalid_request`, 413 `payload_too_large`, 415 `unsupported_media_type`, 429 `rate_limit_exceeded`, 500 `internal_error`, 503 `service_unavailable`; тело ровно `{ code, message }`. 401/403 не используются для отсутствующей сессии в публичных подсказках. Неизвестные пути/методы обрабатываются общим 404 основы Gateway. Текст ошибки не содержит ввода и сообщения поставщика.

### gRPC

[Контракт](../../../api/proto/suggestion/v1/suggestion.proto): пакет `platform.suggestion.v1`, сервис `SuggestionService`.

| RPC | Отдельные сообщения | Требования |
|---|---|---|
| SuggestParties | SuggestPartiesRequest / SuggestPartiesResponse | R1 |
| SuggestAddresses | SuggestAddressesRequest / SuggestAddressesResponse | R2 |
| SuggestBanks | SuggestBanksRequest / SuggestBanksResponse | R3 |
| SuggestEmails | SuggestEmailsRequest / SuggestEmailsResponse | R4 |

Транспорт загружается через `protoPath('suggestion/v1/suggestion.proto')` с `PROTO_LOADER_OPTIONS`. Необязательные scalar-поля объявлены `optional`, чтобы отличать отсутствие от пустой строки при `defaults: true`; HTTP-mapper не копирует служебные oneof-поля proto-loader. Для отсутствующего вложенного сообщения учитывается `null`/`undefined` от loader, наружу поле опускается. Проверки реальной сериализации подтверждают отсутствие КПП у ИП и координат у адреса без них.

Неверный ввод → `INVALID_ARGUMENT` → 400; ошибка/таймаут/квота/неверный протокол источника → `UNAVAILABLE` → 503; непредвиденная ошибка → `INTERNAL` → 500. `DEADLINE_EXCEEDED` на транспортной границе → 503. Сырой provider 403/429 — ошибка доступности источника, не HTTP 403/429 клиента. Прямой gRPC не является внешней точкой входа и недоступен другим вызывающим в первой поставке.

[Buf](../../../api/buf.yaml) сохраняет STANDARD с точечным исключением PACKAGE_DIRECTORY_MATCH для этого файла: namespace по правилам имеет префикс `platform`, путь — `<service>/v1`. Другие правила и файлы не исключены. Это не изменение wire-формата.

### События

Не применимо: поиск не меняет бизнес-данные, очередей и событий нет.

**Ломающие изменения:** нет: существующие операции и proto не меняются. Новые документы и поля не объявляют наличие готовых экранов. Типы генерируются существующей командой; генерация в Gateway выполняется при появлении его пакета. Ручное создание фиктивного `package.json` для обхода этого условия запрещено.

## Данные

### `suggestion-service`

Постоянных сущностей и миграций нет. Модель запроса — вид и нормализованная строка. Модель ответа задаётся схемами четырёх видов в контракте. Кеш хранит только разрешённые поля доменной модели в JSON-envelope `{ version: 1, items }`, не полный JSON DaData.

Ключ кеша: `suggestion-cache:<scope>:v1:<provider>:<hmac>`, HMAC-SHA-256 от детерминированного JSON `[canonicalBaseUrlOrStubVersion, kind, normalizedQuery]` с `SUGGESTION_CACHE_HMAC_SECRET`. Ключ не содержит строку поиска и API-ключ. URL не содержит credentials; изменение ключа доступа само по себе не меняет справочник. Ответы других провайдеров/адресов/версий не смешиваются. Нельзя включать user/company в ключ: результаты общие справочные.

GET/SET имеют ограниченный бюджет; повреждённый JSON или несоответствие модели — промах и попытка удаления записи с тем же бюджетом. TTL устанавливается только при SET: по умолчанию 86400 секунд. Чтение его не продлевает, просроченная запись не используется. В случае промаха разрешены параллельные одинаковые обращения к источнику, без распределённой блокировки. Поиск не имеет необратимых эффектов и ключ идемпотентности не нужен.

Два Redis не имеют общих процессов/томов. Оба без AOF/RDB и резервных копий. Кеш: `maxmemory 128mb`, `allkeys-lru`. Ограничитель: `maxmemory 64mb`, `noeviction`; ошибка записи при заполнении означает 503. TTL не отключает требования контроля доступа и размещения данных в России. PostgreSQL и существующий Redis платформы остаются без изменений.

### Конфигурация

Читается один раз через `@platform/config`, без значений в ошибках. Экспортируется `readSuggestionConfig(env)` и расширяется `readGatewayConfig(env)` основы. У обоих `NODE_ENV`, версия, логгер и остановка следуют общей основе. `SUGGESTION_SCOPE` — непустой идентификатор окружения `[a-z0-9-]{1,32}`; по умолчанию `local`, в production задаётся явно.

| Переменная | Где | Значение по умолчанию / проверка |
|---|---|---|
| SUGGESTION_PROVIDER | сервис | обязательна; `dadata-cloud`, `dadata-onprem-stub`, `stub`; последние два запрещены в production |
| DADATA_CLOUD_URL | сервис | обязательна только для cloud; абсолютный HTTPS URL без userinfo, query, fragment, путь заканчивается `/suggest/` |
| DADATA_CLOUD_API_KEY | сервис | обязательный непустой секрет только для cloud |
| SUGGESTION_TIMEOUT_MS | сервис | 1500; целое 1–3000, фактически не больше остатка gRPC-дедлайна |
| SUGGESTION_CACHE_TTL_SEC | сервис | 86400; целое 1–86400, увеличение срока хранения требует повторного решения |
| SUGGESTION_CACHE_REDIS_URL | сервис | обязательный redis/rediss URL; локально порт 6381; в production rediss или защищённая приватная сеть с ACL |
| SUGGESTION_CACHE_HMAC_SECRET | сервис | обязательный секрет не короче 32 байт, в production своё случайное значение |
| SUGGESTION_REDIS_TIMEOUT_MS | оба | 100; целое 1–1000 и меньше общего бюджета операции |
| SUGGESTION_SCOPE | оба | общее окружение, правило выше |
| SUGGESTION_RATE_REDIS_URL | Gateway | обязательный redis/rediss URL, локально 6380; не тот же экземпляр, что кеш |
| SUGGESTION_RATE_HMAC_SECRET | Gateway | обязательный секрет от 32 байт; общий у всех экземпляров, отдельный от секрета кеша |
| SUGGESTION_RATE_LIMIT_RPS | Gateway | 5; целое 1–1000, технический предел размера журнала, не отдельная квота источника |
| GATEWAY_TRUSTED_PROXY_CIDRS | Gateway | пустая строка → только TCP-peer; иначе список IPv4/IPv6 CIDR через запятую, не `/0` |
| SUGGESTION_GRPC_TARGET | Gateway | обязательный host:port, клиент не управляет им; локально `127.0.0.1:50051`, в Compose `suggestion-service:50051` |
| HTTP_HOST / HTTP_PORT | сервис | `0.0.0.0` / 3001; HTTP обслуживает только health |
| GRPC_HOST / GRPC_PORT | сервис | `127.0.0.1` / 50051; в контейнере привязка `0.0.0.0`, порт не публикуется наружу |
| SHUTDOWN_TIMEOUT_MS | сервис | 15000; единый бюджет отмены запросов и закрытия ресурсов |

Технические пределы env валидируются до readiness; неверное значение не заменяется молча default. Ограничение HTTP-тела 16384 и внешнего ответа 2097152 байта фиксировано в первой версии. Общий HTTP/gRPC-бюджет Gateway берётся из основы (10000/3000 мс по умолчанию), адрес сервиса добавляется только после регистрации его операций.

## Согласованность и сбои

| Шаг | Сбой | Поведение |
|---|---|---|
| Конфигурация / bundle | неверный env, путь, binding, внешний `$ref` | остановка запуска до ready |
| Идентичность | поддельный user/header, недоверенный XFF | не создаёт подтверждённую сессию; XFF игнорируется у недоверенного peer |
| Ограничитель | лимит исчерпан | 429 + Retry-After; сервис не вызывается |
| Ограничитель | Redis недоступен, OOM, timeout, потеря состояния | 503, без локального fallback и повторов; восстановление через общий gate |
| Ввод | неверный тип, длина, JSON, лишние поля | 400; слишком большой body 413, неверный media type 415 |
| Кеш | недоступен / повреждён / TTL истёк | промах, обращение в источник под лимитом Gateway |
| Источник | timeout, сеть, любой non-2xx, неверный JSON/envelope/display | UNAVAILABLE/503; сырой ответ не раскрывается и не сохраняется |
| Запись кеша | не удалась | успешный ответ пользователю, безопасное агрегированное предупреждение |
| HTTP/RPC-клиент | отключился / deadline | отмена незавершённых операций и чтения тела; поздний результат не отправляется и не кешируется |
| Redis-команда после локального timeout | поздно выполнилась | допуск не переигрывается, 503 остаётся; остаточная запись кеша не используется до следующего запроса |
| Остановка | SIGTERM/SIGINT | ready false, остановка допуска, дренирование в общий бюджет, затем отмена, закрытие Redis и gRPC |

Сервис использует HTTP/gRPC health модуля общей основы, имя `suggestion-service`. Готовность не проверяет DaData и необязательный кеш; live показывает процесс. Завершение не ждёт недоступный Redis бесконечно. Gateway сохраняет свой healthcheck и 503 только для подсказок при отказе ограничителя.

## Feature toggles

Не применимо: создаётся новый API без заменяемого старого поведения. Допуск и защита не отключаются флагом. Выбор источника и RPS — конфигурация окружения. Новых флагов нет, `deploy/unleash/flags.json` не меняется, схемы FeatureFlags всех трёх приложений пусты. Отдельная задача удаления release-флага не требуется.

## Безопасность

- **Доступ:** операции подсказок публичны; аутентификационные заголовки не пересылаются сервису. Прямой gRPC из внешней сети запрещён; в приватной сети доступ разрешён только Gateway. Внешний HTTP доступен через ограничивающий reverse proxy.
- **Изоляция компаний:** бизнес-данные компаний не читаются; companyId не принимается и не участвует в поиске. Общий кеш содержит только разрешённые справочные сведения.
- **Персональные данные:** email, адреса и сведения ИП могут быть в кратковременном кеше; шифрование канала и сетевые ACL применяются к источнику и Redis. Кеш без дисковых копий; срок не больше 24 часов по умолчанию. В URL/логах/метриках нет ввода, ключей, тел, IP, HMAC и сырых исключений.
- **Reverse proxy до публичного запуска:** закрытый прямой адрес Gateway, TLS, запрет неоднозначных/повторных Content-Length и конфликтующего Transfer-Encoding, тело не более 16 КиБ для подсказок, таймаут чтения заголовков 5 с и тела 5 с, максимум 20 активных запросов и 20 соединений на IP. Это технические ограничения соединений, не замена RPS. Продолжающийся распределённый поток ограничивается ёмкостью и сетевыми средствами окружения; произвольная DDoS-устойчивость не заявляется. Конфигурация будущего ingress проверяется по этим условиям; локальный прямой запуск использует TCP-peer и не имитирует production-прокси.
- **Redis:** только внутренние порты, ACL по namespace/командам, обязательные секреты на стендах/production; логически разные базы на одном Redis не удовлетворяют изоляции кеша и ограничителя. Офлайн-очереди отключены, одновременное число запросов ограничено инфраструктурой.

## Наблюдаемость

- **Логи:** через общий logger; разрешены requestId, appId, operationId, kind, provider, длина строки, результат (hit/miss/empty/limited/unavailable), duration и безопасный code. Пользовательские значения и raw error не передаются в logger. Известные upstream-ошибки дают статическую категорию.
- **Ограничение диагностики:** ошибки кеша/источника и 429 агрегируются в памяти по фиксированным категориям, без персональных ключей. Не более одной записи категории/вида в 10 секунд на процесс, счётчик подавленных событий включается в следующую запись. Сырые отклонённые запросы не пишутся отдельными access-логами ни в Gateway, ни в reverse proxy. Успешные HTTP-операции используют существующий безопасный журнал основы.
- **Метрики:** будущие счётчики requests/outcomes, cache hit/miss, provider duration и rate-limiter unavailable; labels только app/kind/provider/result/code. Экспортёр не добавляется до принятия общего стека наблюдаемости, в этой поставке доступны агрегированные события логгера.
- **Алерты:** требуются события недоступности ограничителя, source quota и роста 503; численные пороги, каналы и реализация экспортёра относятся к инфраструктуре стенда. Не объявляются работающими по факту наличия дизайна.

## Риски и решения

- [ADR 0004](../../architecture/adr/0004-suggestion-service.md) принят: сетевой лимит делят пользователи NAT; по одному подтверждённому пользователю применяется дополнительный счётчик. Включение этого механизма в реальный вход — зависимость будущей фичи аутентификации, сейчас публичный доступ защищён сетевым ключом.
- Gateway и общие пакеты пока описаны в другой ветке; зависимость T1 обязательна. Контракты и сгенерированные типы можно проверить до реализации процессов; интеграционные проверки рабочего поиска — после появления основы.
- Персональные данные не помещаются в URL или диагностику, но содержатся в ответах/кеше: отказ от дисковых копий и отдельный Redis обязательны, не заменяются только TTL.
- Индивидуальный RPS не задаёт общий бюджет источника. Массовый поток с разных IP может исчерпать тариф; это даёт 503. Дополнительная общая квота не вводится без отдельного решения человека.
- Pact для gRPC требует реальной проверки Protobuf plugin на первом сервисе. T8 выполняет её на настоящем клиенте Gateway и настоящем gRPC-контроллере Suggestion; несовместимость блокирует эту проверку, не заменяется фиктивным Pact JSON или тестом HTTP-заглушки. Общая технология уже предусмотрена стеком; версия плагина фиксируется в составе тестовой поставки после проверки на Node.js 26.
- Среда подготовки документов использует Node.js 24; проверки генерации/типов здесь не доказывают runtime-совместимость новой реализации с Node.js 26. Разработчик проверяет итоговые процессы и образы на требуемом рантайме.
