# ADR 0007. Аутентификация и учёт партнёров

## Контекст

На лендинге посетитель вводит email и ИНН на разных шагах оформления кампании. Подтверждение email позволяет зарегистрировать пользователя до того, как станет известна его организация. В кабинете тот же пользователь оформляет следующие кампании от имени уже связанной с ним организации. Вход начинается с кода по email, в дальнейшем один пользователь сможет входить несколькими способами.

[ADR 0003](0003-api-gateway.md) оставляет реализацию аутентификации на следующий этап. [Дизайн Campaign Launcher](../../features/004-campaign-launcher/design.md) предусматривает проверку пары «пользователь — организация» через порт `CampaignRepresentativeDirectory`. Требуется определить владельцев сессии, профиля и членства и порядок привязки гостевой кампании.

Основание для правил входа и членства — согласованные [требования 005](../../features/005-email-auth/requirements.md) и [требования 006](../../features/006-partners/requirements.md).

## Варианты

| Вариант | Преимущество | Цена для платформы |
| --- | --- | --- |
| Один сервис для входа, пользователей и организаций | Способ входа и профиль создаются в одной транзакции | Изменения способов входа и правил работы с партнёрами требуют общей поставки |
| Два сервиса — аутентификация и учёт партнёров | Способы входа развиваются независимо, регистрация организации и назначение представителя остаются атомарными | Первый вход требует согласованного повтора операций в двух базах |
| Три сервиса — аутентификация, пользователи и организации | У профилей и организаций независимые циклы поставки | Для проверки членства и получения контактов представителя и реквизитов организации приходится собирать данные нескольких владельцев |

## Решение

22 ноября 2026 года человек согласовал вариант с двумя сервисами NestJS. У каждого своя база PostgreSQL и своя схема Prisma. Межсервисные операции выполняются по gRPC. Внешние запросы проходят через API Gateway по [ADR 0006](0006-unified-api.md).

| Компонент | Ответственность |
| --- | --- |
| `auth-service` | Регистрирует учётную запись, подтверждает способы входа, создаёт, проверяет и отзывает сессии. Владеет проверочными кодами и привязками способов входа к стабильному `userId`. |
| `partners-service` | Владеет профилями пользователей, организациями, членством и приглашениями. В профиле хранятся контактные email и телефон, в организации — ИНН и название для клиентов. У пользователя может быть ноль или одна организация, у организации — несколько пользователей. |
| API Gateway | Принимает учётные данные и cookie от браузера, получает результат проверки у `auth-service`, обеспечивает допуск к операции и передаёт прикладным сервисам подтверждённый контекст. Gateway передаёт токены браузеру в cookie с атрибутами `HttpOnly`, `Secure` и `SameSite`. |
| Campaign Launcher | Владеет кампанией. Хранит `organization_id` как идентификатор владельца и `created_by_user_id` как идентификатор автора. Проверяет пару через `partners-service` и сохраняет предусмотренный дизайном снимок данных представителя и организации. |

### Регистрация и вход

1. При запросе и проверке кода `auth-service` приводит адрес входа к нижнему регистру, сохраняет его в этом виде и сравнивает без учёта регистра. Gateway допускает до 15 запросов отправки письма за последние 2 часа по одному токену посетителя суммарно для всех адресов. При исчерпании лимита письмо не отправляется. Проверка введённого кода расходует только попытку ввода. За доставку письма отвечает сервис нотификаций.
2. После успешной проверки `auth-service` находит привязку способа входа. Для существующей привязки он открывает сессию с прежним `userId`. При первом входе резервирует регистрацию для подтверждённого адреса и передаёт стабильный идентификатор регистрации в `partners-service`. Тот создаёт профиль и при повторе возвращает тот же `userId`. Затем `auth-service` завершает привязку и открывает сессию.
3. Подтверждение кода и сохранение результата проверки выполняются атомарно в базе `auth-service`. Если ответ от `partners-service` потерян, сервер продолжает уже подтверждённую регистрацию по её идентификатору. Повторные и параллельные входы для одного адреса используют одну регистрацию. Сессия выдаётся после сохранения привязки.

По R1 фичи 005 код действует 10 минут от выпуска и принимается один раз для своего адреса. Повторная отправка разрешена через минуту после последней отправки. Пока код действует, высылается тот же код с прежним сроком и оставшимся числом попыток. После истечения срока следующий разрешённый запрос выдаёт новый код. На один код допускается пять попыток. Верный ввод с пятой попытки принимается, пятая ошибка исчерпывает лимит. Неверный, использованный или просроченный код не открывает сессию. Сбой доставки письма не влияет на открытые сессии.

В таблице `auth_identities` одна строка связывает `user_id` с уникальной парой `(provider, subject)`. Для email значением `subject` служит нормализованный подтверждённый адрес, для внешнего провайдера — устойчивый идентификатор в пространстве этого провайдера. Новый способ привязывается из действующей сессии после подтверждения владения им. Совпадение контактных адресов само по себе не объединяет учётные записи. Изменение контактного email в профиле и смена адреса для входа — отдельные операции.

### Сессия и тихое обновление

По R3 фичи 005 `auth-service` выдаёт для одной сессии токен доступа (access token) и токен обновления (refresh token). Для защищённого запроса Gateway получает у `auth-service` подтверждение действительности сессии. При сбое проверки Gateway возвращает ошибку временной недоступности и не передаёт действие прикладному сервису.

Когда срок токена доступа истёк, клиент через Gateway выполняет тихое обновление (silent refresh). По действительному токену обновления `auth-service` выдаёт новый токен доступа без повторного ввода кода. С момента последней активности пользователя отсчитываются 24 часа. Фоновое обновление токена не сдвигает этот срок. По достижении 24 часов бездействия, после выхода или отзыва сессии прекращаются и защищённый доступ, и обновление токена. Для продолжения требуется вход по email. Адреса, коды, токены и cookie исключаются из журналов.

### Организация и оформление кампании

Первичное сохранение гостевого черновика допускается до регистрации организации. Подтверждение email устанавливает личность. При оформлении кампании `partners-service` сначала проверяет текущее членство по подтверждённому `userId`.

| Состояние | Результат |
| --- | --- |
| У пользователя уже есть организация | Её идентификатор автоматически используется для кампании. Если в гостевом черновике указан другой ИНН, до завершения оформления пользователю показывают фактическую организацию. |
| Организации у пользователя нет, ИНН свободен | В одной транзакции создаются организация и связь пользователя с ней как первого представителя. Он получает право приглашать коллег. |
| Организации у пользователя нет, ИНН занят | Черновик сохраняется. Для присоединения требуется приглашение представителя на email коллеги. При принятии приглашения проверяются подтверждённый адрес получателя и возможность установить членство. |

Уникальность ИНН и ограничение одной организации на пользователя обеспечиваются базой `partners-service`. При конкурирующих заявках первым представителем становится тот, чья транзакция первой зарегистрировала организацию. После конфликта сервис повторно читает членство и организацию и применяет правила таблицы. Если создание или привязка кампании завершились сбоем после регистрации организации, повтор операции использует созданную связь и тот же ключ идемпотентности кампании.

Для привязки гостевого черновика Campaign Launcher проверяет право на сам черновик по гостевой cookie. Для операций кабинета Gateway передаёт `userId` и `companyId` из подтверждённого контекста сессии. После создания членства контекст обновляется, а для операций от имени организации проверяется актуальность связи. Отзыв членства закрывает доступ и при открытой сессии. Авторство сохраняется. Доступ к конкретному черновику по-прежнему проверяется по правилам [ADR 0005](0005-campaign-launcher.md).

Если проверить членство невозможно, действие от имени организации не выполняется.

### Приглашения

По R4 фичи 006 `partners-service` связывает приглашение с организацией, email получателя и создателем. Приглашение действует 5 суток от создания. Повторная отправка от той же организации на тот же адрес в одной транзакции прекращает действие прежнего приглашения и создаёт новое на 5 суток. Ожидающее приглашение может отозвать только его создатель. Отзыв действует сразу.

При принятии сервис проверяет срок и состояние приглашения, подтверждённый адрес и текущее членство получателя. Успешное принятие и создание членства выполняются в одной транзакции. Повтор успешного принятия сохраняет единственное членство. Если приглашение истекло, отозвано или заменено, адрес отличается либо получатель состоит в другой организации, его членство сохраняется в прежнем состоянии. При конкурирующих принятии и отзыве результат определяется порядком завершения транзакций.

Передача полномочий первого представителя и расширенная ролевая модель отложены. Кто вправе прекратить действующее членство коллеги, остаётся открытым продуктовым вопросом.

## Последствия

- Первый представитель получает полномочия по факту подтверждения email и первичной регистрации ИНН. Это допускает ошибочное или недобросовестное занятие свободного ИНН. Порядок разбора спорной регистрации требует отдельного продуктового решения.
- Изменения профиля и членства доступны всем потребителям через одного владельца. Добавление способа входа сохраняет прежние идентификаторы пользователя, организации и кампаний.
- Первый вход и оформление кампании затрагивают несколько локальных транзакций. Безопасный повтор требуется и при таймауте, когда результат предыдущей записи ещё неизвестен вызывающему сервису.

## Когда пересмотреть

Пересмотреть модель членства, если пользователю понадобится представлять несколько организаций одновременно. Пересмотреть правила первичной регистрации при появлении проверки полномочий представителя. Вернуться к границам сервисов, если у организаций появится самостоятельный жизненный цикл, который потребует отдельной поставки или хранения.
