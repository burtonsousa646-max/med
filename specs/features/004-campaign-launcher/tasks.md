## Задачи

### [ ] T1. Хранилище черновиков и точки приёма

- **Исполнитель:** BE
- **Пакет:** `@platform/campaign-launcher-service`
- **Закрывает:** R1.1, R1.2, R1.4, R1.5, R1.6, R1.7
- **Зависит от:** —
- **Флаг:** —
- **Что сделать:** Создать сервис с собственной PostgreSQL, описать обе таблицы и ограничения владельца в схеме Prisma, создать миграцию и реализовать репозиторий через Prisma. Реализовать транзакции записи и удаления, версию, health и конфигурацию собственной PostgreSQL.
- **Готово, когда:** Интеграционные проверки подтверждают одну заявку у гостя, несколько у пользователя, откат записи, конфликт версий и удаление точек вместе с заявкой.
- **Заметки:** —

### [ ] T2. Сценарии записи и проверка автора

- **Исполнитель:** BE
- **Пакет:** `@platform/campaign-launcher-service`
- **Закрывает:** R1.1, R1.2, R1.3, R1.6, R1.7, R1.9, R2.1, R2.2, R2.3, R2.4, R3.1, R3.2, R3.3, R3.4, R4.2, R4.3, R4.4, R4.5, R4.6, R5.1, R5.2, R5.4, R5.5
- **Зависит от:** T1
- **Флаг:** —
- **Что сделать:** Реализовать четыре gRPC-сценария, доменную валидацию, проверки владельца, защиту полей профиля, повтор POST и маппинг ошибок. Применять подтверждённый снимок профиля, переданный Gateway согласно дизайну.
- **Готово, когда:** Проверки сценариев подтверждают сохранение неполного шага, запрет чужого доступа и изменения полей профиля, сохранение новых данных по новому ИНН и отсутствие дублей при повторе.
- **Заметки:** —

### [ ] T3. Расширение сведений об организации

- **Исполнитель:** BE
- **Пакет:** `@platform/suggestion-service`, `@platform/api-gateway`
- **Закрывает:** R5.1, R5.2, R5.3, R5.5
- **Зависит от:** —
- **Флаг:** —
- **Что сделать:** Добавить маппинг новых необязательных полей в Suggestion и Gateway. Проверить, какие данные доступны в поддерживаемых адаптерах. Для значений без однозначного источника сохранять отсутствие поля.
- **Готово, когда:** Синтетические ответы с полным и частичным набором проходят gRPC и HTTP. Старые поля сохраняют семантику, отсутствующие не подменяются.
- **Заметки:** —

### [ ] T4. Гостевой доступ через Gateway

- **Исполнитель:** BE
- **Пакет:** `@platform/api-gateway`
- **Закрывает:** R1.3, R1.4, R1.6, R2.1, R2.2, R2.4, R2.5, R4.6
- **Зависит от:** T2, T8
- **Флаг:** —
- **Что сделать:** Включить гостевые операции из кандидатного OpenAPI в рабочий `api/openapi/platform.yaml` и сгенерировать типы при участии архитектора. В той же поставке подключить маршруты лендинга, гостевую cookie, проверку Origin, ограничения частоты, маппинг ошибок и gRPC.
- **Готово, когда:** Проверки подтверждают восстановление в том же браузере, отказ без cookie до вызова gRPC, изоляцию черновика.
- **Заметки:** —

### [ ] T5. Доступ из кабинета

- **Исполнитель:** BE
- **Пакет:** `@platform/api-gateway`, `@platform/campaign-launcher-service`
- **Закрывает:** R1.5, R1.6, R2.3, R2.4, R3.1, R3.2, R3.3, R3.4
- **Зависит от:** T2, T8 и готовые аутентификация Gateway и профиль
- **Флаг:** —
- **Что сделать:** Включить операции для авторизованного автора в `api/openapi/platform.yaml` и сгенерировать типы при участии архитектора. В той же поставке подключить маршруты кабинета к подтверждённому контексту сессии. В Gateway получить профиль из Partners и передать подтверждённые идентификатор автора и снимок профиля в gRPC. Применить Origin, ограничения частоты и ошибки по дизайну.
- **Готово, когда:** Контрактные проверки подтверждают создание нескольких черновиков, чтение по UUID автором, отказ другому пользователю и создание черновика пользователем без организации.
- **Заметки:** —

### [ ] T6. Сохранение первого шага на лендинге

- **Исполнитель:** FE
- **Пакет:** `@platform/landing-campaign-launcher`
- **Закрывает:** R1.1, R1.2, R1.3, R1.4, R1.6, R1.7, R1.8, R1.9, R2.2, R2.5, R4.1, R4.2, R4.3, R4.4, R4.5, R4.6, R5.1, R5.2, R5.3, R5.4, R5.5
- **Зависит от:** T3, T4 и клиентская спецификация лендинга
- **Флаг:** —
- **Что сделать:** Через клиент host подключить гостевую сессию, восстановление, операции первого шага и Suggestion. При отсутствии cookie хранить форму в памяти вкладки. Игнорировать устаревшие ответы по ИНН. Применить блокировку перехода и запись по правилам первого шага.
- **Готово, когда:** Проверки охватывают валидные и невалидные значения, отключённые cookie, смену ИНН с ответами не по порядку и ручное переименование точки.
- **Заметки:** —

### [ ] T7. Сохранение первого шага в кабинете

- **Исполнитель:** FE
- **Пакет:** `@platform/app-campaign-launcher`
- **Закрывает:** R1.5, R2.3, R3.1, R3.2, R3.3, R3.4, R4.1, R4.6, R5.1, R5.3, R5.4, R5.5
- **Зависит от:** T3, T5 и клиентская спецификация кабинета
- **Флаг:** —
- **Что сделать:** Подключить модуль под базовым путём `/app`. Через клиент host подключить создание и выбор черновика по UUID. Применить начальные значения профиля и возвращённые признаки блокировки. Использовать правила первого шага и Suggestion из дизайна.
- **Готово, когда:** Проверки подтверждают повторное открытие сохранённых значений, сохранение редактируемых полей и несколько черновиков в кабинете.
- **Заметки:** —

### [x] T8. Общий префикс Gateway и маршруты платформы

- **Исполнитель:** BE
- **Пакет:** `@platform/api-gateway`, `@platform/api-client`
- **Закрывает:** Техническая зависимость T4 и T5
- **Зависит от:** —
- **Флаг:** —
- **Что сделать:** Зарегистрировать общий префикс `/api` с рабочим `api/openapi/platform.yaml`. В этой поставке зарегистрировать общие подсказки и выдачу флагов через `/v1/feature-flags/{web-app}`. В этой же поставке убрать регистрацию прежних префиксов, удалить их рабочие OpenAPI и обновить ссылки в клиентах, инфраструктуре и тестах. Выпустить рабочий контракт вместе с обработчиками и сгенерированными типами.
- **Готово, когда:** Общий API выдаёт подсказки и флаги по разрешённым идентификаторам. Неизвестное приложение получает 404. Контрактные проверки проходят по общим маршрутам. Прежние префиксы возвращают 404.
- **Заметки:** Проверены общий маршрут, схемы флагов и отказ по старым префиксам. Модульные, интеграционные и контрактные тесты выполнены на Node.js 26.
