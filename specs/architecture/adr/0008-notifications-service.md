# ADR 0008. Единый сервис нотификаций с независимыми результатами по каналам

## Контекст

Auth отправляет код до создания профиля. Partners приглашает коллегу на конкретный email. Обоим нужен безопасный повтор после потери ответа. Другие поручения могут включать сразу email и Telegram. Инициатор передаёт контакты и готовый текст, ожидает результат по каждому выбранному каналу в ответе на тот же запрос. Новый канал и смена почтового провайдера должны сохранять этот порядок работы. Основание — [требования 007](../../features/007-notifications/requirements.md).

Возникают два разных сбоя. Если получатель не указан, сервис точно знает, что попытки не было. Если почтовый сервер принял письмо и соединение оборвалось до ответа, сервис не может установить исход по факту обрыва. Переключение провайдера в этот момент может породить второе письмо с тем же кодом.

## Варианты

| Вариант | Польза | Цена |
|---|---|---|
| Библиотека доставки в каждом потребителе | Прямой вызов почтового сервиса, меньше сетевых переходов | Auth и Partners получают секреты провайдеров, ведут отдельные журналы и независимо разбирают спорные результаты. Смена провайдера требует координации релизов. |
| Отдельные сервисы email и Telegram | Каналы можно масштабировать и выпускать независимо | Для одного запроса на несколько каналов всё равно нужен владелец поручения, общего ответа и обработки повторов. В первой поставке это добавляет межсервисную координацию. |
| Один сервис с адаптерами каналов и почтовых провайдеров | Один владелец поручения и журнала. Каждый канал сохраняет свой результат, провайдеры заменяются внутри сервиса | Сервис становится общей зависимостью. Медленный канал требует отдельного бюджета времени, чтобы сохранить результаты остальных. |

## Решение

Предлагается третий вариант. Внутренний NestJS-сервис `notifications-service` принимает поручения по gRPC и владеет собственной PostgreSQL через Prisma. Потребители сохраняют ответственность за содержание, адресата и актуальность сообщения. Внешние маршруты Gateway для отправки не требуются.

### Одно поручение, отдельная попытка для каждого канала

1. Сервис устанавливает личность вызывающего сервиса и принимает стабильный идентификатор поручения. Пара «инициатор, идентификатор» уникальна. При повторе сверяется состав поручения, включая контакты, текст, исходный срок и множество каналов. Изменённое содержимое под прежним ключом вызывает конфликт. Новая разрешённая отправка того же текста получает новый ключ.
2. Для каждого канала сервис проверяет контакт и срок, регистрирует решение и закрепляет исполнителя попытки до внешнего вызова. Параллельные запросы с одним ключом не могут начать две отправки одного канала. Транзакция БД завершается до сетевого вызова. Каналы с корректными контактами выполняются независимо в пределах бюджета запроса.
3. В ответе каждый запрошенный канал получает один результат. Подтверждение приёма даёт «отправлено», пропуск до передачи или однозначный отказ в приёме — «не отправлено» с причиной. Обрыв после начала передачи даёт «отправка не подтверждена». Повтор с прежним ключом возвращает актуальные результаты. Пока исход начатой попытки неизвестен, новую копию сервис не отправляет.
4. Журнал связывает вход, проверку, попытку, ответ и последующее уточнение. Запись результата и соответствующее событие журнала атомарны. Если фиксация попытки невозможна, внешний вызов не начинается. После сбоя процесса на границе внешнего вызова неопределённость сохраняется. Это сознательный компромисс между риском пропуска и дубликата.
5. Перед каждой новой попыткой учитывается исходный срок. Auth передаёт срок кода, Partners проверяет актуальность приглашения перед передачей команды, включая явный повтор после временного отказа. Сервис нотификаций не запускает отложенную отправку приглашения самостоятельно. Проверить исход уже сделанной попытки можно и после истечения срока.

### Каналы и адаптеры

Внутри сервиса сценарий распределяет поручение между адаптерами каналов. Для email он выбирает почтовый транспорт. Внешние провайдеры подключаются отдельными адаптерами, первым предлагается Yandex Cloud Postbox. Выбор между собственным почтовым сервером и внешним провайдером задаёт постоянный серверный operational-флаг Unleash по [ADR 0001](0001-feature-toggles.md). Выбор фиксируется при создании попытки. После переключения флага подтверждения прежней попытки продолжает обрабатывать исходный адаптер.

Адаптер Postbox передаёт непрозрачный идентификатор попытки в метке письма. Успех SendEmail подтверждает приём. При потере ответа сервис принимает события из настроенного доверенного источника Postbox и сопоставляет событие Send с попыткой по метке, даже если идентификатор письма из ответа неизвестен. Обработка повторного события идемпотентна. Несопоставимое событие не меняет результат. Delivery и Bounce фиксируют последующую судьбу письма отдельно от приёма. [SendEmail](https://yandex.cloud/ru/docs/postbox/aws-compatible-api/api-ref/send-email) · [События Postbox](https://yandex.cloud/ru/docs/postbox/concepts/notification)

Для собственного сервера предлагается адаптер SMTP при подтверждении поддержки этого протокола. Положительный завершающий ответ сервера после передачи письма подтверждает приём. При потере этого ответа достоверное уточнение возможно только при наличии источника подтверждений у конкретного сервера. До его определения остаётся возможным длительное состояние «отправка не подтверждена».

Для Telegram инициатор передаёт телефон. Предлагается адаптер клиентского Telegram API с выделенной учётной записью отправителя, разрешением номера в личный чат и отправкой текста. Для использования в окружении нужны учётная запись, разрешённый сценарий отправки и соблюдение ограничений Telegram на поиск по номеру. При недоступном адресате email продолжает работать. MAX подключается в отдельной поставке через тот же интерфейс канала. [Разрешение номера](https://core.telegram.org/method/contacts.resolvePhone) · [Отправка сообщения](https://core.telegram.org/method/messages.sendMessage)

## Последствия

- Auth и Partners используют один внутренний контракт. По нему возвращается исход попытки передачи. Пользовательский ответ Auth о постановке письма на доставку сохраняет смысл, установленный фичей 005.
- Для эксплуатации нужны база сервиса, защищённый доступ к почтовым транспортам и Telegram, настроенный поток событий Postbox и контроль возраста неподтверждённых попыток. В журнале сохраняются безопасные идентификаторы и коды причин. Тексты, контакты, ссылки, учётные данные и исходные события провайдера с персональными данными исключаются из журналов и метрик.
- Обработка сообщений с истёкшим сроком, одновременный повтор, смена провайдера после потери ответа, частичный успех и повтор события провайдера становятся обязательными сценариями приёмки.

## Что нужно обновить

- После принятия ADR оформить дизайн и задачи 007 с моделями состояний, границами таймаутов, восстановлением после сбоя и покрытием критериев R1–R5.
- Описать внутренний контракт отправки в protobuf и зарегистрировать operational-флаг. Интеграции потребителей привязать к задачам 005/T4 и 006/T7.
- Добавить сервис в описание структуры платформы, уточнить инфраструктуру получения событий Postbox и условия подключения собственного почтового сервера и Telegram.

## Когда пересмотреть

Пересмотреть границы сервиса, если отдельному каналу потребуется независимое масштабирование или изоляция секретов на уровне развёртывания. Пересмотреть контракт, если инициаторам вместо ответа по каждому каналу понадобится только асинхронная постановка на доставку либо подтверждение получения сообщения конечным адресатом.
