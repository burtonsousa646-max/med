# Задачи: техническая основа API Gateway

## Общие проверки задач

Для каждого затронутого пакета с кодом обязательны `pnpm --filter <пакет> typecheck`, `test`, `build`, а также `pnpm lint` и `pnpm format:check`. Если меняется gateway — его интеграционные проверки `pnpm --filter @platform/api-gateway test:integration` на достигнутый объём. При изменении контрактов выполняются проверки из `ai/rules/api-contracts.md`; сами OpenAPI и proto меняет архитектор. Новые зависимости допускаются только из принятого стека и дизайна. Runtime-проверки и приёмка образа выполняются на Node.js 26.

### [x] T5. Реестр приложений и упаковка OpenAPI

- **Исполнитель:** BE
- **Пакет:** `@platform/api-gateway`; `@platform/api` — инструменты упаковки без изменения контрактов
- **Закрывает:** K4, K11
- **Зависит от:** T4
- **Флаг:** —
- **Что сделать:** реализовать `AppDefinition`, `OperationBinding`, `OpenApiRegistry` и стартовую сверку операций с контроллерами. Для NestJS 12.4 включить при создании приложения `routeResolutionStrategy: 'specificity'`; реестр сравнивает статические и параметрические сегменты слева направо по дизайну. Упаковывать JSON через существующий Redocly bundle, сохраняя исходные документы; до bundle проверять все ссылки и запрещать сетевые/выходящие за каталог. - **Готово, когда:** два тестовых приложения с одинаковыми путями и operationId различаются по префиксу; неизвестные адреса получают 404; конфликт префиксов/шаблонов, лишний контроллер, потерянная операция и отсутствующий локальный ref запрещают запуск. Проверки запускаются с фактическими версиями NestJS/Express/валидатора и проходят общие проверки.
- **Заметки:** Реестр и Nest выбирают статический сегмент при пересечении маршрутов; сквозные проверки подтверждают выбор валидатора, политики доступа и обработчика в обоих порядках объявления. Проверены конфликт шаблонов, лишний контроллер и отсутствующий локальный ref.
