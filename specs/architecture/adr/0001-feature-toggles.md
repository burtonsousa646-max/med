# ADR 0001. Feature toggles на Unleash, frontend получает флаги через API Gateway

## Контекст

В `tech-stack.md` для feature toggles выбран Unleash, а для frontend и backend заявлены пакеты `@platform/feature-flags`. Не было решено, как устроено остальное:

- откуда браузер получает флаги и кто задаёт контекст вычисления: пользователя и компанию;
- что происходит, если Unleash недоступен;
- как флаги заводятся в локальном окружении и проверяются в тестах;
- как флаги размечаются в коде и спецификациях, чтобы их можно было найти и удалить.

Ограничения платформы:

- frontend обращается только к API Gateway (`ai/rules/frontend.md`);
- компания и пользователь берутся только из сессии (`ai/rules/security.md`);
- секретов во frontend-коде нет;
- данные хранятся в России, внешние SaaS не используются (152-ФЗ).

## Варианты

### Вариант 1. Frontend получает флаги через API Gateway

Gateway вычисляет флаги серверным SDK Unleash с контекстом из сессии и отдаёт их операцией `GET /v1/feature-flags` из OpenAPI приложения.

- **Плюсы:**
  - одна внешняя точка входа, как во всей архитектуре;
  - контекст берётся из сессии, клиент не может его подделать;
  - в браузере нет токена Unleash;
  - наружу уходят только флаги, перечисленные в контракте приложения;
  - frontend получает типы флагов из контракта и не тянет новую зависимость.
- **Минусы:**
  - в каждом OpenAPI приложения есть операция и схема флагов;
  - gateway выполняет лишний запрос при загрузке приложения.

### Вариант 2. Браузер обращается к Unleash Frontend API или Unleash Edge

- **Плюсы:** официальный React SDK, в gateway ничего не нужно писать.
- **Минусы:**
  - вторая внешняя точка входа;
  - контекст вычисления задаёт клиент;
  - frontend-токен попадает в сборку;
  - браузеру видны имена всех флагов проекта;
  - нужна отдельная выкладка Edge.

## Решение

Выбран **вариант 1**. Он не нарушает правила «только gateway» и «компания только из сессии» и не выносит в браузер ни токены, ни лишние флаги.

### Устройство

```
браузер ── GET /v1/feature-flags ──► api-gateway ── unleash-client ──► Unleash
   host: FeatureFlagsProvider            │  контекст из сессии          ▲
   module: useFeatureFlag                │ gRPC metadata: пользователь, │
                                         ▼ компания                     │
                                    <name>-service ── unleash-client ───┘
```

1. **Unleash** развёрнут у себя. Все флаги лежат в проекте `default`. Окружение определяется токеном: `development` — локально, окружения стендов и production заводятся вместе с ними.
2. **Backend.** Пакет `server/shared/feature-flags` (`@platform/feature-flags`):
   - внутри — официальный `unleash-client`, флаги вычисляются локально в процессе;
   - сервис проверяет флаг через свой порт `application/ports/feature-flags.port.ts`, реализация лежит в `infrastructure/feature-flags/`;
   - флаг проверяется в сценарии (`application`) или в gateway, в `domain` никогда.
3. **Контекст вычисления** — только идентификаторы: `userId`, `companyId`. Gateway берёт их из сессии и передаёт в сервисы в gRPC metadata вместе с пользователем и компанией. Персональных данных в контексте нет.
4. **Web.** В `api/openapi/<app>.yaml` есть операция `getFeatureFlags` и схема `FeatureFlags`: по одному необязательному boolean-полю на каждый флаг, видимый этому приложению.
   - Схема — белый список: gateway вычисляет и отдаёт ровно эти флаги и берёт их имена из OpenAPI-документа приложения, отдельного списка в коде gateway нет.
   - Пакет `web/packages/feature-flags` (`@platform/feature-flags`): host подключает `FeatureFlagsProvider`, module читает флаги хуком `useFeatureFlag<FeatureFlags>(name)`, тип флагов берётся из контракта. Пакет загружается в одном экземпляре через Module Federation.
   - На frontend новых зависимостей нет: провайдер — тонкая обёртка над клиентом API и TanStack Query.
5. **Флаги только boolean.** Варианты для A/B-тестов — отдельным ADR, когда понадобятся.

### Недоступность Unleash

Если Unleash недоступен, отдаются флаги из кеша.

| Где | Кеш | Если кеша нет |
|---|---|---|
| сервис и gateway | SDK хранит последнее состояние в памяти и в backup-файле на диске: после перезапуска при недоступном Unleash он читается из файла | все флаги выключены, работает старое поведение |
| frontend | `FeatureFlagsProvider` хранит последний ответ gateway: ошибка обновления не сбрасывает полученные флаги | все флаги выключены |

- Unleash не входит в `/health/ready`: его недоступность не снимает сервисы с трафика.
- Сервис стартует, не дожидаясь Unleash.
- Поведение с выключенным флагом всегда рабочее, поэтому «всё выключено» — безопасное значение по умолчанию.

### Флаги и их жизненный цикл

- **Флаги вводит только архитектор** в разделе «Feature toggles» `design.md`. Разработчик размечает код только теми флагами, которые там описаны, и сам их не вводит.
- **Имя флага:** `<область>.<фича>.<что включает>` в kebab-case.
- **Типы Unleash:**

  | Тип | Срок жизни |
  |---|---|
  | `release` | временный, тип по умолчанию; удаляется после полного включения |
  | `kill-switch`, `operational` | постоянные, только с обоснованием в `design.md` |

- **Где флаг записан.** Архитектор указывает флаг в трёх местах:
  - `design.md`;
  - `deploy/unleash/flags.json` — локальное окружение;
  - схема `FeatureFlags` в OpenAPI, если флаг нужен frontend.
- **Реестр в коде.** Разработчик заводит флаг в реестре своего пакета с пометками `@spec`, `@task`, `@remove`.
- **Удаление** — отдельная задача: удаляются код старого поведения, запись в реестре, поле в схеме `FeatureFlags` (после того как frontend перестал его читать) и запись в `flags.json`.

### Без сессии

`getFeatureFlags` доступна и без сессии, например на экране входа. Тогда флаги вычисляются без `userId` и `companyId`, и ответ `401` не возвращается.

## Последствия

- Frontend и сервисы вычисляют флаги одинаково, с одним и тем же контекстом из сессии.
- Флаг для frontend — это изменение контракта приложения. Добавление поля в `FeatureFlags` — неломающее изменение. Удаление поля после того, как потребители перестали его читать, тоже не считается ломающим, это особый случай для флагов.
- Флаг, который gateway ещё не синхронизировал, приходит выключенным.
- После входа и выхода пользователя host перезапрашивает флаги: меняется контекст.
- В зависимостях backend появляется `unleash-client` — только в `server/shared/feature-flags`. Линтер запрещает импортировать SDK Unleash в другом месте.
- Локальное окружение: при первом старте Unleash создаёт токены из `deploy/.env`, а `pnpm env:up` заводит флаги из `deploy/unleash/flags.json`.
- Тесты не ходят в настоящий Unleash, кроме автотестов API и e2e: те включают флаги через Admin API локального окружения.

## Когда пересмотреть

- Понадобятся A/B-тесты с вариантами.
- Нагрузка на gateway от запросов флагов станет заметной.
- Флаги понадобятся внешним клиентам, у которых нет сессии.
- Сервисы начнут выкладываться в нескольких регионах: тогда стоит рассмотреть Unleash Edge между сервисами и Unleash.
