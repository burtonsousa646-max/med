# Вход, сессии и роли

Код — `server/modules/identity.ts`, тесты — `server/modules/identity.test.ts`, контракт — `api/cabinet.yaml` (партнёр) и `api/admin.yaml` (сотрудник).

## 1. Партнёр: вход через бизнес-ID

Провайдеры: Госуслуги (`gos`), СберБизнес ID (`sber`), Альфа ID для бизнеса (`alfa`), ЛК билайн бизнес (`b2b`). Яндекс ID в порте предусмотрен, в списке не показывается, пока не решено, нужен ли он.

```
кабинет                  api                               провайдер (порт idp)
   │ POST /auth/start {provider}                              │
   │──────────────────────►│ cookie oauth_state=<provider>.<state>, 10 мин
   │◄──────── { url } ─────│                                  │
   │────────────── переход по url ───────────────────────────►│
   │◄──────── /auth/callback/<provider>?code&state ───────────│
   │──────────────────────►│ сверка state с cookie
   │                       │ idp.exchange(code) → человек [+ компания]
   │                       │ users / identities; companies + memberships(owner, signer)
   │◄──── 302 /cabinet, cookie sid ─│
```

- Человек ищется по `(provider, subject)`. Новый — создаётся.
- Если провайдер подтвердил полномочия человека в организации, адаптер возвращает компанию. Платформа создаёт её по ИНН (или находит существующую) и делает человека владельцем и подписантом.
- Остальные участники попадают в компанию только по приглашению владельца (день 2).
- После входа выбрана компания из ответа провайдера или первая из тех, где человек состоит.

Заглушка: `/api/stub/idp` — форма «ИНН, ФИО, почта». Доступна вне production или с `ALLOW_STUB_LOGIN=1`. Возвращает только на свой адрес колбэка.

## 2. Партнёр: вход по коду в SMS

Основной способ на экране входа рядом с бизнес-ID. Входа по почте нет — решение 02.11.2026: он не будет использоваться. Почта остаётся только каналом писем (приглашения, уведомления, запрос подписи).

1. `POST /auth/phone/start { phone }` — код из 6 цифр в SMS (порт `messaging`, канал `sms`, шаблон `login_code`). Номер приводится к виду `+7XXXXXXXXXX`, принимаются только мобильные 9XX (иначе 422). Срок — 10 минут, повторно — не раньше чем через минуту (иначе 429), лимит частоты — как у входа.
2. `POST /auth/phone/verify { phone, code }` — неверный код увеличивает счётчик, после 5 ошибок код сгорает. Верный — одноразовый, ставит cookie `sid`. Учётная запись — identity `phone`, подтверждённый номер пишется в `users.phone`.

Пока `INT_MESSAGING=stub` и вход-заглушка разрешён (не production или `ALLOW_STUB_LOGIN=1`), код приходит в ответе `start` полем `devCode`, и экран показывает его под полем кода — иначе на стенде войти по телефону нельзя. С настоящим SMS-шлюзом поле пропадает само.

Человек без компании видит `/auth/me`, но `/cabinet/*` отвечает 403 «выберите или добавьте компанию».

## 3. Почему учётные записи не склеиваются по почте

Если бы вход через провайдера склеивался с существующей записью по почте, то человек, указавший у провайдера чужую неподтверждённую почту, получил бы чужую учётную запись вместе с компанией. Поэтому:

- в `users.phone` попадает только номер, подтверждённый кодом из SMS; `users.email` вход больше не заполняет;
- почта и телефон от провайдера лежат в `identities.data` как контакт, а не как ключ;
- один человек, вошедший двумя способами, — две записи; объединить их можно будет явным действием с подтверждением обеих сторон, когда понадобится.

## 4. Сотрудник билайна

`POST /auth/staff/start` → корпоративный SSO (порт `staffSso`) → `/auth/staff/callback` → 302 в `/admin`.

- Роли приходят из SSO при каждом входе и перезаписывают сохранённые: сняли роль в каталоге — сняли и здесь.
- Без единой роли платформы — 403.
- Отключённый сотрудник (`staff.active = false`) не входит, даже если SSO пускает.

Заглушка: `/api/stub/sso` — форма «почта, имя, роли через запятую».

## 5. Сессии

| | Партнёр | Сотрудник |
|---|---|---|
| срок | 30 дней | 12 часов |
| cookie | `sid`, httpOnly, SameSite=Lax, Secure в production | то же |

В cookie — случайные 32 байта, в базе — их SHA-256: утечка базы не даёт войти. `POST /auth/logout` удаляет сессию из базы, старый токен больше не действует.

## 6. Роли и права

Проверка в обработчиках — промежуточные функции `partner(...roles)` и `staff(...roles)`. Компания и роль берутся из сессии, а не из запроса.

Роли партнёра:

| Роль | Кто | Что может (по плану дня 2) |
|---|---|---|
| owner | владелец, вошёл через бизнес-ID | всё; если `signer` — принимать оферту и подтверждать оплату |
| staff | маркетолог | кампании и статистика; оплату отправляет руководителю на подтверждение |
| accountant | бухгалтер | баланс, документы, счета |
| agency | агентство | кампании субклиентов |

Роли сотрудников:

| Роль | Что может |
|---|---|
| moderator | очередь модерации |
| manager | партнёры, кампании, спецпроекты |
| finance | платежи, корректировки, выплаты |
| admin | всё, включая справочники и журнал интеграций |

## 7. Изоляция компаний

Каждый запрос кабинета видит только компанию из сессии. Сменить её можно только на ту, где человек состоит (`POST /auth/company`, иначе 403). Тест «чужая компания недоступна» проверяет это. Политики строк PostgreSQL (RLS) — следующий уровень защиты, до подключения реальных партнёров ([architecture.md](architecture.md#44-изоляция-компаний)).
