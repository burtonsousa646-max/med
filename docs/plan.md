# Рекламная платформа билайна: архитектура и план работ

29.10.2026. Цель — из прототипов собрать автономную рабочую платформу: партнёр сам запускает рекламу, абонент видит её на поверхностях, клики и результаты считаются, деньги списываются, документы формируются, сотрудники билайна модерируют и управляют. ## 0. Укладываемся ли в 3–4 дня

**Да, если «полноценная» значит пилот на тестовых данных.** Все внутренние процессы настоящие: вход, кампании, модерация, аукцион, показ, клик, конверсия, баланс в копейках с двойной записью, документы, бэкофис, отчёты. Каждая внешняя система подключена через свой порт с заглушкой, которая ведёт себя как настоящая (асинхронно, с вебхуками и ошибками).

**Нет, если речь о промышленной эксплуатации.** За 3–4 дня не сделать: реальные интеграции (зависят от команд билайна, доступов и договоров), ИБ-аудит и аттестацию по ПДн, нагрузку уровня миллионов показов в час, юридическую часть (оферта, договор с ОРД, агентская схема). Это следующий этап, и архитектура под него заложена.

Резерв — 4-й день. Если отстаём, режем по порядку: PDF документов (оставляем HTML), отчёт о приросте, загрузку баз хешей, OpenRTB-выход.

## 2. Архитектура

Модульный монолит на TypeScript: один репозиторий, один язык, два процесса из одного кода. Модули общаются через функции, не по сети. Когда билайну понадобится вынести модуль в отдельный сервис (например, показ — под нагрузку), граница уже проведена.

### 2.2 Показ: как выбирается реклама

`POST /public/serve { placement, context: { geo, screen, time }, medId? }` → до 50 мс:

1. **Отбор**: живые кампании с этим местом показа из индекса в памяти (перечитывается раз в 5 с и по событию).
2. **Фильтры**: расписание, гео (радиус от точки), сегмент, остаток бюджета и баланса, частота (не больше 3 показов кампании на MED-ID за 7 дней), стоп-листы, исключения «не для конкурентов», не больше 3 рекламодателей на один триггер.
3. **Скор**: `ставка × pCTR × качество`. pCTR — априорный по месту и типу оффера, сглаженный наблюдаемым CTR кампании (байесовское среднее). ML-модель — порт, подключим у Big Data.
4. **Аукцион**: обобщённая вторая цена (GSP) на несколько мест слота. Собственные офферы билайна — с теневой ставкой «конверсия × маржа».
5. **Ответ**: креатив, erid, подписанный токен показа. Поверхность шлёт маяк показа и ведёт клик через `/c/<token>`.

Оплачиваемый клик — по правилам из «Триггеров», раздел 5.4: открылась целевая страница, повторный клик того же MED-ID за 24 ч бесплатный, тап раньше 0,5 с не считается.

### 2.3 Деньги

- Все суммы в копейках, `bigint`. Двойная запись: каждая операция — проводки, сумма которых ноль. Баланс — сумма проводок, не поле.
- Счета: баланс партнёра, бонусный баланс, холд под кампанию, выручка билайна, выплаты партнёру, сбор ОРД 3%, расчёты со шлюзом.
- Идемпотентность: каждая денежная операция несёт ключ, повтор возвращает тот же результат.
- Списания за клик пишутся пачкой раз в минуту из событий (не на каждый клик), остаток для фильтра показа — в памяти с допуском перерасхода не больше одного клика на кампанию.

### 2.4 Данные абонента

Платформа не хранит номера телефонов абонентов. Ключ — MED-ID (случайный ID из контура билайна). Без интеграции с DMP поверхность передаёт обезличенный ID устройства, и он играет роль MED-ID. Отчёт партнёру — только агрегаты, не меньше 50 человек в ячейке.

### 2.5 Что сознательно не ставим сейчас

| Не ставим | Чем закрываем | Когда добавить |
|---|---|---|
| Kafka | outbox-таблица в Postgres, воркер с `FOR UPDATE SKIP LOCKED` | когда событий больше ~2 тыс./с или билайн даст свою шину. Адаптер шины читает тот же outbox |
| ClickHouse | `events` с партициями по дням + почасовые свёртки | когда отчёты по событиям станут медленнее 1 с |
| Redis | индекс кампаний и счётчики частоты в памяти процесса | когда API больше одного экземпляра |
| Kubernetes | systemd на VPS | при переезде в облако билайна |
| ML pCTR | байесовское сглаживание | при подключении Big Data |
| VCG | GSP | когда в слоте больше 3 мест и это влияет на доход |

## 3. Интеграции

Принцип: у каждой внешней системы свой порт — интерфейс в терминах платформы (не в терминах системы). Сейчас за портом заглушка, потом адаптер билайна. Переключение — переменная окружения `INT_<СИСТЕМА>=stub|beeline`. Ядро про конкретную систему не знает.

Общее для всех портов:
- **Исходящие асинхронные** вызовы идут через outbox: запись в той же транзакции, что и изменение, воркер отправляет с ретраями. Ничего не теряется, если система недоступна.
- **Входящие** — `/hooks/<система>` с проверкой подписи; повтор того же события безопасен.
- **`external_refs`** — связка любой нашей сущности с её ID во внешней системе (компания ↔ клиент в CRM билайна, креатив ↔ erid, платёж ↔ транзакция шлюза).
- **`integration_log`** — каждый запрос и ответ, без секретов и ПДн, виден в бэкофисе.

| 3.1 ✓ | Каталог мест показа и минимальных ставок; serving: отбор, фильтры, скор, GSP, теневая ставка | на одинаковых данных аукцион даёт предсказуемый результат — проверено тестом |
| 3.2 ✓ | Tracking: маяк показа, клик через редирект с `click_id`, правила оплачиваемого клика, частота | повторный клик за 24 ч не оплачивается |
| 3.3 ✓ | Конверсии: постбэк с HMAC, CSV, кабинет, споры, атрибуция по окнам | заявка из постбэка попадает в статистику и спор |
| 3.4 ✓ | Списания и пейсинг: клики и результаты → проводки, дневной бюджет, остановка по балансу | кампания без денег перестаёт показываться за минуту |
| 3.5 ✓ | Audiences: гео-радиус от точек и сигналы через `dmp` — в фильтрах показа, прогноз охвата в сборке. **Загрузка баз хешей отложена** (резерв плана) | показ учитывает гео и сигналы абонента |
| 3.6 ✓ | Витрина «лучшее рядом» как настоящая поверхность на serving + JS-сниппет для встраивания | витрина показывает кампании всех партнёров через аукцион |
| 3.7 ✓ | Нагрузочная проверка serve и click | p95 до 50 мс на стенде |

| # | Задача | Готово, когда |

| 4.1 ✓ | Бэкофис: очередь модерации, партнёры, кампании, финансы (корректировки, выплаты), места показа и ставки, журнал интеграций | сотрудник проходит модерацию и выплату без доступа к базе |

| 4.3 ✓ | Уведомления через `messaging`: заявка, мало денег, кампания отклонена | события доходят в заглушку и видны в журнале |

## 5. Скиллы и инструменты

| Где | Что |
|---|---|
| перед стартом, по желанию | `grilling` — прогнать план через жёсткие вопросы |
| модерация, помощник, поиск витрины | `claude-api` — модель, кэширование подсказок, структурированный ответ |
| бэкофис и перенос экранов | `impeccable` и `frontend-design` в рамках `design-system/` |
| отчёты и графики | `dataviz` |
| конец каждого дня | `code-review`, `simplify`, обновление `docs/` |
| день 4 | `security-review` |
| проверка в браузере | встроенный браузер и Playwright |

Дни 2–4 содержат независимые задачи (например, документы и маркировка, бэкофис и отчёты). После фундамента их можно вести параллельными сессиями — это сократит срок до 3 дней.

## 6. Риски

| Риск | Что делаем |
|---|---|
| День 3 перегружен | serving и tracking — в первую очередь, аудитории по сигналам упрощаем до гео |
| Заглушки расходятся с реальными системами | порты описаны в терминах платформы; карта интеграций (4.6) уходит командам рано, их ответы правят порты, а не ядро |
| Лицензия шрифта Beeline Sans на открытом стенде | стенд под паролем или без шрифта — решить до выкладки |
| Требования ИБ билайна к ПДн | номера абонентов не храним с первого дня, только MED-ID |
