# Стек платформы

Технологии новой платформы. Стек прототипа не используется. Версии здесь не указываются: они фиксируются в `package.json` и lock-файлах. Изменение стека — только через ADR в `specs/architecture/adr/`.

## Общее

|---|---|
| Менеджер пакетов | pnpm |
| Монорепо | pnpm workspaces — см. [structure.md](structure.md#монорепо) |

## Backend

| Область | Выбор |
|---|---|
| Рантайм | Node.js |
| Язык | TypeScript |
| Фреймворк | NestJS |
| База данных | PostgreSQL |
| ORM | Prisma |
| Очереди | BullMQ на Redis |
| Общение между сервисами | gRPC |
| Внешний вход | API Gateway |
| Feature toggles | Unleash |

**Архитектура:** микросервисы, внутри каждого сервиса — чистая архитектура. Frontend и внешние клиенты обращаются к сервисам только через API Gateway. Сервисы общаются между собой по gRPC. У каждого микросервиса своя база данных; в чужую базу сервис не ходит.

**Поставка:** каждый сервис — в своём Docker-контейнере.

## Контракты

Все контракты лежат в одном каталоге репозитория: OpenAPI для API Gateway и `.proto` для gRPC между сервисами. Путь к каталогу определяется вместе со структурой репозитория. Типы и клиенты для frontend и backend генерируются из этих контрактов.

## Логирование, мониторинг и healthcheck

> Статус: предложение, ждёт подтверждения.

Всё строится на OpenTelemetry и стеке Grafana, развёрнутом у себя: данные не уходят во внешние SaaS.

```
сервисы, gateway, frontend
        │  логи (stdout, JSON) · метрики · трассировки (OTLP)
        ▼
  OpenTelemetry Collector / Grafana Alloy
        │
        ├── Loki        — логи
        ├── Prometheus  — метрики
        └── Tempo       — трассировки
        ▼
     Grafana — дашборды, поиск, связь лог ↔ трасса
     Alertmanager — алерты
```

| Область | Выбор |
|---|---|
| Логи backend | pino (`nestjs-pino`), JSON в stdout |
| Сбор логов | Grafana Alloy → Loki |
| Метрики | OpenTelemetry SDK → Prometheus |
| Трассировки | OpenTelemetry SDK → Tempo |
| Ошибки и RUM frontend | Grafana Faro |
| Дашборды | Grafana |
| Алерты | Alertmanager |
| Healthcheck | `@nestjs/terminus`; для gRPC — стандартный `grpc.health.v1` |

### Логи

- Пишутся в stdout в JSON, в файлы не пишутся: сбор — забота инфраструктуры.
- Обязательные поля: `timestamp`, `level`, `service`, `version`, `env`, `trace_id`, `span_id`, `message`.
- `trace_id` проходит через весь путь: frontend → API Gateway → gRPC (metadata) → задачи в очереди Redis (в данных задачи).
- Уровни: `error` — нужна реакция; `warn` — нештатно, но обработано; `info` — значимые события; `debug` — только локально и на стендах.
- Не логируются: персональные данные, токены, коды из SMS, секреты, тела запросов целиком.
- Журнал действий пользователей и операций с деньгами — это аудит, а не логи: он хранится в базе сервиса.

### Метрики

- Каждый сервис отдаёт RED-метрики по HTTP и gRPC: число запросов, ошибки, длительность (p50, p95, p99).
- Метрики рантайма Node.js: задержка event loop, память, GC.
- Метрики зависимостей: пул соединений с базой, Redis, длина и возраст очередей, упавшие задачи.
- Бизнес-метрики — отдельно, с префиксом сервиса; какие именно — в `design.md` фичи.
- Feature toggles: метрики клиента Unleash.

### Трассировки

- Автоинструментирование HTTP, gRPC, Prisma, Redis.
- Контекст передаётся по стандарту W3C `traceparent`.

### Healthcheck

| Endpoint | Что проверяет | Кто использует |
|---|---|---|
| `GET /health/live` | процесс жив и отвечает; зависимости не проверяет | перезапуск контейнера |
| `GET /health/ready` | доступны своя база, Redis и обязательные для работы зависимости | приём трафика, `HEALTHCHECK` в Docker |
| `grpc.health.v1.Health/Check` | то же, что `ready`, для gRPC | API Gateway и другие сервисы |

- `ready` не проверяет другие микросервисы: иначе падение одного сервиса каскадом снимает с трафика остальные.
- Endpoint'ы health не требуют авторизации, не пишутся в логи и не попадают в метрики запросов.
- Frontend-контейнер отдаёт `GET /health` и `GET /version.json` с версиями хоста и микрофронтендов.

### Алерты

- Доля ошибок и p95 длительности выше порога.
- Сервис не готов дольше заданного времени.
- Растёт очередь или возраст старейшей задачи.
- Всплеск ошибок на frontend.

Пороги и каналы доставки алертов определяются отдельно.

## Открытые вопросы

- **Согласованность данных между сервисами.** У каждого сервиса своя база, поэтому изменение, затрагивающее несколько сервисов, нельзя выполнить одной транзакцией. Пример — оплата: кампания и баланс живут в разных сервисах. Нужно выбрать подход (transactional outbox, saga) и зафиксировать его в ADR.
- **Гарантия доставки событий через BullMQ.** Если события между сервисами должны доходить гарантированно, нужно определить требования к персистентности Redis.
- **Путь к каталогу контрактов** — вместе со структурой репозитория.
