# Пользователи, организации и приглашения коллег

## Обзор

Partners хранит профиль пользователя, актуальную организацию и приглашения. Владение кампанией и её авторство фиксирует Campaign Launcher. Связи устанавливаются при оформлении кампании, гостевой ввод ИНН остаётся в черновике. Основание — [R1–R4](requirements.md) и [ADR 0007](../../architecture/adr/0007-auth-and-partners-services.md).

## Затронутые части

Новый пакет `@platform/partners-service`, потребители Auth, Gateway и Campaign Launcher. Host кабинета предоставляет профиль и действия с приглашениями. Лендинг использует профиль при продолжении гостевого оформления.

## Взаимодействие

1. После проверки email Auth вызывает EnsureUserProfile с ключом регистрации. Partners возвращает стабильный userId, сохраняет первоначальный контактный email, оставляет организацию пустой. Повтор не перезаписывает контакты.
2. Gateway запрашивает GetUserProfile для вошедшего пользователя, показывает контакты и фактические реквизиты перед оформлением. Если есть членство, его организация приоритетна, в том числе при несовпадении с ИНН черновика.
3. При оформлении Campaign Launcher сначала проверяет право на исходный черновик, затем вызывает ResolveCampaignOrganization. Partners блокирует профиль и повторно читает членство. Если оно есть, возвращает текущую организацию. Иначе для свободного ИНН создаёт организацию и назначает первого представителя одной транзакцией. При занятом ИНН возвращает invitation_required. Черновик сохраняется. Если за время между показом формы и оформлением фактическая организация изменилась, Campaign Launcher возвращает конфликт и запрашивает подтверждение актуальных данных до завершения.
4. Для действий от имени организации Campaign Launcher проверяет пару через GetRepresentative. Partners выдаёт контакты и реквизиты только при действующем членстве. Владелец кампании и автор сохраняются при изменении членства. Права на конкретный черновик проверяются по правилам 004.
5. Создатель приглашения определяется из сессии. Partners проверяет его текущее право первого представителя, фиксирует адрес получателя и организацию. Ссылка для коллеги содержит идентификатор приглашения. При принятии Gateway передаёт подтверждённый адрес входа из Auth. Пользователь входит или регистрируется до принятия. Другой адрес либо другое текущее членство исключают присоединение.

## Контракты

[PartnersService](../../../api/proto/partners/v1/partners.proto): EnsureUserProfile для Auth; GetUserProfile для Gateway; ResolveCampaignOrganization и GetRepresentative для Campaign Launcher; CreateInvitation, AcceptInvitation, RevokeInvitation для Gateway. Для приглашения используется единый ресурс `/v1/partners/invitations/{invitationId}`. Клиент создаёт UUID. Gateway передаёт его в CreateInvitation как idempotency_key, Partners сохраняет тот же UUID как идентификатор приглашения. POST создаёт приглашение, PATCH с телом `{"status":"accepted"}` принимает его, DELETE отзывает. Повтор UUID другим создателем либо с другим адресом даёт 409 без раскрытия данных. Внешние операции чтения своего профиля, создания, принятия и отзыва приглашений описаны в [кандидате OpenAPI](../../../api/openapi-preview/auth-partners.yaml). Идентификаторы действующего пользователя и организации поступают из проверенного контекста. Внешняя команда произвольного присвоения ИНН отсутствует. Дополнения публикуются вместе с обработчиками в едином документе /api/v1. Межсервисные события для установления членства не требуются.

## Данные

Начальная миграция в отдельной PostgreSQL сервиса.

| Запись | Поля и ограничения |
|---|---|
| Пользователь | UUID, уникальный UUID регистрации, исходный подтверждённый адрес регистрации для проверки повтора, контактные email и телефон, необязательная ссылка на организацию. |
| Организация | UUID, уникальный ИНН строкой из 10 или 12 цифр, название для клиентов при наличии, идентификатор первого представителя. Создание возможно только вместе с его членством. |
| Приглашение | UUID, организация, нормализованный адрес, создатель, время создания и истечения, состояние, принявший пользователь. Не более одного ожидающего приглашения на организацию и адрес. |
| Повтор команды | Для создания приглашения сохраняются ключ запроса, создатель, исходные параметры и результат. Уникальность пары «создатель, ключ». |

## Согласованность и сбои

- Повтор регистрации с тем же ключом и адресом возвращает прежний профиль, с другими параметрами — конфликт. При гонке за ИНН проигравшая транзакция перечитывает актуальные данные. Нельзя создать две организации для одного пользователя или двух первых представителей для одного ИНН.
- При потере ответа после регистрации организации повтор оформления использует её прежний идентификатор и прежний ключ кампании. Истёкший дедлайн или недоступность Partners дают 503 без завершения защищённого действия.
- Для приглашения отсчитываются 5 суток от создания. Повтор транспортного запроса с прежним ключом возвращает тот же результат. Намеренная повторная отправка получает новый ключ, атомарно заменяет предыдущее приглашение той же организации и выдаёт новый срок. В той же транзакции Partners фиксирует задание доставки ссылки на адрес получателя. Адаптер нотификаций использует UUID приглашения как ключ доставки, повторяет временные сбои и проверяет актуальность приглашения перед отправкой. Поздно доставленная старая ссылка не восстанавливает приглашение. Подключение почтовой доставки зависит от контракта сервиса нотификаций.
- При принятии Partners в одной транзакции проверяет время, адрес, состояние и членство, сохраняет связь и отметку принятия. Повтор тем же получателем возвращает успех без восстановления прекращённого членства. Отзыв ожидающего приглашения доступен его создателю. При конкурирующих командах первая зафиксированная транзакция определяет допустимость следующей. На момент истечения срока приглашение недействительно даже до очистки записей.

## Feature toggles

Флаги не требуются. Чтение актуального членства обязательно для операций организации.

## Безопасность

UUID приглашения не предоставляет полномочий без подтверждения адреса получателя. Сравнение адресов использует правила 005. Вызовы Partners ограничены доверенными сервисами по назначению метода, заявленный userId браузера игнорируется. Чужие ресурсы скрываются ответом 404, конфликт состояния — 409. Персональные данные, ИНН и ссылки приглашений исключены из журналов и меток.

## Наблюдаемость

Счётчики создания и повторного использования профилей, конфликтов ИНН, отказов проверки членства и исходов приглашений. Измеряются длительность транзакций и доля временных сбоев. Алерты — ошибки регистрации, рост таймаутов и недоступность базы. Для диагностики используются requestId и тип операции.

## Риски и решения

Первичный захват свободного ИНН допускается правилами продукта. Споры, передача полномочий и политика прекращения членства требуют отдельного решения. Текущая поставка проверяет уже прекращённое членство и не вводит операцию его удаления.
