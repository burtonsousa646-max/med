# Стек платформы

Технологии новой платформы. Стек прототипа не используется. Версии здесь не указываются: они фиксируются в `package.json` и lock-файлах. Изменение стека — только через ADR в `specs/architecture/adr/`.

## Общее

| Область | Выбор |
|---|---|
| Рантайм | Node.js 26 LTS |
| Менеджер пакетов | pnpm |
| Монорепо | pnpm workspaces — см. [structure.md](structure.md#монорепо) |
| TypeScript | 6.0 — последняя версия, которую поддерживает typescript-eslint; переход на 7 — когда появится поддержка |
| Линтер | ESLint 10 с typescript-eslint (strict, с проверкой типов); для React — `@eslint-react/eslint-plugin` и `eslint-plugin-react-hooks` |
| Форматирование | Prettier |
| Сообщения коммитов | commitlint + husky |

## Frontend

| Область | Выбор |
|---|---|
| Рантайм | Node.js |
| Язык | TypeScript |
| Сборка | Vite |
| UI | React |
| Общий стор | TanStack Store |
| Роутинг | TanStack Router, файловый роутинг через `@tanstack/router-plugin` |
| Запросы и кеширование | TanStack Query; HTTP внутри запросов — openapi-fetch, типы — openapi-typescript |
| Стили | Vanilla Extract |
| Модульные тесты | Vitest + Testing Library, user-event |
| Разработка компонентов | Storybook — stories рядом с компонентами |
| Визуальные тесты | Storybook + Playwright: скриншоты stories |
| Контрактные тесты | Pact JS |
| Линтер и форматирование | ESLint + Prettier |
| Feature toggles | Unleash |

**Архитектура:** web-приложения на Module Federation. Каждое web-приложение — host и его module: host инициализирует общие провайдеры, клиент API и store, module — функциональные части приложения. У каждого web-приложения свой файл OpenAPI и один экземпляр клиента API — подробно в [structure.md](structure.md#web--frontend).

**Поставка:** весь frontend — host и module всех web-приложений — в одном Docker-контейнере.

## Backend

| Область | Выбор |
|---|---|
| Рантайм | Node.js |
| Язык | TypeScript |
| Фреймворк | NestJS |
| База данных | PostgreSQL |
| ORM | Prisma |
| Идентификаторы | UUID v7 |
| Очереди | BullMQ на Redis |
| Общение между сервисами | gRPC |
| Внешний вход | API Gateway |
| Модульные и интеграционные тесты | Vitest |
| Контрактные тесты | Pact JS |

**Архитектура:** микросервисы, внутри каждого сервиса — чистая архитектура. Frontend и внешние клиенты обращаются к сервисам только через API Gateway. Сервисы общаются между собой по gRPC. У каждого микросервиса своя база данных; в чужую базу сервис не ходит.

**Поставка:** каждый сервис — в своём Docker-контейнере.

## Контракты

Все контракты лежат в одном каталоге репозитория — `api/`: OpenAPI для API Gateway и `.proto` для gRPC между сервисами, см. [structure.md](structure.md#api--контракты). Типы и клиенты для frontend и backend генерируются из этих контрактов. Правила — `ai/rules/api-contracts.md`.

| Область | Выбор |
|---|---|
| Внешний API | OpenAPI 3.1 |
| Проверка OpenAPI | Redocly CLI |
| Клиент и типы для frontend | openapi-typescript + openapi-fetch |
| Валидация запросов в gateway | по OpenAPI во время работы |
| Protobuf: проверка, поиск ломающих изменений, генерация | Buf |
| Код из `.proto` для NestJS | ts-proto |
| Контрактные тесты | Pact JS |

## Тестирование

| Уровень | Что проверяет | Инструмент | Кто пишет |
|---|---|---|---|
| Модульный — frontend | компоненты, хуки, состояние | Vitest + Testing Library | frontend-разработчик |
| Визуальный | UI-компоненты из `components/` host и module — по stories | Storybook + Playwright, сравнение скриншотов | frontend-разработчик |
| Контрактный — frontend | запросы web-приложения к API Gateway: web-приложение — потребитель | Pact JS | frontend-разработчик |
| Модульный — backend | домен и сценарии сервиса | Vitest | backend-разработчик |
| Контрактный — backend | gateway выполняет контракты web-приложений; сервисы — контракты gateway и других сервисов по gRPC и событиям | Pact JS | backend-разработчик |
| Интеграционный | сервис с базой, Redis, очередями и gRPC | Vitest | backend-разработчик |
| Автотесты API | сценарии через API Gateway | Playwright | тестировщик |
| E2E | сценарий пользователя через frontend, gateway и сервисы | Playwright | тестировщик |

Тестировщик отвечает за план тестов фичи (`test-plan.md`), автотесты и e2e. Модульные, визуальные, контрактные и интеграционные тесты пишут разработчики в рамках своих задач.

**Контрактные тесты** — consumer-driven: потребитель описывает, какие запросы делает и какие ответы ожидает, Pact записывает это в pact-файл, а поставщик проверяет, что выполняет все pact-файлы своих потребителей. Это дополняет контракты в `api/`, а не заменяет их: OpenAPI и `.proto` описывают API целиком, pact-файлы — то, чем потребители реально пользуются. Контрактные тесты и pact-файлы для HTTP и gRPC лежат в `api/` рядом с контрактами, см. [structure.md](structure.md#api--контракты).

## Логирование, мониторинг и healthcheck

> Статус: предложение, ждёт подтверждения.

Всё строится на OpenTelemetry и стеке Grafana, развёрнутом у себя: данные не уходят во внешние SaaS.

```
сервисы, gateway, frontend
        │  логи (stdout, JSON) · метрики · трассировки (OTLP)
        ▼
  OpenTelemetry Collector / Grafana Alloy
        │
        ├── Loki        — логи
        ├── Prometheus  — метрики
        └── Tempo       — трассировки
        ▼
     Grafana — дашборды, поиск, связь лог ↔ трасса
     Alertmanager — алерты
```

| Область | Выбор |
|---|---|
| Логи backend | pino (`nestjs-pino`), JSON в stdout |
| Сбор логов | Grafana Alloy → Loki |
| Метрики | OpenTelemetry SDK → Prometheus |
| Трассировки | OpenTelemetry SDK → Tempo |
| Ошибки и RUM frontend | Grafana Faro |
| Дашборды | Grafana |
| Алерты | Alertmanager |
| Healthcheck | `@nestjs/terminus`; для gRPC — стандартный `grpc.health.v1` |

### Логи

- Пишутся в stdout в JSON, в файлы не пишутся: сбор — забота инфраструктуры.
- Обязательные поля: `timestamp`, `level`, `service`, `version`, `env`, `trace_id`, `span_id`, `message`.
- `trace_id` проходит через весь путь: frontend → API Gateway → gRPC (metadata) → задачи в очереди Redis (в данных задачи).
- Уровни: `error` — нужна реакция; `warn` — нештатно, но обработано; `info` — значимые события; `debug` — только локально и на стендах.
- Не логируются: персональные данные, токены, коды из SMS, секреты, тела запросов целиком.
- Журнал действий пользователей и операций с деньгами — это аудит, а не логи: он хранится в базе сервиса.

### Метрики

- Каждый сервис отдаёт RED-метрики по HTTP и gRPC: число запросов, ошибки, длительность (p50, p95, p99).
- Метрики рантайма Node.js: задержка event loop, память, GC.
- Метрики зависимостей: пул соединений с базой, Redis, длина и возраст очередей, упавшие задачи.
- Бизнес-метрики — отдельно, с префиксом сервиса; какие именно — в `design.md` фичи.
- Feature toggles: метрики клиента Unleash.

### Трассировки

- Автоинструментирование HTTP, gRPC, Prisma, Redis.
- Контекст передаётся по стандарту W3C `traceparent`.

### Healthcheck

| Endpoint | Что проверяет | Кто использует |
|---|---|---|
| `GET /health/live` | процесс жив и отвечает; зависимости не проверяет | перезапуск контейнера |
| `GET /health/ready` | доступны своя база, Redis и обязательные для работы зависимости | приём трафика, `HEALTHCHECK` в Docker |
| `grpc.health.v1.Health/Check` | то же, что `ready`, для gRPC | API Gateway и другие сервисы |

- `ready` не проверяет другие микросервисы: иначе падение одного сервиса каскадом снимает с трафика остальные.
- Endpoint'ы health не требуют авторизации, не пишутся в логи и не попадают в метрики запросов.
- Frontend-контейнер отдаёт `GET /health` и `GET /version.json` с версиями host и module всех web-приложений.

### Алерты

- Доля ошибок и p95 длительности выше порога.
- Сервис не готов дольше заданного времени.
- Растёт очередь или возраст старейшей задачи.
- Всплеск ошибок на frontend.

Пороги и каналы доставки алертов определяются отдельно.

## Открытые вопросы

- **Согласованность данных между сервисами.** У каждого сервиса своя база, поэтому изменение, затрагивающее несколько сервисов, нельзя выполнить одной транзакцией. Пример — оплата: кампания и баланс живут в разных сервисах. Нужно выбрать подход (transactional outbox, saga) и зафиксировать его в ADR.
- **Гарантия доставки событий через BullMQ.** Если события между сервисами должны доходить гарантированно, нужно определить требования к персистентности Redis.
- **Формы на frontend.** Библиотека форм не выбрана; до решения формы пишутся на состоянии компонента.
- **Pact для gRPC.** HTTP-контракты Pact JS поддерживает из коробки, gRPC — через плагин Protobuf. Плагин нужно проверить на первом сервисе.
- **Контракты событий в очередях** — отложено до первых сервисов с очередями. Pact поддерживает их как message-контракты; тогда же решим, где хранить их pact-файлы.
- **Pact Broker.** Pact-файлы хранятся в репозитории, в `api/pacts/`. Pact Broker понадобится, если сервисы будут выкладываться независимо и нужна проверка совместимости версий перед выкладкой (`can-i-deploy`).
- **Дизайн-система** пока вне рамок: где лежат токены и базовые компоненты, решается отдельно.
- **В каком окружении снимать эталоны визуальных тестов.** Эталоны лежат в `snapshots/` папки компонента. Отрисовка шрифтов и сглаживание отличаются на macOS и Linux, поэтому эталон, снятый на macOS, может не совпасть со скриншотом в CI на Linux. Варианты: снимать и сравнивать везде в одном Docker-образе Playwright; или снимать эталоны только в CI.
- **Проверка доступности в линтере.** `eslint-plugin-jsx-a11y` не поддерживает ESLint 10, поэтому правила доступности пока не подключены. Варианты: дождаться поддержки, взять форк или проверять доступность в тестах.
