# ADR 0003. Техническая основа API Gateway на NestJS с валидацией OpenAPI

## Контекст

API Gateway уже определён как единственный внешний вход платформы в [стеке](../tech-stack.md), [структуре](../structure.md#api-gateway) и [правилах архитектуры](../../../ai/rules/architecture.md). Он проверяет сессию и права, валидирует запросы по OpenAPI, вызывает сервисы по gRPC и собирает ответы. Бизнес-правила и бизнес-данные остаются в сервисах. [ADR 0001](0001-feature-toggles.md) поручает gateway выдачу флагов frontend.

В репозитории пока нет `server/apps/api-gateway/`, OpenAPI приложений и прикладных gRPC-контрактов. Из общих backend-пакетов существуют `tooling`, `contracts` и `feature-flags`; `config`, `logger`, `health` и `observability` описаны как целевые, но ещё не реализованы.

Человек выбрал поэтапное проектирование:

1. Техническая основа gateway: модули, контракты, транспорт, ошибки, сбои, healthcheck, feature flags и проверки.
2. После согласования первого этапа — требования к аутентификации совместно с аналитиком, затем её архитектура и реализация.

Первый этап относится к инфраструктуре по разделу «Работа вне фичи» [процесса SDD](../../../ai/rules/sdd.md). Этот ADR предлагает общие решения; дизайн реализации и задачи составляются после его принятия. Принятие ADR не означает согласование будущих сценариев входа.

## Варианты

### Вариант 1. Прикладной gateway на NestJS с Express и express-openapi-validator

Операции реализуются контроллерами NestJS. Middleware проверяет запросы по исходным OpenAPI-документам; gRPC-клиенты используют контракты платформы.

- **Плюсы:** соответствует выбранному NestJS; позволяет собирать ответы для экрана; проверка структуры запроса использует тот же документ, что и генерация типов.
- **Минусы:** нужно сопровождать адаптацию ошибок middleware и NestJS, проверять соответствие контроллеров контрактам; появляются зависимости HTTP-адаптера и валидатора.

### Вариант 2. NestJS с DTO и декораторами валидации

OpenAPI остаётся внешним контрактом, но runtime-валидация описывается отдельными DTO.

- **Плюсы:** привычная интеграция с NestJS, ошибки проходят через механизм фреймворка.
- **Минусы:** дублирование ограничений, возможность расхождения DTO и OpenAPI; сам по себе вариант не выполняет правило о runtime-валидации по исходному OpenAPI. Потребуется дополнительная генерация или сверка схем.

### Вариант 3. Отдельный инфраструктурный API Gateway и NestJS для агрегации

Валидация и маршрутизация выносятся в отдельный продукт, NestJS собирает ответы приложений.

- **Плюсы:** инфраструктурные политики можно централизовать за пределами приложения.
- **Минусы:** новый компонент вне стека, две конфигурации маршрутов и дополнительные эксплуатационные обязанности. Текущий объём задач не обосновывает такое усложнение.

### Вариант 4. NestJS с Fastify

Официальный `@nestjs/platform-fastify` предоставляет HTTP-слой с собственной экосистемой плагинов, валидацией и сериализацией по схемам маршрутов.

- **Плюсы:** потенциально меньшие накладные расходы HTTP-слоя по сравнению с Express; официальная интеграция с NestJS.
- **Минусы:** встроенная валидация схем маршрутов не заменяет загрузку исходного OpenAPI и проверку всех частей запроса по его операциям. Для нашего contract-first подхода нужно отдельно подобрать и проверить интеграцию; выбранный `express-openapi-validator` рассчитан на Express.

### Вариант 5. NestJS с NodeAdapter

Официальный `@nestjs/platform-node` работает поверх `node:http`, поддерживает многие Express middleware и рекомендован документацией NestJS начиная с версии 12.3. Используемая в workspace версия NestJS 12.4 позволяет рассмотреть этот адаптер.

- **Плюсы:** отсутствие Express как отдельного HTTP-фреймворка, потенциально меньшие накладные расходы; возможность использовать часть экосистемы Express.
- **Минусы:** совместимость с Express неполная; работа `express-openapi-validator` и необходимых middleware на этом адаптере в платформе не проверена. Рекомендация NestJS сама по себе не подтверждает совместимость нашего конвейера.

Устройство адаптеров и условия их сравнительных тестов описаны в [документации NestJS](https://docs.nestjs.com/techniques/performance), механизм валидации Fastify — в [документации Fastify](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/). Собственных замеров платформы нет; результаты простых HTTP-маршрутов не считаются оценкой производительности gateway с OpenAPI-валидацией и gRPC.

## Решение

Принят **вариант 1**. ADR согласован человеком 2026-11-17 в переписке; статус обновлён по его решению.

**Выбор HTTP-адаптера отдельно согласован человеком 2026-11-17:** оставляем Express (`@nestjs/platform-express`) с `express-openapi-validator`. Основание — готовая runtime-валидация по исходному OpenAPI 3.1 без повторного описания ограничений в DTO. Подключение к NestJS и нормализация ошибок остаются нашей задачей. Выбор не основан на утверждении, что Express быстрее альтернатив.

Fastify и NodeAdapter рассмотрены и для первого этапа не выбираются: потенциальный выигрыш HTTP-слоя пока не обоснован нагрузкой платформы, а интеграция исходного OpenAPI с Fastify и совместимость выбранного валидатора с NodeAdapter потребовали бы дополнительных проверок. Выбор адаптера был согласован отдельно до принятия ADR целиком.

### Границы первого этапа

В первый этап входят:

- пакет `@platform/api-gateway`, загрузка конфигурации и OpenAPI-документов;
- HTTP-конвейер, валидация запросов, единый формат ошибок;
- адаптеры gRPC с ограничением времени и отменой вызовов;
- механизм выдачи флагов по контракту приложения;
- healthcheck, безопасное логирование и завершение процесса;
- общие пакеты `config`, `logger` и `health` в минимальном объёме, необходимом gateway; их публичные интерфейсы фиксируются в последующем дизайне;
- модульные, интеграционные и контрактные проверки в границах реально появившихся потребителей.

Следующий этап определяет способ входа, создание и хранение сессий, выход, сроки жизни и отзыв сессий, роли, CSRF, лимиты попыток и доверенную передачу идентичности сервисам. В первом этапе нет временного входа, тестовых пользователей в рабочем процессе или доверия к пользовательским заголовкам идентичности. Бизнес-операции, очереди, загрузка файлов и внешние интеграции добавляются отдельными спецификациями.

### Пакет и модули

Структура развивает существующее описание gateway, не применяя к нему искусственный бизнес-домен:

```text
server/apps/api-gateway/
  src/
    routes/                 контроллеры и сборка ответов прикладных операций
    auth/                   граница определения контекста и проверки доступа
    clients/                адаптеры gRPC и преобразование транспортных типов
    feature-flags/          выдача флагов и реестр собственных флагов gateway
    openapi/                загрузка документов, выбор контракта, валидация
    errors/                 нормализация HTTP, gRPC и непредвиденных ошибок
    health/                 подключение @platform/health
    generated/              типы из api/openapi, руками не изменяются
    app.module.ts           сборка модулей и зависимостей
    main.ts                 запуск и завершение
  test/                     интеграционные проверки, тестовые контракты и gRPC-сервер
  Dockerfile
  package.json
```

Контроллер выбирает заранее определённый метод сервиса и преобразует данные. Клиент не задаёт адрес upstream, имя сервиса или метод gRPC. Расчёты, транзакции, инварианты, идемпотентность бизнес-команд и аудит выполняются в сервисах. Gateway не подключает Prisma, PostgreSQL или BullMQ; собственный Redis на первом этапе ему не нужен.

### OpenAPI и адреса приложений

У каждого приложения сохраняется свой `api/openapi/<app>.yaml`. Предлагается внешний префикс `/api/<app>`: например, полный адрес операции флагов кабинета — `/api/cabinet/v1/feature-flags`. В документе это `servers.url: /api/cabinet` и путь `/v1/feature-flags`. Имена `cabinet` и `backoffice` здесь — примеры, а не создание приложений.

Это позволяет двум приложениям иметь одинаковые пути `/v1/...` с разными схемами ответов, включая `FeatureFlags`. Gateway выбирает контракт по зарегистрированному префиксу. Этот выбор определяет схему API, но не даёт прав доступа. Неизвестный префикс и незарегистрированная операция возвращают 404; fallback на другой документ отсутствует.

Список приложений и привязка префикса к документу задаются в сборке gateway при добавлении контракта. Пути к файлам не принимаются из запроса. При запуске проверяются уникальность префиксов, корректность документов, отсутствие пересечений шаблонов маршрутов внутри приложения и соответствие прикладных контроллеров операциям OpenAPI в обе стороны. Неоднозначность или несоответствие блокирует готовность процесса.

В Docker-образ входят исходные OpenAPI-документы и их локальные зависимости `$ref`; получение схем по сети во время старта и запроса запрещено. Сгенерированные TypeScript-типы не заменяют runtime-схемы. Документы не генерируются из декораторов NestJS.

Пока нет ни одного согласованного приложения, gateway запускается только с healthcheck. Проверки конвейера используют синтетические документы из `test/fixtures/`, которые не становятся публичным API. Первая прикладная спецификация добавляет реальный документ и операции; каркас не создаёт фиктивные `cabinet.yaml` или `public.yaml`.

### HTTP и валидация

Предлагаются `@nestjs/platform-express` и `express-openapi-validator` как зависимости gateway. Валидатор заявляет поддержку OpenAPI 3.1 и Express в [официальном репозитории](https://github.com/cdimascio/express-openapi-validator). NestJS позволяет подключать middleware HTTP-платформы через `app.use()` — [документация NestJS](https://docs.nestjs.com/middleware). Совместимость конкретных версий с Node.js и NestJS из workspace подтверждается интеграционной проверкой до реализации прикладных маршрутов.

Конвейер запроса:

1. Создать серверный идентификатор запроса; установить ограничение размера тела и времени HTTP-запроса.
2. Выбрать зарегистрированные приложение и операцию по адресу и методу.
3. Разобрать тело и проверить его, параметры пути, query и контрактные заголовки по OpenAPI.
4. Применить политику доступа операции.
5. Вызвать контроллер, а при необходимости — gRPC-клиент.
6. Сформировать HTTP-ответ; преобразовать любую ошибку в общий формат.

Конкретные настройки валидатора: `validateRequests` включён, `allowUnknownQueryParameters: false`, `removeAdditional: false`, `coerceTypes: false` для тела, `allErrors: false`. Политика следует [документации настроек запросов](https://cdimascio.github.io/express-openapi-validator-documentation/usage-validate-requests/): неизвестные query-параметры отклоняются; лишние свойства не удаляются молча; преобразование query/path выполняется по схемам, без такого преобразования JSON-тела. В объектах запросов закрытого состава указывается `additionalProperties: false`. Неизвестная операция не пропускается к контроллерам.

`validateSecurity: false`: проверкой доступа владеет модуль `auth`, отключение проверки валидатором не делает операции публичными. Автоматическая загрузка обработчиков и файлов отключена. Проверка ответов по OpenAPI обязательна в интеграционных проверках; в рабочем процессе первого этапа она выключена. Ошибки Express middleware и NestJS проходят через один нормализатор; отдельно проверяется, что стандартные HTML-ответы Express не выходят наружу.

### Граница аутентификации

Публичной считается только операция с явным `security: []` на уровне операции. Для всех остальных операций первый этап возвращает `401` с кодом `unauthenticated` до вызова контроллера. Именованная схема `security`, для которой ещё нет реализации, не открывает доступ. Healthcheck — отдельное техническое исключение.

Контекст анонимного запроса не содержит пользователя и компании. Cookie и заголовки `Authorization`, `x-user-id`, `x-company-id` и аналогичные поля сами по себе не создают контекст; gateway не пересылает их в gRPC metadata. Порт получения подтверждённого контекста и его расширение для ролей определяются на этапе аутентификации. Разработка первого этапа не создаёт публичного механизма эмуляции сессии.

В первом этапе CORS не включается: предполагается размещение web и API под одним origin через инфраструктуру окружения. Иная топология требует явного списка origin и отдельного решения при проектировании входа. Терминация TLS и правила reverse proxy уточняются для стенда; до этого gateway не доверяет forwarded-заголовкам для идентификации клиента. Защищённые операции не могут быть выложены до согласования модели доверия gateway → сервис.

### gRPC, таймауты и сбои

Клиенты используют `@platform/contracts` и его `PROTO_LOADER_OPTIONS`; transport DTO остаются в `clients/` и на HTTP-границе. Адреса сервисов задаются конфигурацией и валидируются при старте. До появления реального сервиса транспорт проверяется на локальном тестовом gRPC-сервере, без создания производственного mock-сервиса.

Предлагаемые технические значения по умолчанию: общий бюджет обработки операции — 10 секунд, отдельный gRPC-вызов — не больше 3 секунд и не больше остатка общего бюджета, JSON-тело — не больше 1 МиБ. Конфигурация может менять их в пределах положительных значений, причём бюджет отдельного вызова не превышает общий. Это ограничения каркаса, а не SLO продукта; увеличение для конкретной операции требует описания в её дизайне.

Дедлайн gRPC передаётся upstream. Разрыв HTTP-соединения и исчерпание общего бюджета отменяют незавершённые gRPC-вызовы. Транспорт не выполняет автоматических повторов, включая повторы после `UNAVAILABLE`: даже таймаут не доказывает, что команда не была выполнена. Повторяемость и идемпотентность конкретных операций определяет их спецификация. Необратимый результат нельзя гарантировать локальным кешем gateway.

По умолчанию все части агрегированного ответа обязательны: ошибка одной зависимости завершает запрос ошибкой и отменяет оставшиеся вызовы. Частичный результат допускается только по явно согласованному контракту операции. Сбой сервиса затрагивает его операции, но не снимает весь gateway с трафика.

### Единые ошибки

Формат соответствует [правилам контрактов](../../../ai/rules/api-contracts.md): `{ code, message, details? }`, текст для человека — по-русски. `details` включается только для разрешённых контрактом структурированных данных и не содержит значений запроса, внутренних адресов, стеков или текстов исключений. Заголовок `X-Request-Id` содержит серверный идентификатор; добавлять его в тело каждой ошибки не требуется.

| Источник | HTTP | Код по умолчанию |
|---|---|---|
| Ошибка структуры запроса, JSON, `INVALID_ARGUMENT` | 400 | `invalid_request` |
| Нет подтверждённой сессии, `UNAUTHENTICATED` | 401 | `unauthenticated` |
| `PERMISSION_DENIED` | 403 | `permission_denied` |
| Неизвестный маршрут, `NOT_FOUND` | 404 | `not_found` |
| `ALREADY_EXISTS`, `ABORTED` | 409 | `conflict` |
| `FAILED_PRECONDITION` | 422 | `business_rule_violation` |
| Слишком большое тело | 413 | `payload_too_large` |
| Неподдерживаемый Content-Type | 415 | `unsupported_media_type` |
| `RESOURCE_EXHAUSTED` | 429 | `rate_limit_exceeded` |
| `UNAVAILABLE`, `DEADLINE_EXCEEDED`, исчерпание бюджета операции | 503 | `service_unavailable` |
| Непредвиденная ошибка, остальные коды gRPC | 500 | `internal_error` |

413 и 415 дополняют общую таблицу HTTP-ошибок платформы после принятия ADR. `RESOURCE_EXHAUSTED` используется как 429 только для явно распознанного ограничения клиента; неизвестное исчерпание ресурсов upstream преобразуется в 503. Отмена после отключения клиента не требует HTTP-ответа. Коды gRPC и разрешённые машинные коды бизнес-ошибок проверяются по контракту операции; произвольные сообщения upstream клиенту не передаются. Сокрытие чужого ресурса через 404 обеспечивается сервисом, владеющим ресурсом.

### Feature toggles

Сохраняется ADR 0001: gateway подключает `@platform/feature-flags`; операция `getFeatureFlags` возвращает только свойства схемы `FeatureFlags` выбранного приложения. Отдельный список выдаваемых флагов в коде не ведётся. На первом этапе контекст анонимный, отсутствующие значения считаются выключенными, Unleash не влияет на readiness.

Механизм проверяется на тестовом контракте с разными схемами двух приложений. Рабочий маршрут появляется вместе с первым реальным OpenAPI приложения, с явным `security: []`. Ответ не кешируется общим HTTP-кешем: `Cache-Control: no-store`, чтобы будущие персональные значения не смешивались между сессиями. Новых флагов этот ADR не вводит; техническая основа не скрывается за release-флагом.

### Конфигурация, healthcheck и завершение

Конфигурация читается один раз через `@platform/config`. Она включает HTTP- и внутренний gRPC-health-порты, адрес привязки, бюджеты времени, размер тела, адреса реально подключённых сервисов и существующие переменные Unleash. Значения, единицы измерения, диапазоны и имена переменных фиксируются в дизайне до передачи разработчику. Неверная конфигурация и отсутствующий обязательный файл схемы запрещают запуск.

`GET /health/live` показывает работоспособность процесса. `GET /health/ready` и внутренний `grpc.health.v1.Health/Check` проверяют завершение локальной инициализации, загрузку контрактов и отсутствие остановки процесса. Другие сервисы и Unleash не входят в готовность; базу и Redis, которых у gateway нет, он не проверяет. Через gRPC gateway не предоставляет прикладных методов.

Healthcheck не требует сессии и не возвращает адреса, конфигурацию или секреты. Наружу доступен только прикладной HTTP-вход; доступность healthcheck для инфраструктуры и изоляция внутреннего gRPC-порта задаются окружением.

При SIGTERM/SIGINT gateway снимает readiness, прекращает принимать новые операции, ожидает текущие не более 15 секунд и отменяет оставшиеся вызовы, затем закрывает gRPC-клиенты и SDK Unleash. `live` остаётся успешным, пока процесс способен отвечать. Проверка учитывает известное ограничение остановки SDK Unleash из `tech-stack.md`.

### Наблюдаемость и безопасность

Логи идут только через `@platform/logger`: идентификатор запроса, приложение, шаблон маршрута, метод, статус, длительность, разрешённый машинный код ошибки. Сырые URL с query, тела, заголовки авторизации, cookie и персональные данные не записываются. Healthcheck исключается из журналов запросов.

Внешний request ID не становится доверенным идентификатором; gateway создаёт свой. Это не заменяет будущие `trace_id` и `span_id`. Стек OpenTelemetry/Grafana остаётся отдельным неподтверждённым решением: этот ADR не вводит `observability` и не обещает метрики или трассировки, которых ещё нет. Дизайн фиксирует границы подключения HTTP/gRPC-метрик и трассировки для последующего этапа.

Ни в конфигурации репозитория, ни в тестах нет рабочих секретов и данных пользователей. В будущем пользователь и компания определяются исключительно по сессии; параметры клиента не могут заменить эту проверку.

## Последствия

- У gateway будет один процесс NestJS и один Docker-образ для всех окружений.
- Стек дополняется Express-адаптером NestJS и валидатором OpenAPI; версии и lock-файл меняются только при реализации согласованных задач.
- Префиксы `/api/<app>` становятся частью внешней адресации; host должен использовать соответствующий base URL. До появления потребителей перехода со старых адресов не требуется.
- Каркас можно проверить без бизнес-сервисов и готовой системы входа; он пока не предоставляет функциональность кабинета или бэкофиса.
- Закрытые операции остаются недоступными до второго этапа. Это ограничение первой поставки, которое нельзя обходить конфигурацией «доверять заголовкам».
- Нужны общие пакеты конфигурации, логирования и healthcheck; их реализация входит в план технической основы, а не предполагается существующей.
- Совместимость middleware с версиями платформы, порядок обработки ошибок и упаковка схем проверяются до добавления прикладных операций.

## Когда пересмотреть

- Появились требования к публичному API внешних клиентов, отдельным доменам или иной адресации приложений.
- Выбранная библиотека не поддерживает используемую часть OpenAPI 3.1 или несовместима с платформой.
- Подтверждённые нагрузочные требования требуют другого HTTP-адаптера или инфраструктурного gateway.
- Потребовались потоковые ответы, WebSocket, большие файлы или длительные операции: текущие бюджеты и JSON-конвейер для них не определены.
- Согласованы требования к входу и ролям: отдельное решение расширяет границу `auth` и определяет доверие между gateway и сервисами.
