# Перенос фичи из прототипа

Как перенести фичу прототипа на новую платформу. Это та же новая фича по `ai/workflows/feature.md`, но с другим источником требований и дополнительной сверкой. Ниже — только отличия.

**Из прототипа берётся только CJM** — путь пользователя: сценарии, шаги, экраны, тексты, правила, ошибки и крайние случаи. Техническая реализация прототипа — код, архитектура, модули, модель данных, API, интеграции — не изучается и не переносится. Правило — `ai/rules/sdd.md`, раздел «Прототип: только CJM».

## Выбор фичи

Фича для переноса — законченный для пользователя путь в прототипе, который можно пройти и проверить отдельно: например, вход, подключение компании, запуск кампании, пополнение баланса, статистика.

Порядок переноса — от путей, без которых не пройти другие: вход и компания раньше кампаний, кампании раньше статистики и денег.

CJM изучается по запущенному прототипу (`cd prototype && npm install && npm run dev`) и по описаниям пользовательских сценариев в `docs/`. Технические разделы `docs/` — архитектура, модель данных, интеграции, выкладка — не используются.

## 1. Требования — аналитик

```
/analyst опиши требования к <фича> по CJM прототипа
```

Отличия от новой фичи:
- в `requirements.md` — `source: prototype`;
- требования описывают путь пользователя прототипа полностью: роли, шаги, экраны, тексты, правила, ошибки и крайние случаи;
- раздел «Отличия от прототипа» заполнен: где путь пользователя меняется и почему;
- путь, похожий на ошибку или упрощение, вынесен в открытые вопросы, а не перенесён молча.

**K1 — дополнительно проверить:**
- требования описывают весь путь пользователя, который есть в прототипе;
- каждое отличие от прототипа осознанное;
- в требованиях нет ничего из технической реализации прототипа.

## 2. Дизайн — архитектор

```
/architect спроектируй фичу NNN-slug
```

Архитектор проектирует фичу по требованиям в архитектуре платформы, как новую. На устройство прототипа он не смотрит.

**K2 — дополнительно проверить:**
- в дизайне нет решений, взятых из прототипа: его модулей, схемы базы, API, интеграций.

## 3. План тестов — тестировщик

Раздел «Сверка с прототипом» в `test-plan.md` заполнен: какие шаги пути пользователя сверяются с прототипом и где ожидаются отличия по требованиям.

## 4. Разработка

Как в новой фиче. Frontend-разработчик повторяет экраны и путь пользователя запущенного прототипа, кроме отличий в требованиях. Код прототипа никто не изучает и не переносит.

## 5. Проверка — тестировщик

```
/qa проверь фичу NNN-slug со сверкой с прототипом
```

Тестировщик проходит сценарии в запущенном прототипе и в платформе и сверяет шаги, экраны и тексты. Расхождение, которого нет в «Отличиях от прототипа», — дефект или вопрос.

## После переноса

- Источник правды для фичи — `specs/features/NNN-slug/`. `docs/` и `prototype/` не меняются.
- Прототип не удаляется, пока он не будет заменён целиком.
