# Тестирование

Как писать и запускать тесты. Правило для разработчиков, тестировщика и архитектора. Кто какие тесты пишет и какими инструментами — `specs/architecture/tech-stack.md`, раздел «Тестирование». План тестов фичи — `test-plan.md` по шаблону `ai/templates/test-plan.md`.

## Кто что пишет

| Уровень | Кто | Где лежит | Команда |
|---|---|---|---|
| Модульный — frontend | frontend-разработчик | рядом с кодом, `*.test.tsx` | `pnpm --filter <пакет host или module> test` |
| Визуальный | frontend-разработчик | stories рядом с компонентом в `components/`, `*.stories.tsx` | `pnpm --filter <пакет host или module> test:visual` |
| Модульный — backend | backend-разработчик | рядом с кодом, `*.spec.ts` | `pnpm --filter @platform/<service> test` |
| Интеграционный | backend-разработчик | `test/` сервиса, `*.test.ts` | `pnpm --filter @platform/<service> test:integration` |
| Контрактный | frontend- и backend-разработчики | `api/contract-tests/` | `pnpm --filter @platform/api test:contract` |
| Автотесты API | тестировщик | `tests/api/specs/<NNN-slug>/` | `pnpm --filter @platform/api-tests test` |
| E2E | тестировщик | `tests/e2e/specs/<NNN-slug>/` | `pnpm --filter @platform/e2e test` |

Контрактные тесты — `ai/rules/api-contracts.md`, раздел «Контрактные тесты».

## Общие правила

- **Тест проверяет поведение, а не реализацию.** Тест не должен ломаться при рефакторинге, который не меняет поведение.
- **Тест связан с требованием.** Тест на критерий приёмки упоминает его номер в названии или описании: `R1.2`. Автотест и e2e упоминают номер тестового случая: `TC5`.
- **Название — на русском и описывает ожидаемое поведение:** `it('не даёт отправить кампанию без креатива')`.
- **Структура — подготовка, действие, проверка.** Одно действие на тест.
- **Тест независим.** Сам создаёт свои данные, не зависит от порядка запуска и других тестов, убирает за собой.
- **Тест детерминирован.** Время — через фиктивные часы или порт часов, случайность — с фиксированным зерном, сеть — только к тому, что тест поднял сам.
- **Без фиксированных пауз.** Вместо `sleep` — ожидание условия.
- **Данные — синтетические.** Реальные персональные данные в тестах запрещены. Данные создаются фабриками с осмысленными значениями по умолчанию.
- **Моки — только на границе.** В модульных тестах подменяются порты и внешние зависимости, а не внутренние функции тестируемого модуля.
- **Нестабильный тест** не пропускается молча: он чинится сразу или помечается с причиной и задачей на исправление, о чём сообщается человеку.
- **Нельзя** ослаблять проверки, пропускать или удалять тесты, чтобы проверка прошла.

## Модульные тесты — frontend

- Vitest и Testing Library, окружение jsdom; настройки — `@platform/web-config/vitest`.
- Элементы ищутся по ролям и доступным именам: `getByRole('button', { name: 'Отправить' })`. Поиск по классам, `data-testid` и структуре DOM — только если по-другому нельзя.
- Действия пользователя — через `@testing-library/user-event`, а не прямой вызов обработчиков.
- Запросы к API подменяются на уровне клиента `@platform/api-client`, а не мокированием хуков TanStack Query.
- Проверяются состояния загрузки, пустое, ошибки и нет прав.

## Визуальные тесты

- Источник визуальных тестов — stories Storybook: каждая story компонента — отдельный визуальный тест. Отдельных файлов визуальных тестов нет.
- Снимаются UI-компоненты из `src/components/` host и module, а не страницы.
- Playwright открывает каждую story собранного Storybook, снимает скриншот и сравнивает с эталоном.
- Stories покрывают все варианты и состояния компонента: данные, пусто, ошибка, загрузка, нет прав.
- Данные в stories — фиксированные; анимации отключены; время и случайность зафиксированы.
- Эталонные скриншоты обновляются только осознанно — когда изменение внешнего вида предусмотрено задачей — и коммитятся вместе с ним.
- Где хранить эталоны и в каком образе их снимать — открытый вопрос в `specs/architecture/tech-stack.md`.
- Дизайн-система пока вне рамок визуальных тестов.

## Модульные тесты — backend

- Vitest; настройки — `@platform/server-tooling/vitest`.
- Домен тестируется без NestJS и без моков: это чистый код.
- Сценарии тестируются с подменёнными портами; проверяется результат и вызовы портов, важные для поведения.
- Для каждого сценария — успешный путь, каждое нарушение бизнес-правила, нет прав, повтор.

## Интеграционные тесты

- Сервис целиком или его инфраструктурный слой с настоящими PostgreSQL и Redis из `pnpm env:up`.
- Отдельная база для тестов: `<name>_service_test`. Перед запуском применяются все миграции.
- Каждый тест работает в своих данных: чистит таблицы до теста или использует уникальные идентификаторы.
- Проверяются: репозитории и маппинг, транзакции и откат, ограничения базы, задачи BullMQ и их повторы, gRPC-контроллеры с маппингом ошибок.
- Другие сервисы и внешние системы подменяются заглушками портов.

## Автотесты API и e2e

- Playwright. Пакеты — `tests/api` (`@platform/api-tests`) и `tests/e2e` (`@platform/e2e`).
- Запускаются на поднятой локально платформе или стенде; адрес — из переменной окружения.
- Данные создаются через API платформы в подготовке теста, а не напрямую в базах.
- E2E — только сценарии пользователя целиком. Проверки правил и ошибок, которые не требуют интерфейса, — в автотестах API или ниже.
- Элементы ищутся по ролям и доступным именам; ожидания — встроенные в Playwright.
- Проверяются сценарии с включёнными и выключенными feature toggles, если флаг меняет поведение.
- Запуск против боевого окружения запрещён.

## Покрытие

- Каждый критерий приёмки покрыт хотя бы одним тестом — это проверяет таблица покрытия в `test-plan.md`.
- Процент покрытия кода — сигнал, а не цель. Домен и сценарии покрываются полностью; код, который нельзя проверить тестом, — повод пересмотреть код.
