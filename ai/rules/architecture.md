# Архитектура

Принципы, по которым устроена платформа, и правила зависимостей. Правило для всех ролей, которые проектируют и пишут код. Стек — `specs/architecture/tech-stack.md`, структура репозитория — `specs/architecture/structure.md`, решения — `specs/architecture/adr/`.

## Общая схема

```
браузер
  └─ web-приложение: host ── module, module …   (Module Federation)
            │ HTTP, OpenAPI приложения
            ▼
        api-gateway ── единственный внешний вход
            │ gRPC
            ▼
        <name>-service ──gRPC──► <name>-service
            │                         │
         своя база                 своя база
            └──── события (BullMQ на Redis) ────┘
```

## Сервисы

- **Граница сервиса — бизнес-возможность**, а не техническая функция: «кампании», «биллинг», «модерация», а не «база», «уведомления по почте в общем виде».
- **Сервис владеет своими данными.** У каждого сервиса своя база, её схема описана только в его `prisma/`. Ни один сервис не читает и не пишет в чужую базу.
- **Данные другого сервиса** получаются только через его gRPC API или его события.
- **Новый сервис, изменение границ сервиса, перенос данных между сервисами** — только через ADR.
- **Сервис не знает о frontend.** Форма ответа для экрана собирается в gateway.

## Взаимодействие

| Способ | Когда |
|---|---|
| gRPC, синхронно | нужен ответ сейчас: запрос данных, команда, результат которой нужен вызывающему |
| событие, асинхронно | изменение должно дойти до других сервисов, но вызывающему не нужно ждать |
| HTTP через gateway | только для frontend и внешних клиентов |

- Синхронные цепочки вызовов короткие: не больше двух переходов между сервисами в одном запросе пользователя. Длиннее — повод пересмотреть границы или перейти на события.
- Каждый межсервисный вызов имеет таймаут. Повтор вызова допустим только для идемпотентных операций.
- Распределённых транзакций нет. Согласованность данных между сервисами — открытый вопрос в `specs/architecture/tech-stack.md`; до решения в ADR операция, затрагивающая несколько сервисов, проектируется в `design.md` с явным описанием поведения при сбое на каждом шаге.
- Контракты событий отложены до первых сервисов с очередями.

## API Gateway

- Единственная точка входа для frontend и внешних клиентов.
- Проверяет сессию и права, валидирует запрос по OpenAPI, вызывает сервисы, собирает ответ.
- Не содержит бизнес-логики и не хранит бизнес-данные.
- Компания и пользователь берутся из сессии, а не из параметров запроса.

## Чистая архитектура внутри сервиса

```
presentation ──► application ──► domain
      │               ▲
      ▼               │ реализует порты
infrastructure ───────┘
```

| Слой | Что в нём | Может зависеть от |
|---|---|---|
| `domain` | сущности, объекты-значения, доменные события, инварианты, доменные ошибки | ни от чего, кроме стандартной библиотеки |
| `application` | сценарии (use cases), порты — интерфейсы репозиториев и внешних систем | `domain` |
| `infrastructure` | реализации портов: Prisma, BullMQ, gRPC-клиенты, внешние системы | `application`, `domain` |
| `presentation` | gRPC-контроллеры, обработчики очередей, преобразование ошибок | `application`, `domain` |

- `domain` не импортирует NestJS, Prisma, gRPC и любые библиотеки ввода-вывода.
- `application` знает только порты, а не их реализации.
- Типы Prisma и сгенерированные типы gRPC не выходят за `infrastructure` и `presentation`: на границе они преобразуются в доменные типы.
- Правила кода сервиса — `ai/rules/backend.md`.

## Web-приложения: host и module

- **Web-приложение** — отдельный продукт для своих пользователей: кабинет партнёра, бэкофис. У каждого свой файл OpenAPI `api/openapi/<app>.yaml` и свой экземпляр клиента API; клиент ходит только в API Gateway.
- **Host** — оболочка web-приложения в Module Federation, по одному на приложение. Инициализирует общее для приложения: клиент API, `QueryClient`, общий store, провайдер feature toggles и другие провайдеры, — отвечает за вход, навигацию, загрузку module и общую обработку ошибок.
- **Module** — функциональная часть web-приложения: отдельная сборка, которую загружает host. Граница module — бизнес-область внутри приложения: кампании, баланс, документы.
- Module получает клиент API, `QueryClient`, общий store и провайдеры от host и не создаёт своих.
- Module не импортирует код host и других module. Общее — только через провайдеры host и пакеты `web/packages/`.
- Общие библиотеки в одном экземпляре — только те, что перечислены в пресете Vite `@platform/web-config/vite`.
- Новое web-приложение и новый module — через ADR.
- Правила кода — `ai/rules/frontend.md`.

## Зависимости между пакетами

| Пакет | Может зависеть от | Не может зависеть от |
|---|---|---|
| `server/apps/*` | `server/shared/*` | другие `server/apps/*`, `web/*` |
| `server/shared/*` | другие `server/shared/*` | `server/apps/*`, `web/*` |
| `web/apps/<app>/host` | `web/packages/*` | module и другие web-приложения, `server/*` |
| `web/apps/<app>/modules/*` | `web/packages/*` | host, другие module, другие web-приложения, `server/*` |
| `web/packages/*` | другие `web/packages/*` | `web/apps/*`, `server/*` |
| `api` | пакеты, которые проверяют контрактные тесты | — |
| `tests/*` | `web/packages/api-client` и общие пакеты для тестов | код сервисов и приложений напрямую |

Сервисы связаны только контрактами в `api/`, а не импортом кода друг друга.

## Скрипты пакетов

Каждый пакет объявляет стандартные скрипты, если они к нему применимы. Корневые команды `pnpm typecheck`, `pnpm test`, `pnpm build` запускают их во всех пакетах.

| Скрипт | Что делает | В каких пакетах |
|---|---|---|
| `typecheck` | проверка типов | все с TypeScript |
| `test` | модульные тесты | все с кодом |
| `storybook` | Storybook для разработки компонентов | host и module web-приложений |
| `test:visual` | визуальные тесты stories — Storybook + Playwright | host и module web-приложений |
| `test:visual:update` | обновить эталоны визуальных тестов | host и module web-приложений |
| `test:integration` | интеграционные тесты | `server/apps/*` |
| `test:contract` | контрактные тесты | `api` |
| `build` | сборка | приложения, сервисы, пакеты со сборкой |

Скрипты пакета `api` — в `ai/rules/api-contracts.md`.

## Конфигурация

- Конфигурация — только из переменных окружения, читается и проверяется при старте через `@platform/config`. Неверная конфигурация — сервис не стартует.
- Адреса, ключи и секреты не хранятся в коде.
- Один образ Docker на сервис для всех окружений: окружения отличаются только переменными.

## Feature toggles

Решение — `specs/architecture/adr/0001-feature-toggles.md`, устройство и пакеты — `specs/architecture/tech-stack.md` и `specs/architecture/structure.md`.

- **Только Unleash и пакеты `@platform/feature-flags` (backend) и `@platform/web-feature-flags` (web).** SDK Unleash вне этих пакетов запрещён линтером. Frontend получает флаги только от API Gateway операцией `getFeatureFlags`, в Unleash напрямую не обращается.
- **Флаги вводит только архитектор** — в разделе «Feature toggles» `design.md` фичи. Разработчик размечает код флагами из дизайна и задач и своих флагов не вводит.
- **Имя флага:** `<область>.<фича>.<что включает>` в kebab-case, например `campaigns.launch.new-checkout`.
- **Тип Unleash:**

  | Тип | Срок жизни |
  |---|---|
  | `release` | временный, по умолчанию |
  | `kill-switch`, `operational` | постоянные — только с обоснованием в `design.md` |

  Флаги только boolean.
- **Где флаг записан.** Архитектор указывает его в `design.md`, в `deploy/unleash/flags.json` и, если флаг нужен frontend, в схеме `FeatureFlags` OpenAPI приложения.
- **Контекст** — только `userId` и `companyId` из сессии. Других данных пользователя в контексте нет.
- **Одна точка ветвления.** На backend флаг проверяется в сценарии сервиса или в gateway, на frontend — в маршруте или на входе в экран. В `domain` и в `components/` флаги не читаются.
- **Разметка в коде.** Имя флага берётся только из реестра пакета: `application/feature-flags.ts` сервиса, `src/feature-flags/` gateway, `src/model/featureFlags.ts` host и module. У каждой записи реестра есть JSDoc с `@spec NNN-slug`, `@task Tn`, `@remove <задача или условие>`. Строки с именами флагов по месту запрещены.
- **Unleash недоступен** — отдаются флаги из кеша, а без кеша все выключены. Поэтому поведение с выключенным флагом всегда рабочее и проверяется тестами.
- **Удаление.** Флаг `release` после полного включения удаляется отдельной задачей. Вместе с ним удаляются код старого поведения, запись в реестре, поле в `FeatureFlags` и запись в `flags.json`.

## Наблюдаемость и healthcheck

- Каждый сервис и gateway отдают `/health/live`, `/health/ready` и `grpc.health.v1` через `@platform/health`.
- Логи — только через `@platform/logger`, `console` запрещён линтером.
- Стек наблюдаемости ещё не подтверждён — раздел в `specs/architecture/tech-stack.md`. До подтверждения действуют только правила этого раздела.

## Решения

- Решения, которые меняют платформу в целом, оформляются ADR по шаблону `ai/templates/adr.md` в `specs/architecture/adr/`.
- Когда ADR обязателен — раздел «Когда нужен ADR» в `ai/agents/architect.md`.
- Код, который расходится с принятым ADR, — дефект архитектуры: либо исправляется код, либо пишется новый ADR.
