# Общие правила

Правила для всех ролей. Агент читает этот файл до начала любой работы.

## Ветки

Основная ветка — `main`. Работа ведётся в отдельной ветке от `main`.

| Ветка | Когда |
|---|---|
| `feature/<NNN-slug>` | фича по спецификации `specs/features/NNN-slug/` |
| `fix/<NNN-slug>` | исправление ошибки в уже реализованной фиче |
| `refactor/<slug>` | изменение структуры репозитория или кода без изменения поведения |
| `chore/<slug>` | работа вне фичи: инфраструктура, зависимости, `ai/` |

`<NNN-slug>` совпадает с каталогом спецификации, например `feature/004-campaign-launch`.

## Коммиты

### Кто коммитит

Агент готовит один или несколько коммитов: группирует изменения и пишет сообщения по правилам ниже. Человек проверяет их и согласовывает.

Перед **каждым** коммитом агент:
1. Добавляет в индекс только файлы этого коммита.
2. Показывает человеку список файлов и полный текст сообщения.
3. Ждёт явного согласования и только после него коммитит.

Правила согласования:
- Просьба «закоммить» — это задача подготовить коммит, а не согласование сообщения: агент всё равно сначала показывает коммит.
- Согласование действует только на показанный коммит. Если после согласования изменились файлы или сообщение, агент показывает коммит заново.
- Серию коммитов можно согласовать одним ответом, если агент показал их все.
- Так же, с отдельным согласованием, выполняются `push`, `amend`, `rebase` и любое другое переписывание истории.
- Агент не обходит проверки: `--no-verify` запрещён.

### Формат

Формат — [Conventional Commits](https://www.conventionalcommits.org/ru/). Тип и область пишутся по-английски, описание и тело — по-русски.

```
<тип>(<область>): <описание>

<тело — необязательно>

Spec: <NNN-slug>
Task: <номер задачи из tasks.md>
Agent: <id роли>
```

Формат проверяет commitlint: хук `commit-msg` локально и проверка в CI. Конфигурация — `commitlint.config.mjs` в корне репозитория.

### Тип

| Тип | Когда |
|---|---|
| `feat` | новая функциональность для пользователя или другого сервиса |
| `fix` | исправление ошибки |
| `refactor` | изменение кода без изменения поведения |
| `perf` | ускорение без изменения поведения |
| `test` | только тесты |
| `docs` | только документация в `specs/` |
| `spec` | требования, дизайн, задачи и план тестов фичи |
| `contract` | изменение контрактов в `api/` |
| `build` | зависимости, сборка, Dockerfile, `deploy/` |
| `ci` | CI |
| `chore` | прочее, что не попадает в код продукта, например `ai/` |

### Область

Имя пакета без префикса `@platform/` или каталог верхнего уровня:
- сервисы и приложения: `campaigns-service`, `api-gateway`, `shell`, `cabinet`;
- общие пакеты: `design-system`, `logger`;
- остальное: `api`, `deploy`, `ai`, `specs`.

Если коммит затрагивает несколько пакетов одной задачи, указывается основной. Если основного нет, область не указывается.

### Описание

- Начинается со строчной буквы, без точки в конце, не длиннее 72 символов вместе с типом и областью.
- Говорит, что изменилось в системе, а не что делал автор: `feat(billing-service): пополнение баланса через СБП`, а не `добавил метод`.

### Тело

Пишется, если из описания не понятно, **почему** сделано именно так. Отделяется от описания пустой строкой. Список изменённых файлов не нужен.

### Служебные строки

Пишутся последним блоком после пустой строки, в таком порядке:

| Строка | Когда |
|---|---|
| `BREAKING CHANGE: <что сломалось и как перейти>` | при ломающем изменении |
| `Spec: <NNN-slug>` | обязательна для `feat`, `fix`, `refactor`, `perf`, `test`, `contract` в рамках фичи |
| `Task: <номер>` | вместе со `Spec:` — номер задачи из `tasks.md` |
| `Agent: <id роли>` | обязательна, если коммит подготовил агент; `id` — из frontmatter файла роли, например `backend-developer` |

По `Spec:` и `Task:` можно найти, какому требованию соответствует код, и наоборот. По `Agent:` видно, какая роль подготовила изменение.

### Ломающие изменения

Отмечаются `!` после области и строкой `BREAKING CHANGE:`.

```
contract(api)!: статус кампании возвращается объектом

BREAKING CHANGE: поле status теперь { code, reason } вместо строки
Spec: 012-campaign-moderation
Task: T3
Agent: architect
```

### Размер коммита

- Одна задача из `tasks.md` — один или несколько коммитов. Один коммит — не больше одной задачи.
- Каждый коммит проходит проверки затронутых пакетов: типы, линтер, тесты.
- Сгенерированный код коммитится вместе с изменением контракта, из которого он получен.

### Примеры

```
feat(campaigns-service): отправка кампании на модерацию

Spec: 004-campaign-launch
Task: T2
Agent: backend-developer
```

```
fix(cabinet): баланс не обновлялся после пополнения картой

Кеш баланса сбрасывался до ответа шлюза, поэтому экран
перечитывал старое значение.

Spec: 007-balance-topup
Task: T5
Agent: frontend-developer
```

```
spec(specs): требования к входу по бизнес-ID

Spec: 002-business-id-login
Agent: analyst
```
