# Регистрация и вход по email

## Обзор

Оба шага используют `POST /v1/auth/email`. Тело только с email запрашивает письмо (202). Тело с email и code подтверждает вход (204). Gateway выбирает метод gRPC после проверки тела по OpenAPI. Поле code с неверным форматом даёт 400 до вызова Auth. Лимит отправки применяется только к запросу письма. При первом подтверждении auth-service регистрирует профиль через partners-service. Только после завершения регистрации Gateway устанавливает cookie сессии. При следующем входе сохраняется тот же пользователь. Основание — [R1–R3](requirements.md) и [ADR 0007](../../architecture/adr/0007-auth-and-partners-services.md).

## Затронутые части

Новый пакет `@platform/auth-service` владеет проверками и сессиями. API Gateway обслуживает HTTP, лимит посетителя и cookie. Host лендинга и кабинета использует общий клиент Gateway. Partners предоставляет идемпотентное создание профиля. Доставка писем — отдельная зависимость.

## Взаимодействие

1. При запросе кода Gateway получает идентификатор посетителя из проверенной cookie либо выпускает криптографически случайный идентификатор в защищённой cookie. Отдельный серверный ключ для ограничения запросов строится по идентификатору посетителя. В Redis ограничителя Gateway атомарно удаляет записи возрастом от двух часов и допускает до 15 запросов отправки за окно по всем адресам. Допущенный запрос учитывается до вызова Auth, включая случай отказа по минутному интервалу. При сбое ограничителя отправка закрыта.
2. Auth переводит email в нижний регистр перед всеми поисками и записями. Под блокировкой адреса создаёт шестизначный случайный код на 10 минут или повторно использует действующий код через минуту после предыдущей отправки. Повтор сохраняет срок и счётчик попыток. На пятой ошибке код блокируется до истечения исходного срока. Успех погашает код. Проверки для разных адресов независимы.
3. После подтверждения Auth закрепляет за адресом стабильный ключ регистрации. Вызов Partners с этим ключом создаёт профиль без организации и возвращает userId. После фиксации связи Auth открывает сессию. При повторном входе по уже привязанному адресу вызов создания профиля пропускается.
4. При защищённом действии Gateway проверяет access token через Auth. Состояние сессии проверяется на каждый запрос. Gateway различает пользовательские операции и фоновые запросы по назначению маршрута. Фоновые обновления и опрос состояния не продлевают срок бездействия. Если токен истёк во время работы, после тихого обновления Gateway учитывает успешно авторизованный повтор пользовательского запроса как активность. Для операции организации Gateway получает текущий профиль из Partners, кампании дополнительно проверяют пару у владельца членства.
5. При истечении access token клиент однократно вызывает refresh, объединяя параллельные обновления в одном host. Повтор исходной операции допускается только после ответа Gateway о том, что доступ отклонён до вызова обработчика. Сбой связи после передачи команды требует её собственной гарантии идемпотентности.

## Контракты

[Внешние операции](../../../api/openapi-preview/auth-partners.yaml) под общим префиксом /api/v1: запрос кода, подтверждение, тихое обновление и выход. Кандидат публикуется в едином OpenAPI вместе с обработчиками после интеграции единого маршрутизатора. Действующие контракты не меняются.

[AuthService](../../../api/proto/auth/v1/auth.proto) принимает запросы только от Gateway. RequestEmailCode и VerifyEmailCode обслуживают R1–R2, ValidateSession, RefreshSession и RevokeSession — R3. Для R2 используется EnsureUserProfile из [PartnersService](../../../api/proto/partners/v1/partners.proto). В login-ответе по gRPC токены предназначены для Gateway. Внешний HTTP-ответ устанавливает две cookie, тело токенов не содержит. Публичного API сервиса нотификаций этот дизайн не вводит.

## Данные

Собственная PostgreSQL и Prisma. Начальная миграция создаёт следующие записи.

| Запись | Поля и ограничения |
|---|---|
| Проверка адреса | Нормализованный email, шифротекст кода для повторной отправки, срок, последняя отправка, число попыток, состояние. Одна текущая проверка на адрес. |
| Способ входа | Уникальная пара provider и subject, UUID регистрации, состояние регистрации, userId после привязки. Один пользователь может иметь несколько способов входа. |
| Сессия | UUID, userId, хеш случайного refresh token, время последней пользовательской активности, отметка отзыва. Отдельная запись токена доступа содержит хеш, ссылку на сессию и время истечения. Хеши индексируются. |
| Доставка | Идентификатор отправки, ссылка на проверку, состояние. Создаётся вместе с решением об отправке. Истёкшие коды не доставляются. |

Предлагаемый срок access token — 15 минут. Refresh token действует в пределах живой сессии. При обновлении Auth под блокировкой сессии выдаёт новый access token, refresh token остаётся действительным до отзыва или таймаута бездействия. Для одновременного refresh из нескольких вкладок каждый выданный access token действует до собственного срока. Хеш последнего истёкшего токена остаётся доступен для распознавания access_expired на протяжении живой сессии. Выход отзывает всю сессию. Решение о бездействии использует серверное время и границу ≥ 24 часов.

## Согласованность и сбои

Проверка, изменение числа попыток и погашение кода сериализуются по адресу. Победивший запрос атомарно сохраняет успешную проверку и резервирует регистрацию. После сбоя Auth продолжает создание профиля по сохранённому ключу. Использованный код не позволяет получить новую сессию. Если браузер потерял ответ с cookie, новый вход потребует свежего подтверждения и вернёт тот же профиль.

Для доставки используется устойчивый идентификатор отправки. Адаптер передаёт его сервису нотификаций, чтобы после неоднозначного результата безопасно повторить попытку. Ответ о принятии запроса означает постановку на доставку. Ошибка до сохранения задания даёт 503. Сбой рассылки не влияет на открытые сессии. Реальная доставка зависит от согласования внутреннего контракта нотификаций.

Gateway явно разрешает машинный код access_expired только для ответа ValidateSession. Неверный код и недействительная сессия дают 401, ограничения — 429, недоступность владельца сессии — 503. Gateway прекращает обработку до прикладного вызова. Истёкший access token отличается машинным кодом access_expired, позволяющим клиенту запустить refresh. После отзыва или истечения сессии требуется новый вход.

## Feature toggles

Флаги не требуются. Новые маршруты публикуются вместе с готовыми обработчиками и адаптером доставки.

## Безопасность

Токены непрозрачные, генерируются криптографически стойким генератором. Gateway выставляет host-only cookie HttpOnly, Secure, SameSite=Lax и удаляет их с прежними атрибутами при выходе. Браузер сохраняет cookie доступа при истечении серверного срока access token, чтобы Gateway мог вернуть access_expired. Cookie доступа и обновления ограничены путями /api/v1 и /api/v1/auth/sessions соответственно. Для команд браузера Gateway проверяет Origin по списку доверенных приложений и запрещает кеширование ответов. В Logout принимается refresh cookie, в том числе при истёкшем access token. Сравнение кода и токенов защищено от временных утечек. Адреса, коды, токены и cookie исключены из журналов, трасс и меток. Ключ шифрования кодов поступает из конфигурации секретов.

## Наблюдаемость

Счётчики принятых и ограниченных отправок, исходов подтверждения и обновления. Отдельно измеряются возраст незавершённой регистрации и очередь доставки. Алерты — рост ошибок Partners, недоступность ограничителя, задания доставки старше срока кода. В логах только requestId и исход операции.

## Риски и решения

При очистке cookie меняется идентификатор посетителя. Общий сетевой ограничитель Gateway продолжает действовать. Дизайн доставки согласуется отдельно. Связь запуска кампаний с организацией описана в [дизайне 006](../006-partners/design.md).
