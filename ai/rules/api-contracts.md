# Контракты API

Как описываются, меняются, генерируются и проверяются контракты. Правило для архитектора, разработчиков и тестировщика. Расположение файлов — `specs/architecture/structure.md`, раздел `api/`.

## Принцип

Contract-first: сначала контракт, потом код.

- OpenAPI и `.proto` в `api/` — источник правды. Код gateway, сервисов и клиентов генерируется из них.
- Контракт меняет архитектор в рамках дизайна фичи. Разработчик, которому не хватает контракта, не обходит это, а останавливается.
- Pact-файлы в `api/pacts/` показывают, чем потребители реально пользуются. Изменение, которое ломает pact-файл, — ломающее изменение, даже если OpenAPI или `.proto` формально совместимы.

## OpenAPI — внешний API

Версия — OpenAPI 3.1. Один файл на web-приложение: `api/openapi/<app>.yaml`, например `cabinet.yaml`, `backoffice.yaml`. Файл описывает всё, что это приложение запрашивает у API Gateway. API для внешних клиентов — отдельным файлом, например `public.yaml`.

### Пути и операции

- Пути — существительные во множественном числе в kebab-case: `/campaigns/{campaignId}/creatives`.
- Версия API — в начале пути: `/v1/...`.
- Методы: `GET` — чтение, `POST` — создание и действия, `PATCH` — частичное изменение, `PUT` — полная замена, `DELETE` — удаление.
- Действие, которое не сводится к изменению ресурса, — `POST` на подресурс-глагол: `POST /v1/campaigns/{campaignId}/submit`.
- У каждой операции есть `operationId` в camelCase — по нему называются функции клиента: `getCampaign`, `submitCampaign`.
- У каждой операции есть `summary` на русском и `tags` с областью.
- В пути и параметрах нет `companyId` для операций кабинета: компания определяется по сессии.

### Данные

| Что | Как |
|---|---|
| имена полей | camelCase |
| идентификаторы | строка UUID |
| дата и время | строка ISO 8601 в UTC: `2026-11-08T10:15:00Z` |
| только дата | строка `YYYY-MM-DD` |
| деньги | строка с целым числом копеек, поле с суффиксом `Kop`: `"amountKop": "150000"` |
| перечисления | строки в lower_snake_case |
| необязательное поле | отсутствует в ответе, а не `null`; `null` — только если «нет значения» отличается от «не передано» |

Схемы выносятся в `components/schemas` и переиспользуются. Схема запроса и схема ответа — разные схемы, даже если сейчас совпадают.

### Списки

- Пагинация — по курсору: параметры `cursor` и `limit`, в ответе `items` и `nextCursor`.
- `limit` — с максимумом, указанным в контракте.
- Фильтры и сортировка — параметрами запроса, описанными в контракте.

### Ошибки

Все ошибки — в одном формате:

```yaml
Error:
  type: object
  required: [code, message]
  properties:
    code:    { type: string, description: машинный код ошибки в lower_snake_case }
    message: { type: string, description: текст для человека на русском }
    details: { type: object, additionalProperties: true }
```

| Статус | Когда |
|---|---|
| 400 | запрос не прошёл валидацию по контракту |
| 401 | нет сессии |
| 403 | нет прав на действие |
| 404 | ресурса нет или он принадлежит другой компании |
| 409 | конфликт состояния: действие недопустимо в текущем статусе, повтор с другим телом |
| 422 | запрос корректен, но нарушает бизнес-правило |
| 429 | превышен лимит запросов |
| 500, 503 | ошибка сервера, сервис недоступен |

Каждая операция перечисляет коды ошибок, которые может вернуть.

### Идемпотентность

Операции, которые создают платёж, списание или другой необратимый эффект, принимают заголовок `Idempotency-Key`. Повтор с тем же ключом возвращает тот же результат.

## Protobuf — gRPC между сервисами

Файлы — `api/proto/<service>/v1/*.proto`. Стиль проверяет Buf.

- Пакет: `platform.<service>.v1`, например `platform.campaigns.v1`.
- Сервис: `<Name>Service`, методы — глагол и существительное: `GetCampaign`, `SubmitCampaign`.
- У каждого метода свои сообщения `<Method>Request` и `<Method>Response`, даже если сейчас пустые.
- Поля — snake_case; номера полей никогда не переиспользуются; удалённые поля и номера — в `reserved`.
- Перечисления: первое значение — `<ENUM>_UNSPECIFIED = 0`, значения с префиксом имени перечисления.
- Время — `google.protobuf.Timestamp`, деньги — `int64` копеек с суффиксом `_kop`, идентификаторы — `string` UUID.
- Ошибки — стандартные коды gRPC; машинный код ошибки передаётся в деталях ошибки.

## Совместимость

Можно без версии:
- добавить операцию, метод, необязательное поле, значение перечисления, код ошибки.

Ломающее изменение:
- удалить или переименовать операцию, метод, поле;
- сделать поле обязательным, сменить тип или формат;
- изменить смысл поля или кода ошибки;
- сломать хотя бы один pact-файл.

Ломающее изменение:
1. отмечается в `design.md` фичи и в коммите `contract(...)!` со строкой `BREAKING CHANGE:`;
2. проводится в три шага: добавить новое → перевести всех потребителей → удалить старое; либо через новую версию `v2`;
3. не удаляет старое, пока хотя бы один pact-файл на него опирается.

## Генерация кода

| Из чего | Что | Куда | Инструмент |
|---|---|---|---|
| `api/openapi/<app>.yaml` | типы web-приложения; клиент — openapi-fetch, один экземпляр на приложение в host | `web/packages/api-client/src/generated/<app>.ts` | openapi-typescript |
| `api/openapi/*.yaml` | типы для gateway | `server/apps/api-gateway/src/generated/` | openapi-typescript |
| `api/proto/**/*.proto` | типы, клиенты и интерфейсы контроллеров NestJS | `server/shared/contracts/src/generated/` | Buf + ts-proto |

- Сгенерированный код руками не правится и коммитится вместе с изменением контракта.
- Gateway валидирует входящие запросы по OpenAPI во время работы, а не только по типам.

## Контрактные тесты

Consumer-driven контракты на Pact JS. Тесты — `api/contract-tests/`, pact-файлы — `api/pacts/`.

| Потребитель → поставщик | Тест потребителя | Pact-файлы | Проверка поставщика |
|---|---|---|---|
| web-приложение → api-gateway | `consumers/<app>/` — frontend-разработчик | `pacts/http/` | `providers/api-gateway/` — backend-разработчик |
| api-gateway → сервис | `consumers/api-gateway/` — backend-разработчик | `pacts/grpc/` | `providers/<name>-service/` — backend-разработчик |
| сервис → сервис | `consumers/<name>-service/` — backend-разработчик | `pacts/grpc/` | `providers/<name>-service/` — backend-разработчик |

Правила:
- Тест потребителя описывает только то, чем потребитель реально пользуется: поля, которые он читает, и ошибки, которые обрабатывает.
- Тест потребителя проверяет код потребителя — сгенерированный клиент и функции работы с API, — а не вручную собранный запрос.
- Ожидания — по типу и формату (matchers Pact), а не по конкретным значениям, кроме значений, важных для логики.
- Состояние поставщика задаётся через provider states с понятными именами: `кампания в статусе draft существует`.
- Pact-файлы создаются тестами и руками не правятся. Имя — `<consumer>-<provider>.json`.
- Проверка поставщика запускает его с заглушками его собственных зависимостей и проверяет все pact-файлы, где он поставщик.

## Скрипты пакета `api`

| Команда | Что делает |
|---|---|
| `pnpm --filter @platform/api lint` | проверка OpenAPI (Redocly) и `.proto` (Buf) |
| `pnpm --filter @platform/api breaking` | поиск ломающих изменений `.proto` относительно `main` (Buf) |
| `pnpm --filter @platform/api generate` | генерация кода из контрактов |
| `pnpm --filter @platform/api test:contract` | тесты потребителей и проверка поставщиков |

После любого изменения в `api/` прогоняются `lint`, `generate` и `test:contract`; после изменения `.proto` — ещё и `breaking`.
