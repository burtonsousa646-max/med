# Новая фича

Как провести новую фичу от запроса до приёмки. Процессом управляет человек: он запускает роли по шагам и согласует результат на контрольных точках. Правила процесса — `ai/rules/sdd.md`, вызов ролей — `ai/adapters/README.md`.

Команды ниже — в синтаксисе Claude Code и Gemini CLI. В Kimi Code — `/skill:<роль>`, в Codex — `$<роль>`.

## Схема

```
1. /analyst            requirements.md            ──► K1 человек согласует требования
2. /architect          design.md, tasks.md, api/  ──► K2 человек согласует дизайн, задачи, ADR
3. /qa                 test-plan.md               ──► K3 человек согласует план тестов
4. /backend-developer  задачи BE  ┐
   /frontend-developer задачи FE  ┘  параллельно  ──► K4 все задачи выполнены
5. /qa                 проверка фичи              ──► K5 человек принимает фичу
```

Шаги 3 и 4 начинаются после K2 и идут параллельно.

## 0. Ветка

```
git switch develop && git pull
git switch -c feature/NNN-slug
```

Номер `NNN` — следующий свободный в `specs/features/`. Если номер ещё не ясен, аналитик предложит его на шаге 1, а ветку можно переименовать.

## 1. Требования — аналитик

```
/analyst <что нужно сделать и зачем>
```

Аналитик заводит `specs/features/NNN-slug/requirements.md`, пишет требования и переводит документ в `review`.

**K1 — что проверить перед согласованием:**
- цель и пользователи понятны;
- у каждого требования есть проверяемые критерии приёмки `R1.1`;
- описаны ошибки, крайние случаи и «вне рамок»;
- открытые вопросы решены или явно отложены;
- нет решений о реализации.

Согласование — поставить `status: approved` в `requirements.md` и согласовать коммит аналитика.

## 2. Дизайн и задачи — архитектор

```
/architect спроектируй фичу NNN-slug
```

Архитектор пишет `design.md` и `tasks.md`, меняет контракты в `api/`, при необходимости — ADR, и переводит документы в `review`. Если нужен ADR, архитектор останавливается до его согласования.

**K2 — что проверить:**
- дизайн не меняет требования и не выходит за их рамки;
- затронутые сервисы, host и module названы, границы сервисов и module не нарушены;
- контракты изменены, ломающие изменения отмечены;
- описано поведение при сбоях, безопасность, флаги, наблюдаемость;
- каждый критерий приёмки закрыт задачами, у задач есть исполнитель BE или FE;
- ADR, если есть, — `accepted`.

Согласование — `status: approved` в `design.md` и `tasks.md`, `status: accepted` в ADR.

## 3. План тестов — тестировщик

```
/qa напиши план тестов для фичи NNN-slug
```

**K3 — что проверить:**
- каждый критерий приёмки покрыт тестами;
- для каждого случая выбран уровень и указано, кто пишет тест;
- есть негативные случаи, права доступа, повторы, сбои, выключенные флаги.

Согласование — `status: approved` в `test-plan.md`.

## 4. Разработка — backend и frontend

Задачи берутся из `tasks.md` по порядку и с учётом зависимостей: сначала задачи, от которых зависят другие, обычно backend.

```
/backend-developer выполни задачу T1 фичи NNN-slug
/frontend-developer выполни задачу T4 фичи NNN-slug
```

Один запуск — одна задача. После каждой задачи разработчик показывает коммиты на согласование.

**Что проверить по каждой задаче:**
- сделано то, что описано в задаче, и ничего сверх неё;
- проверки из отчёта проходят;
- тесты нужных уровней написаны;
- задача отмечена `[x]` в `tasks.md`.

Если разработчик остановился с вопросом, ответ — в зоне той роли, чей документ неполон: требования — аналитик, дизайн, задачи и контракты — архитектор. Изменение согласованного документа — по разделу «Изменения после согласования» в `ai/rules/sdd.md`.

**K4** — все задачи в `tasks.md` отмечены `[x]`.

## 5. Проверка — тестировщик

```
/qa проверь фичу NNN-slug
```

Тестировщик пишет автотесты API и e2e, запускает все тесты фичи, заводит дефекты и заполняет итог приёмки в `test-plan.md`.

Если есть дефекты — процесс `ai/workflows/bugfix.md`, раздел «Дефект в фиче, которая ещё не принята». После исправлений — повторная проверка:

```
/qa перепроверь дефекты фичи NNN-slug
```

**K5 — решение человека:**
- открытых блокирующих и значимых дефектов нет;
- все критерии приёмки выполнены;
- рекомендация тестировщика — «принять».

## 6. Завершение

```
git push -u origin feature/NNN-slug
```

Дальше — pull request в `develop` по правилам команды.
