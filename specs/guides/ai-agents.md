# Команда ИИ-агентов

Как устроена команда ИИ-агентов, которая переписывает прототип в полноценную платформу и развивает её дальше. Разработка ведётся по spec driven development: сначала спецификация, потом код.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Как переписываем | В этом же репозитории. Прототип перенесён в `prototype/`, новая платформа строится в корне. Берём фичу и переписываем относящиеся к ней сервисы. Прототип остаётся рабочим эталоном, пока его не заменит новая платформа |
| Менеджер пакетов | pnpm, монорепо на pnpm workspaces — см. `specs/architecture/structure.md` |
| Документация | `docs/` остаётся как есть и описывает прототип. Вся новая документация ведётся в `specs/` |
| Управление процессом | Процессом управляет человек: сам запускает агентов по шагам workflow и проверяет результат на контрольных точках. Агента-оркестратора нет |
| Язык | Агенты, правила, шаблоны и спецификации пишутся на русском |
| Стандарт разработки | Обсуждается отдельно, затем раскладывается по `ai/rules/` |

## Роли

| Роль | Файл | Что делает |
|---|---|---|
| Аналитик | `ai/agents/analyst.md` | Требования: что и зачем |
| Архитектор | `ai/agents/architect.md` | Решения и дизайн: как устроено, на какие задачи режется |
| Frontend-разработчик | `ai/agents/frontend-developer.md` | Интерфейс по дизайну и задачам |
| Backend-разработчик | `ai/agents/backend-developer.md` | Сервисы, API, база по дизайну и задачам |
| Тестировщик | `ai/agents/qa.md` | План тестов, автотесты API и e2e, приёмка фичи по спецификации |

Кто какие тесты пишет:

| Роль | Тесты |
|---|---|
| Frontend-разработчик | модульные, визуальные, контрактные |
| Backend-разработчик | модульные, контрактные, интеграционные |
| Тестировщик | план тестов, автотесты API, e2e |

Инструменты — в `specs/architecture/tech-stack.md`, раздел «Тестирование».

## Статусы спецификаций

| Статус | Что значит | Кто ставит |
|---|---|---|
| `draft` | черновик, агент работает над документом | агент |
| `review` | агент закончил, документ на проверке у человека | агент |
| `approved` | документ согласован, следующая роль может начинать | человек |

Следующая роль начинает работу только по документам в статусе `approved`. ADR проходят статусы `proposed` → `accepted` / `rejected`, позже — `superseded`; `accepted` и `rejected` ставит человек.

## Независимость от LLM

Агенты одинаково работают в Claude Code, Codex, Kimi Code и Gemini CLI. Роли и правила пишутся один раз в `ai/` в нейтральном формате. Для каждого инструмента генерируется тонкий адаптер, который велит агенту прочитать файл роли и её правила. Если инструмент поменяет формат, правится только генератор.

Роль вызывается командой — подробно в `ai/adapters/README.md`:

| Инструмент | Как вызвать роль | Адаптер |
|---|---|---|
| Claude Code | `/analyst <задача>` | `.claude/commands/<id>.md` |
| Gemini CLI | `/analyst <задача>` | `.gemini/commands/<id>.toml` |
| Kimi Code | `/skill:analyst <задача>` | `.agents/skills/<id>/SKILL.md` |
| Codex | `$analyst <задача>` | `.agents/skills/<id>/SKILL.md` |

Codex не поддерживает свои слэш-команды в проекте, поэтому роль в нём вызывается как навык — через `$`.

Адаптеры генерируются командой `pnpm ai:adapters` и проверяются `pnpm ai:adapters:check`.

```
GEMINI.md                    # одна строка: @./AGENTS.md — для Gemini CLI
ai/
  README.md                  # как устроена команда агентов и как подключить инструмент
  agents/                    # КТО: роли
    analyst.md
    architect.md
    frontend-developer.md
    backend-developer.md
    qa.md
  rules/                     # КАК: стандарты разработки, общие для ролей
    common.md                # язык, стиль, коммиты, что запрещено всем
    sdd.md                   # жизненный цикл спеки, статусы, контрольные точки
    architecture.md          # слои, модули, границы, порты и адаптеры
    backend.md
    frontend.md
    api-contracts.md         # contract-first: сначала OpenAPI, потом код
    testing.md
    security.md
  workflows/                 # В КАКОМ ПОРЯДКЕ: процессы с передачей между ролями
    feature.md               # аналитик → архитектор → разработчики → тестировщик
    migrate-feature.md       # перенос фичи прототипа на новую платформу
    bugfix.md
  templates/                 # шаблоны артефактов
    requirements.md
    design.md
    tasks.md
    test-plan.md
    adr.md
  config/
    models.yaml              # роль → уровень модели → конкретная модель у каждого провайдера
  adapters/                  # генератор команд ролей под Claude Code, Codex, Kimi Code и Gemini CLI
specs/
  guides/                    # руководства по процессу (этот документ)
  product/                   # видение, глоссарий, роли пользователей (их ведёт аналитик)
  architecture/              # целевая архитектура и adr/ (их ведёт архитектор)
  features/NNN-slug/

    tasks.md                 # архитектор режет на задачи FE и BE
    test-plan.md             # тестировщик
```

## Принципы

1. **Агенты передают работу друг другу через файлы в `specs/`, а не через чат.** У каждой роли есть входы и выходы. Аналитик пишет `requirements.md`, архитектор читает его и пишет `design.md` и `tasks.md`, разработчики берут задачи из `tasks.md`, тестировщик проверяет по `requirements.md` и `test-plan.md`. Поэтому каждая роль может работать на своей модели.
2. **Роль и стандарт хранятся отдельно.** В файле агента описаны ответственность, порядок работы, критерии готовности и список правил, которые нужно прочитать. Сами стандарты живут в `ai/rules/`, и несколько ролей используют их совместно.
3. **В файле агента не указываем модель.** Агент получает уровень (`reasoning` / `standard` / `fast`), а `ai/config/models.yaml` сопоставляет уровень с моделью у каждого инструмента. В Claude Code модель записывается в команду роли автоматически; Codex, Kimi Code и Gemini CLI не умеют задавать модель в навыке или команде, для них это подсказка, какую модель выбрать.
4. **Инструменты описываем как права, а не как названия.** В файле агента указано, что можно читать, в какие пути писать и какие команды запускать. Адаптер переводит это в формат конкретного инструмента.
5. **У агентов единый формат:** YAML frontmatter и тело из фиксированных разделов.

```markdown
---
id: backend-developer
description: Реализует сервисы, API и миграции по design.md и tasks.md
tier: standard
rules: [common, sdd, architecture, backend, api-contracts, testing, security]
inputs: [specs/features/*/design.md, specs/features/*/tasks.md]
outputs: [код сервисов, миграции, тесты]
permissions:
  read: ["**"]
  write: [<пути backend>]
  run: [<команды тестов и линтеров>]
---

## Роль
## Зона ответственности
## Порядок работы
## Критерии готовности
## Что запрещено
```

## Перенос прототипа

Прототип переписывается по фичам, а не целиком:

1. Архитектор описывает целевую архитектуру в `specs/architecture/`, включая каталоги новой платформы в репозитории.
2. Для каждой фичи по `ai/workflows/migrate-feature.md`: аналитик описывает требования, опираясь на `docs/` и поведение прототипа, затем архитектор пишет дизайн и задачи, разработчики переписывают относящиеся к фиче сервисы, а тестировщик сверяет новое поведение со спецификацией и прототипом.
3. После переноса фичи источником правды для неё становится `specs/features/`.
