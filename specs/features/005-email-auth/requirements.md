# Регистрация и вход по email

## Цель

Посетитель подтверждает свой email и продолжает оформление кампании под собственной учётной записью. Первый и последующие входы проходят одинаково. Организация для входа не требуется. Границы ответственности определены в [ADR 0007](../../architecture/adr/0007-auth-and-partners-services.md).

## Пользователи

| Роль | Действие |
|---|---|
| Посетитель | Вводит адрес и код из письма при первом или повторном входе. |
| Авторизованный пользователь | Работает в своей сессии и может завершить её. |

## Требования

### R1. Подтверждение адреса

Как посетитель, я хочу получить код на свой email, чтобы подтвердить доступ к почте.

- **R1.1.** Дано новый или уже зарегистрированный адрес. Когда посетитель запрашивает код в пределах лимита, тогда платформа передаёт письмо для доставки сервису нотификаций. Сам запрос кода не создаёт профиль и не открывает сессию.
- **R1.2.** Дано код для одного адреса. Когда введён неверный, просроченный, уже использованный код или код предъявлен для другого адреса, тогда вход отклонён и новая учётная запись не появляется.
- **R1.3.** Дано с одним токеном посетителя за последние 2 часа уже поступило 15 запросов отправки письма. Когда с этим токеном запрашивают ещё одно письмо, в том числе на другой email, тогда запрос отклоняется, письмо не отправляется и посетитель получает сообщение об ограничении.
- **R1.4.** Дано адрес получил код и код ещё не использован. Когда с последней отправки прошло меньше минуты, повторная отправка отклоняется. Начиная с одной минуты и до истечения срока кода при доступном лимите отправляется тот же код. Срок отсчитывается от его выпуска.
- **R1.5.** Дано с выпуска кода прошло 10 минут. Когда посетитель предъявляет этот код, вход отклоняется. Следующий разрешённый запрос отправки выдаёт новый код со своим сроком действия.
- **R1.6.** Дано действующий код и четыре неверных ввода. Когда посетитель вводит верный код с пятой попытки, тогда проверка проходит. Если пятый ввод неверен, дальнейший ввод этого кода отклоняется, даже если значение верное и срок действия ещё не истёк. Повторная отправка того же кода сохраняет число использованных попыток.

### R2. Одна учётная запись при первом и повторном входе

Как посетитель, я хочу продолжить работу с прежними данными при следующем входе.

- **R2.1.** Дано адрес впервые успешно подтверждён. Когда регистрация завершается, тогда у пользователя один профиль и действующая сессия. Он может продолжить с лендинга без ИНН и членства.
- **R2.2.** Дано пользователь уже зарегистрирован. Когда он входит по новому действительному коду на свой адрес, тогда получает доступ к тому же профилю с прежним идентификатором и актуальным членством.
- **R2.3.** Дано параллельные первые входы по одному адресу либо потеря ответа после создания профиля. Когда подтверждённая регистрация завершается или продолжается после сбоя, тогда результат связан с одним профилем. До завершения регистрации защищённый доступ не выдаётся.
- **R2.4.** Дано адрес сохранён в нижнем регистре. Когда посетитель вводит этот адрес в другом регистре при запросе или подтверждении кода, тогда платформа распознаёт тот же адрес и после подтверждения открывает прежний профиль.

### R3. Доступ по сессии

Как авторизованный пользователь, я хочу работать без повторного ввода кода до завершения сессии.

- **R3.1.** Дано действующая сессия. Когда пользователь обращается к защищённой операции, тогда платформа определяет вошедшего пользователя и применяет права этой операции.
- **R3.2.** Дано пользователь вышел, срок сессии истёк или сессия отозвана. Когда со старой сессией повторяют защищённое действие, тогда оно не выполняется и требуется вход. Такой же результат получает посетитель без сессии.
- **R3.3.** Дано действительность сессии невозможно проверить из-за сбоя. Когда запрошено защищённое действие, тогда оно не выполняется, пользователь получает сообщение о временной недоступности.
- **R3.4.** Дано сессия активна и срок токена доступа (access token) истёк. Когда пользователь продолжает работу, тогда платформа получает новый токен доступа по действительному токену обновления (refresh token) без ввода кода и без перехода на страницу входа (silent refresh).
- **R3.5.** Дано с последней активности пользователя прошло 24 часа или больше. Когда поступает защищённый запрос или запрос тихого обновления, тогда сессия завершена и требуется повторный вход по email. Фоновое обновление токена само по себе не считается активностью пользователя.
- **R3.6.** Дано пользователь вышел или его сессия отозвана. Когда предъявляют токен обновления этой сессии, тогда получить новый токен доступа нельзя.

## Правила и ограничения

Входящие адреса для аутентификации приводятся к нижнему регистру перед сохранением и сравниваются без учёта регистра. На один токен посетителя допускается до 15 запросов отправки письма за 2 часа суммарно по всем адресам. Для каждого выпущенного кода допускается до 5 попыток ввода. Ввод кода расходует только попытку проверки.

Один подтверждённый способ входа принадлежит одному пользователю. Контактный email и адрес входа могут различаться. Изменение контактов сохраняет прежний способ входа. При будущем подключении другого способа потребуется действующая сессия и подтверждение владения этим способом. Совпадения email для объединения профилей недостаточно.

## Ошибки и крайние случаи

Если отправку письма выполнить не удалось, посетитель не получает доступ и может повторить запрос с учётом лимита (R1). Если ответ о регистрации потерян, при повторе сохраняется прежний профиль (R2). Проблемы с доставкой письма сами по себе не завершают уже открытые сессии.

## Нефункциональные требования

Адреса, коды и данные сессий исключаются из журналов. Количественные цели по нагрузке и времени доставки пока не заданы.

## Вне рамок

Доставка писем внутри сервиса нотификаций, реализация дополнительных способов входа и управление организацией. Регистрация организации описана в [фиче 006](../006-partners/requirements.md).

## Отличия от прототипа

Не применимо. Основание — согласованный сценарий платформы.
