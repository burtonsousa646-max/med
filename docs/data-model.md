# Модель данных

PostgreSQL 17. Схема — `migrations/`: `0001_integrations.sql` (общее для интеграций), `0002_core.sql` (ядро), `0003_catalog.sql` (начальные справочники из прототипа).

Общие правила:
- деньги — `bigint` в копейках, суффикс `_kop`;
- время — `timestamptz`;
- всё, что принадлежит партнёру, несёт `company_id`; запросы кабинета всегда фильтруют по нему;
- перечисления — `text` с `check`, а не типы `enum`: новое значение добавляется одной миграцией без пересоздания типа;
- гибкие части (условия оффера, таргетинг, ответы внешних систем) — `jsonb`; всё, по чему ищем и считаем, — отдельные колонки.

## identity

| Таблица | Что | Ключевое |
|---|---|---|
| `users` | человек со стороны партнёра | `email` — только подтверждённая кодом почта |
| `staff` | сотрудник билайна | `roles` ⊂ {moderator, manager, finance, admin}, обновляются при каждом входе через SSO |
| `identities` | способ входа | `(provider, subject)` — ID у провайдера; ссылается на `users` или `staff`, ровно на одно; контакты от провайдера — в `data` |
| `otp_codes` | коды входа | хранится хеш `sha256(почта + код)`, срок 10 минут, до 5 попыток |
| `sessions` | сессии | ключ — хеш токена из cookie; `company_id` — выбранная компания партнёра |

## partners

| Таблица | Что | Ключевое |
|---|---|---|
| `companies` | юрлицо партнёра | `inn` уникален; `kyc_status`: pending → verified / rejected / blocked; `agency_id` — субклиент агентства; `offer_version` и `offer_accepted_at` — принятая оферта |
| `memberships` | человек в компании | роль owner / staff / accountant / agency; `signer` — может принимать оферту и подтверждать оплату |
| `invitations` | приглашение в компанию | токен (хеш), срок, роль staff или accountant |
| `points` | точки продаж | координаты `lat`, `lon`, флаг «в рекламе» |
| `partner_consents` | согласия партнёра | вид, версия текста, когда дано и отозвано |

## catalog

| Таблица | Что | Ключевое |
|---|---|---|
| `placements` | места показа | `pricing` cpc / cpm; `base_ctr` — априорный CTR для скора и прогноза; `slots` — мест в одном показе; `min_bid_kop`; `needs_consent` — пуши |
| `offer_types` | типы офферов | click, coupon, lead, promo, sub; `share` — платит клиент, партнёру выплаты; `fee_pct` — доля билайна; `data` — тексты и поля условий для кабинета |
| `triggers` | сигналы и триггеры | `tier` T1–T4, `value` hot / week / wide / off (off — не продаётся), `ttl_days`, `max_advertisers`, `min_bid_kop`, `reach_hint` |
| `stop_words` | правила модерации | регулярное выражение, причина со ссылкой на закон, вариант исправления |
| `settings` | параметры бэкофиса | бонус первой кампании, наценка широкой карточки, сбор ОРД, минимальный бюджет, частота, правила клика |

Начальные значения перенесены из прототипа. Минимальные ставки по тирам — допущения из «Триггеров», раздел 4: T1 5 ₽, T2 10 ₽, T3 20 ₽, T4 35 ₽.

## campaigns

| Таблица | Что | Ключевое |
|---|---|---|
| `campaigns` | кампания | статусы ниже; `terms` — условия оффера; `targeting` — сигналы, радиус, точки; `placements`; `bid_kop` (null — автоставка); `budget_month_kop`, `daily_cap_kop`; `version` — оптимистичная блокировка |
| `creatives` | креатив | каждая правка — новая строка с `version + 1`; в показ идёт последняя `approved`; `erid` от ОРД уникален |
| `approvals` | отправка руководителю | токен (хеш) со сроком жизни, кто и когда подтвердил |
| `special_requests` | заявка на спецпроект | статус и менеджер |

Статусы кампании: `draft` → `approval` (ждёт руководителя) → `invoice` (ждёт оплату счёта) → `moderation` → `live` ⇄ `paused` → `finished` → `archived`; из `moderation` возможен `rejected`, после исправления — снова `moderation`. Правила переходов — в модуле campaigns (день 2).

## moderation

`moderation_tasks`: задача на креатив. `auto` — идёт автопроверка; `queued` — ждёт сотрудника; `approved` / `rejected` с причиной для партнёра. `auto_result` — какие стоп-слова сработали и что сказала модель.

## billing

Двойная запись. Три таблицы:

- `accounts` — счета. У партнёра: `partner_main` (деньги), `partner_bonus` (бонусы), `partner_payout` (накопленные выплаты). У платформы (`company_id` null): `beeline_revenue`, `gateway` (расчёты со шлюзом), `bank` (расчётный счёт), `bonus_fund`, `ord_fee`, `payout_clearing`, `adjustment`. Один счёт каждого вида на компанию.
- `transactions` — операция: topup, charge, bonus, payout, refund, adjustment, commission. `idempotency_key` уникален и обязателен.
- `entries` — проводки: счёт и сумма со знаком. **Сумма проводок одной операции — ноль**: триггер `entries_balanced` проверяет это в конце транзакции базы и отменяет её, если не сошлось.

Баланс счёта — представление `account_balances` (сумма проводок). Знак: плюс — деньги на счёте, минус — счёт отдал.

Примеры операций (суммы в рублях для краткости):

| Операция | Проводки |
|---|---|
| пополнение СБП 10 000 | `partner_main` +10 000, `gateway` −10 000 |
| бонус первой кампании 3 000 | `partner_bonus` +3 000, `bonus_fund` −3 000 |
| списание за 100 кликов по 12 | `partner_main` −1 200, `beeline_revenue` +1 200 |
| начисление партнёру за купоны 5 000, комиссия 20 % | `partner_payout` +4 000, `beeline_revenue` +1 000, `gateway` −5 000 |
| выплата 4 000 на р/с | `partner_payout` −4 000, `payout_clearing` +4 000 |

Порядок списания (основной или бонусный счёт первым), холды под кампанию и сбор ОРД — правила модуля billing, день 2.

| Таблица | Что |
|---|---|
| `payments` | платёж через шлюз или по счёту; деньги на баланс — только при `succeeded`, ссылкой на `transaction_id` |
| `invoices` | счёт-оферта: номер, сумма, оплачен ли |
| `payouts` | выплата за месяц: начислено, комиссия, к выплате; одна на компанию и месяц |

## documents

`documents`: оферта, счёт, акт, счёт-фактура, отчёт агента, договор. Статусы: draft → issued → sent → delivered → signed / rejected (по вебхукам ЭДО). Файл — ключ в хранилище.

## audiences

`segments`: гео, правила по сигналам, загруженная база хешей, сегмент DMP. `company_id` null — общий сегмент платформы.

## tracking

| Таблица | Что | Ключевое |
|---|---|---|
| `impressions` | показы | партиции по дням `impressions_YYYYMMDD`, плюс `impressions_default` для строк без партиции. Воркер раз в час создаёт партиции на 7 дней вперёд (`ensure_impression_partitions`). `med_id` — обезличенный ID, не номер |
| `clicks` | клики | `click_id` — непредсказуемый ID из ссылки; `billable` и `reason` (repeat24h, tooFast, fraud); `charge_tx_id` — какой операцией списан. Без партиций: кликов на два порядка меньше показов, а искать по `click_id` нужно по всей таблице |
| `conversions` | результаты | заявка, заказ, погашение, продление; статусы pending → approved / rejected → returned; `dispute_until`; `(company_id, order_id)` уникален — повтор постбэка не задваивает |
| `tracking_keys` | ключи сервера партнёра | хеш ключа, подсказка из последних символов, отзыв; несколько ключей для смены без простоя |

## reporting

`stats_hourly`: показы, охват, клики, оплачиваемые клики, конверсии, траты по кампании, часу и месту. Кабинет и бэкофис читают только свёртки, не сырые события.

## Общее для интеграций

`outbox`, `inbound_events`, `external_refs`, `integration_log` — в [integrations.md](integrations.md#2-три-способа-обмена). `audit_log` — кто что сделал: партнёр, сотрудник или система, с изменением в `diff`.

## Миграции

- Файл `NNNN_описание.sql`, применяется один раз, в своей транзакции; применённые — в `schema_migrations`.
- После выкладки на стенд файл не меняется: исправление — новой миграцией. До первой выкладки (сейчас) файлы можно править и пересоздавать базу.
