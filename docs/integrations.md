# Интеграции

Как платформа общается с внешними системами и как подключить систему билайна вместо заглушки. Код — `server/integrations/`.

## 1. Принцип

Ядро не знает конкретных систем. У каждой системы есть **порт** — интерфейс в терминах платформы (`ports.ts`): «зарегистрируй креатив и верни erid», а не «POST /v3/creatives в ОРД Х». За портом стоит **адаптер**:

- `stub` — заглушка (`stubs.ts`), сейчас стоит за всеми портами;
- `beeline` — адаптер системы билайна (`beeline/<порт>.ts`), появляется при подключении.

Какой адаптер работает, задаёт переменная окружения `INT_<ПОРТ>` (по умолчанию `stub`): `INT_ORD=beeline`, `INT_STAFF_SSO=beeline`. При старте api и worker проверяют, что для каждого заданного значения адаптер есть, иначе не запускаются (`checkPorts`). Текущее состояние — `GET /api/health` и `GET /api/admin/ports`.

Вызов из модуля:

```ts
import { port } from '../integrations/index.ts'
const company = await port('companyRegistry').findByInn(inn)
```

## 2. Три способа обмена

### 2.1 Синхронный вызов

Модулю нужен ответ сейчас: реестр юрлиц при входе, геокодер при добавлении точки, согласие абонента в момент показа. Модуль вызывает порт напрямую. Таймауты и ретраи — внутри адаптера; ошибка доходит до модуля, он решает, что показать человеку.

### 2.2 Исходящая очередь (outbox)

Изменение должно дойти до системы, но ответ не нужен немедленно: креатив — в ОРД, документ — в ЭДО, выплата — в учётную систему. Модуль в своей транзакции кладёт задачу:

```ts
await sql.begin(async tx => {
  const [cr] = await tx`insert into creatives ... returning id`
  await enqueue(tx, 'ord', 'registerCreative', { creativeId: cr.id }, `ord:creative:${cr.id}`)
})
```

и регистрирует исполнителя, который вызовет порт и сохранит результат:

```ts
handle('ord', 'registerCreative', async ({ creativeId }) => {
  const { erid } = await port('ord').registerCreative({ ... })
  await sql`update creatives set erid = ${erid} where id = ${creativeId}`
})
```

Свойства:
- задача и изменение сохраняются вместе или не сохраняются;
- ключ идемпотентности: повторная постановка той же задачи ничего не создаёт;
- воркер берёт задачу в аренду на 5 минут: упавший воркер не теряет задачу, а два воркера не берут одну;
- ошибка — повтор через 10 с, 40 с, 2,5 мин, 10 мин, 40 мин, затем раз в час; после 8 попыток `failed`;
- исполнитель должен быть идемпотентным: задачу могут выполнить дважды (воркер упал после вызова, до отметки). Поэтому в порт передаётся `idempotencyKey` или наш ID, по которому система узнает повтор.

### 2.3 Входящие вебхуки

Система сообщает о событии: оплата прошла, документ подписан, купон погашен. Адрес — `POST /api/hooks/<порт>/<событие>`.

| Заголовок | Значение |
|---|---|
| `X-Event-Id` | уникальный ID события у отправителя |
| `X-Signature` | `sha256=` + HMAC-SHA256 сырого тела в hex, ключ — секрет системы |

Секрет — переменная `HOOK_SECRET_<ПОРТ>` (`HOOK_SECRET_PAYMENTS`). Вне production без переменной используется `dev-secret-<порт>`; в production без переменной вебхук отклоняется.

Отметка о событии (`inbound_events`) и его обработка идут в одной транзакции. Повтор того же `X-Event-Id` возвращает `{ ok: true, duplicate: true }` и не обрабатывается. Ошибка обработчика — ответ 500, отметки нет, событие нужно прислать снова.

Обработчик в модуле:

```ts
onHook('payments', 'payment.succeeded', async (body, tx) => {
  // писать только через tx — в той же транзакции, что и отметка о событии
})
```

### 2.4 Связка ID и журнал

- `external_refs (entity, entity_id, system, external_id)` — наша сущность ↔ её ID во внешней системе: компания ↔ клиент CRM билайна, платёж ↔ транзакция шлюза. Одна пара на систему, внешний ID уникален внутри системы.
- `integration_log` — каждый асинхронный вызов порта и каждый входящий вебхук: система, действие, успех, время, запрос и ответ. Поля с секретами и контактами (`token`, `secret`, `password`, `code`, `phone`, `email`, `to`, `body`) заменяются на `***`. Порты горячего пути показа (`dmp`, `consents`, `cleanRoom`, `adtech`, `observability`) пишут в журнал только ошибки.

## 3. Как подключить систему билайна

1. Получить от команды системы: документацию API, тестовый контур, учётные данные, секрет вебхуков, адреса для белых списков.
2. Создать `server/integrations/beeline/<порт>.ts`, реализующий интерфейс порта из `ports.ts`. Перевод в термины системы — только внутри адаптера. Если системе нужно что-то, чего в порте нет, — сначала обсудить изменение порта: оно касается ядра.
3. Добавить адаптер в `adapters.beeline` в `server/integrations/index.ts`.
4. Секреты — в переменные окружения (`<ПОРТ>_URL`, `<ПОРТ>_TOKEN` и так далее), не в код и не в базу.
5. Если система шлёт события — зарегистрировать обработчики `onHook` и задать `HOOK_SECRET_<ПОРТ>`.
6. Тест адаптера на тестовом контуре системы: те же сценарии, что проходят на заглушке.
7. Включить на стенде `INT_<ПОРТ>=beeline`, проверить журнал интеграций в бэкофисе, затем в бою.

Откатиться на заглушку — вернуть `INT_<ПОРТ>=stub`.

## 4. Реестр портов

Волна — очередь подключения: **1** — нужна для запуска с реальными деньгами, **2** — для роста охвата, **3** — для масштаба. «Особые значения» — как заставить заглушку вернуть ошибку или отказ в тестах.

### 4.1 Вход и компания

| Порт | Системы | Методы | Обмен | Волна |
|---|---|---|---|---|
| `idp` | ЕСИА, СберБизнес ID, Альфа ID для бизнеса, Яндекс ID (под вопросом), ЛК B2B билайна | `authUrl(provider, state, redirectUri)` — адрес страницы провайдера; `exchange(provider, code, redirectUri)` — человек и, если провайдер подтвердил полномочия, компания | синхронно, OAuth / OIDC | 1 |
| `staffSso` | SSO сотрудников билайна (AD, Keycloak) | `authUrl`, `exchange` → почта, имя, роли | синхронно, OIDC | 1 |
| `companyRegistry` | DaData, Контур.Фокус, ЕГРЮЛ | `findByInn(inn)` → реквизиты, адрес, руководитель, статус, риск | синхронно | 1 |
| `b2bCrm` | CRM корпоративных клиентов билайна | `findClient(inn)` → клиент и менеджер; `createLead(inn, topic, details)` | синхронно | 2 |
| `geo` | Яндекс Карты, гео-сервис билайна | `geocode(addr)` → координаты; `reach(lat, lon, radiusM)` → сколько людей | синхронно | 1 |

Особые значения заглушек: `idp` — страница `/api/stub/idp` с формой «ИНН, ФИО, почта»; `staffSso` — `/api/stub/sso` с формой «почта, имя, роли»; `companyRegistry` — ИНН, оканчивающийся на `0000`, ликвидирован, не 10 и не 12 цифр — не найден; `b2bCrm` — примерно треть ИНН «уже клиенты» (по хешу ИНН); `geo.reach` — 9 тыс. человек на км².

Важно для адаптера `idp`: возвращать `company` только если провайдер подтвердил, что человек — руководитель или представитель этой организации. Платформа делает такого человека владельцем и подписантом компании.

### 4.2 Деньги и документы

| Порт | Системы | Методы | Обмен | Волна |
|---|---|---|---|---|
| `payments` | эквайринг билайна: СБП, карты | `create(paymentId, method, amountKop, description, returnUrl)` → внешний ID и адрес оплаты; `refund(...)` | синхронно + вебхуки `payment.succeeded`, `payment.failed` | 1 |
| `bankStatement` | выписка расчётного счёта билайна | `incoming(since)` → поступления: сумма, ИНН плательщика, назначение | опрос воркером + вебхук `incoming` | 1 |
| `subscriberBilling` | биллинг абонентов билайна | `charge(medId, amountKop, purpose)` — оплата со счёта телефона; `grantBonus(medId, kind, amount)` — гигабайты, минуты, баллы | синхронно + вебхуки продления и отмены подписки | 2 |
| `accounting` | SAP / 1С билайна | `syncCounterparty`, `postRevenue`, `requestPayout` | outbox | 1 |
| `edo` | Диадок, СБИС, оператор ЭДО билайна | `invite(inn, kpp, operator)`; `send(documentId, inn, kind, fileKey)` | outbox + вебхук `document.status` | 1 |
| `signature` | ПЭП по SMS, КЭП | `request(phone, text)` → ID запроса; `verify(requestId, code)` | синхронно | 1 |
| `ord` | ОРД (выбор билайна) → ЕРИР | `registerOrganization`, `registerContract`, `registerCreative` → erid, `reportStats(period, rows)` | outbox | 1 |

Особые значения: `payments` — адрес оплаты ведёт на страницу заглушки `/api/stub/pay/<id>` (день 2); `subscriberBilling.charge` — MED-ID на `broke` получает отказ; `signature.verify` — верный код `0000`; `ord.registerCreative` — erid из 11 символов base58, одинаковый для одного креатива.

### 4.3 Данные и аудитории

| Порт | Системы | Методы | Обмен | Волна |
|---|---|---|---|---|
| `dmp` | Big Data / DMP билайна, MED-ID | `match(medId, triggerIds)` → уверенность по каждому сигналу; `estimate(triggerIds, гео)` → охват | синхронно, горячий путь | 2 |
| `cleanRoom` | X5, Альфа-Банк, страховщики через контур билайна | `signals(medId)` → сигналы партнёров с TTL, основанием согласия и исключениями конкурентов | синхронно, горячий путь | 3 |
| `consents` | реестр согласий абонентов | `check(medId, purpose)` — реклама (ст. 18 ФЗ «О рекламе»), пуши, профиль | синхронно, горячий путь | 1 |

Особые значения: `dmp.match` — каждый сигнал срабатывает примерно у четверти MED-ID (по хешу); `consents.check` — MED-ID на `optout` без согласия. Запись сигнала партнёра — как в «Триггерах и едином профиле», раздел 3.1.

### 4.4 Поверхности и каналы

| Порт | Системы | Методы | Обмен | Волна |
|---|---|---|---|---|
| поверхности | приложение «Мой билайн», beeline.ru, Магазин билайна, ЛК B2B, Билайн ТВ | не порт: они вызывают `/api/public` — запрос рекламы, маяк показа, клик (день 3) и JS-сниппет | они → мы | 1 |
| `cvm` | CVM-платформа билайна: пуши, входящие, SMS | `deliver(medId, channel, campaignId, text, url)` | outbox | 2 |
| `adtech` | Билайн Adtech | `fraudScore(clickId, medId, ip, userAgent, placement)` → 0..1; дальше — OpenRTB и выбор рекламы | синхронно | 2 |
| `messaging` | SMS-шлюз билайна, почта, Telegram | `send(channel, to, template, params)` | синхронно или outbox | 1 |

Особые значения: `adtech` — user agent с `bot`, `curl`, `python` получает 0,95; `messaging` — не отправляет, пишет в консоль (вне тестов) и в `stubState.messages`.

Про Adtech. МЁД строится поверх Билайн Adtech, а не третьей рекламной системой. В автономном режиме рекламу выбирает свой движок (модуль serving, день 3). Если договоримся, что выбор делает Adtech, в порт добавится `decide(...)`, а кабинет и поверхности этого не заметят.

### 4.5 Партнёры

| Порт | Системы | Методы | Обмен | Волна |
|---|---|---|---|---|

| результаты партнёра | сервер, CRM, 1С партнёра | не порт: постбэк и загрузка CSV через `/api/public` и кабинет (день 3) | они → мы | 1 |
| кассы | кассы партнёров | не порт: вебхук `pos/coupon.redeemed` | они → мы | 2 |

### 4.6 Инфраструктура

| Порт | Системы | Методы | Обмен | Волна |
|---|---|---|---|---|
| `llm` | Claude, ИИ билайна | `moderate(text, imageUrl, offerType)` → вердикт, уверенность, причины | синхронно | 1 |
| `storage` | S3 облака билайна, CDN | `put`, `get`, `url` | синхронно | 1 |
| `bi` | DataLens, хранилище билайна | `export(dataset, period, rows)` | outbox | 3 |
| `support` | Service desk билайна | `createTicket(companyId, topic, text, contact)` | outbox | 2 |
| `observability` | мониторинг билайна | `metric(name, value, tags)` | синхронно, без ожидания | 2 |

Особые значения: `llm` — всегда `ok` с уверенностью 0,5, модерация держится на правилах (стоп-слова); `storage` — файлы на диске в `var/storage` (`STORAGE_DIR`), отдаются по `/api/files/<key>` (день 2).

## 5. Что спросить у команд билайна

| Тема | Вопрос | Для порта |
|---|---|---|
| маркировка | какой ОРД, есть ли договор и тестовый контур | `ord` |
| оплата | какой эквайринг принимает деньги юрлиц, есть ли СБП для бизнеса | `payments` |
| документы | какой оператор ЭДО, кто подписывает со стороны билайна | `edo` |
| сотрудники | как сотрудники входят во внутренние системы, где хранятся роли | `staffSso` |
| данные | есть ли API у DMP, в каком виде MED-ID, кто владелец | `dmp`, `consents` |
| поверхности | как «Мой билайн» сейчас получает баннеры: свой сервис или Adtech | поверхности, `adtech` |
| каналы | кто владеет CVM, как ограничена частота по всем каналам | `cvm` |
| учёт | куда передавать выручку и заявки на выплаты партнёрам | `accounting` |
| размещение | облако билайна, требования ИБ к контуру с персональными данными | все |
