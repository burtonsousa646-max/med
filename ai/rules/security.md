# Безопасность

Обязательные правила безопасности. Правило для всех ролей, которые проектируют, пишут и проверяют код. Нарушение этих правил — блокирующий дефект, даже если требования о нём не говорят.

## Доступ

- **Аутентификация** — только в API Gateway. Сервисы доверяют данным о пользователе и компании только от gateway.
- **Сессия** — в cookie с флагами `HttpOnly`, `Secure`, `SameSite`. Токены и данные сессии не хранятся в `localStorage`, `sessionStorage` и коде страницы.
- **Права проверяются на сервере.** Скрытая кнопка на frontend — не защита: каждая операция проверяет права в gateway или сервисе.
- **Изоляция компаний.** Компания берётся только из сессии. Параметр `companyId` от клиента для операций кабинета — ошибка проектирования. Каждый запрос к данным компании фильтруется по компании из сессии.
- **Чужой ресурс** — ответ 404, а не 403: не подтверждаем, что ресурс существует.
- **Действия сотрудников** бэкофиса проверяются по ролям сотрудника; доступ к данным партнёров — только в объёме роли.

## Входные данные

- Всё, что пришло извне — запрос, файл, вебхук, сообщение из очереди, — недоверенное.
- Запросы валидируются в gateway по OpenAPI; бизнес-правила и инварианты — в домене сервиса.
- SQL — только через Prisma и `$queryRaw` с шаблонной строкой. Сборка SQL из строк с данными запрещена, `$queryRawUnsafe` и `$executeRawUnsafe` запрещены.
- Загружаемые файлы: проверка типа по содержимому, ограничение размера, хранение вне каталога, откуда отдаётся статика, имя файла на сервере генерируется.
- Вебхуки внешних систем проверяются по подписи или секрету до обработки.
- Адреса для перенаправления после входа — только из разрешённого списка.

## Frontend

- HTML из данных не вставляется: `dangerouslySetInnerHTML` запрещён без санитайзера и решения в `design.md`.
- Внешние ссылки из пользовательских данных — с `rel="noopener noreferrer"` и проверкой схемы (`http`, `https`).
- Секреты и ключи во frontend-коде запрещены: всё, что попало в сборку, видно пользователю.
- Ответы сервера с ошибками показываются по полю `message`, без технических деталей.

## Секреты

- Секреты — только в переменных окружения. В коде, конфигах репозитория, тестах и логах их нет.
- `.env` не коммитится; в репозитории — только `.env.example` без настоящих значений.
- Секрет, попавший в репозиторий, считается скомпрометированным: его меняют, а не только удаляют из истории.

## Персональные данные

- Платформа обрабатывает персональные данные и подчиняется 152-ФЗ: данные хранятся и обрабатываются на территории России, внешние SaaS для них не используются.
- Собирается и хранится только то, что нужно для фичи; что именно — описано в `requirements.md` и `design.md`.
- Персональные данные не пишутся в логи, трассировки, метрики, данные задач очереди сверх необходимого и тексты ошибок.
- В логах вместо персональных данных — идентификаторы.
- В тестах и на стендах — только синтетические данные.

## Логи

Никогда не логируются: пароли, коды из SMS, токены, cookie сессии, ключи API, секреты, полные тела запросов и ответов, номера телефонов, адреса почты, паспортные и платёжные данные.

## Деньги и необратимые действия

- Операции с деньгами — только на сервере, в одной транзакции, с ключом идемпотентности.
- Суммы — целые копейки; дробные числа запрещены.
- Каждая операция с деньгами и каждое действие сотрудника бэкофиса записываются в аудит в базе сервиса: кто, что, когда, над чем.

## Ошибки

- Клиенту не возвращаются стеки, тексты исключений, SQL и внутренние адреса — только `code` и `message`.
- Подробности ошибки — в логах сервера, без запрещённых данных.

## Ограничения

- Gateway ограничивает частоту запросов для входа, отправки кодов и других операций, которые можно перебирать.
- Списки и выгрузки ограничены по размеру.
- У каждого внешнего вызова есть таймаут.

## Зависимости

- Новые зависимости — только из стека или через ADR.
- Install-скрипты зависимостей разрешаются явно в `allowBuilds` в `pnpm-workspace.yaml` после проверки пакета.
- Уязвимости зависимостей проверяются командой `pnpm audit`; критические исправляются до выкладки.

## Проверка

Архитектор описывает безопасность в разделе «Безопасность» `design.md`. Разработчик проверяет свою задачу по этому правилу. Тестировщик включает в план тестов права доступа, изоляцию компаний и некорректные входные данные.
