# Backend

Как писать код сервисов и API Gateway. Правило для backend-разработчика и архитектора. Принципы архитектуры — `ai/rules/architecture.md`, контракты — `ai/rules/api-contracts.md`, тесты — `ai/rules/testing.md`, безопасность — `ai/rules/security.md`.

## Стек

NestJS, TypeScript, PostgreSQL через Prisma, очереди BullMQ на Redis, gRPC между сервисами. Подробно — `specs/architecture/tech-stack.md`. Зависимости, которых нет в стеке, добавляются только через ADR.

## Структура сервиса

```
src/
  domain/
    <aggregate>/
      <aggregate>.entity.ts       сущность и её инварианты
      <value>.value.ts            объекты-значения
      <aggregate>.errors.ts       доменные ошибки
      <aggregate>.events.ts       доменные события
  application/
    <use-case>/
      <use-case>.use-case.ts      сценарий
      <use-case>.spec.ts
    feature-flags.ts              реестр флагов сервиса — если сервис проверяет флаги
    ports/
      <name>.repository.ts        интерфейсы репозиториев
      <name>.gateway.ts           интерфейсы внешних систем и других сервисов
      feature-flags.port.ts       порт флагов
  infrastructure/
    prisma/                       PrismaService, репозитории, маппинг модели ↔ домен
    grpc/                         клиенты других сервисов
    queue/                        продюсеры BullMQ
    <external>/                   адаптеры внешних систем
    feature-flags/                реализация порта флагов через @platform/feature-flags
  presentation/
    grpc/                         контроллеры gRPC, маппинг ошибок
    queue/                        обработчики задач BullMQ
  <service>.module.ts             сборка модуля NestJS: порты → реализации
  main.ts
```

- Один файл — одна сущность, сценарий или адаптер.
- Имена файлов — kebab-case с суффиксом роли: `.entity.ts`, `.use-case.ts`, `.repository.ts`, `.controller.ts`.
- Классы — PascalCase, функции и переменные — camelCase.

## Домен

- Сущности и объекты-значения — обычные классы TypeScript без декораторов и зависимостей от фреймворков.
- Инварианты проверяются в домене: сущность нельзя создать или перевести в недопустимое состояние.
- Изменение состояния — методами сущности с понятными именами (`submit()`, `pause()`), а не присваиванием полей снаружи.
- Нарушение правила — доменная ошибка, класс-наследник общей доменной ошибки с машинным кодом.
- Деньги — `bigint` копеек, имена с суффиксом `Kop`: `balanceKop`. Дробные числа для денег запрещены.
- Время — в UTC; текущее время сценарий получает через порт часов, а не через `new Date()` в домене.
- Идентификаторы — UUID v7, создаются в домене или сценарии, а не базой.

## Сценарии

- Один сценарий — одно действие пользователя или системы: `SubmitCampaignUseCase`.
- Сценарий получает зависимости только через порты в конструкторе.
- Сценарий отвечает за транзакцию: всё, что должно измениться вместе, меняется в одной транзакции через порт единицы работы.
- Сценарий возвращает доменные типы или простой DTO, но не модели Prisma и не сообщения gRPC.

## Порты и DI

- Порт — интерфейс в `application/ports/` и токен для DI рядом с ним.
- Реализация порта — в `infrastructure/`, связывается с токеном в `<service>.module.ts`.
- Импорты классов, которые NestJS внедряет по типу, — обычные, не `import type`: иначе пропадут метаданные для DI. Линтер в `server/` это учитывает.

## Данные и Prisma

- Схема — `prisma/schema.prisma` своего сервиса. Клиент Prisma генерируется в сервис и используется только в `infrastructure/prisma/`.
- Модели Prisma преобразуются в доменные сущности в репозитории; наружу из репозитория выходят только доменные типы.
- Таблицы и столбцы в базе — snake_case через `@@map` и `@map`; модели и поля в Prisma — PascalCase и camelCase.
- Время — `DateTime` с `@db.Timestamptz`, деньги — `BigInt`.
- Сырые запросы — только `$queryRaw` и `$executeRaw` с шаблонной строкой. `$queryRawUnsafe` и `$executeRawUnsafe` запрещены.
- Каждый запрос списка ограничен по количеству и использует индекс; новые запросы по большим таблицам сопровождаются индексом в той же миграции.

### Миграции

- Миграция создаётся командой `pnpm --filter @platform/<service> exec prisma migrate dev --name <что меняется>`.
- Применённая миграция не меняется никогда. Ошибка исправляется новой миграцией.
- Ломающее изменение схемы проводится в несколько шагов: добавить новое → перенести данные и код → удалить старое отдельной миграцией после выкладки.
- Миграция, которая может потерять данные, — только с явным решением в `design.md`.
- Миграция должна применяться на чистой базе и поверх всех предыдущих.

## gRPC

- Контроллеры реализуют интерфейсы, сгенерированные из `.proto` в `@platform/contracts`.
- Контроллер только преобразует сообщение в вход сценария, вызывает сценарий и преобразует результат и ошибки. Логики в контроллере нет.
- Доменные ошибки преобразуются в коды gRPC в одном месте — фильтре исключений сервиса:

| Доменная ситуация | Код gRPC |
|---|---|
| нарушено бизнес-правило | `FAILED_PRECONDITION` |
| объект не найден | `NOT_FOUND` |
| нет прав | `PERMISSION_DENIED` |
| неверные данные | `INVALID_ARGUMENT` |
| конфликт, повтор с другими данными | `ALREADY_EXISTS` или `ABORTED` |
| внешняя система недоступна | `UNAVAILABLE` |

- Вызов другого сервиса — только через порт и gRPC-клиент в `infrastructure/grpc/`, с таймаутом.

## API Gateway

- Маршруты реализуют операции из `api/openapi/`; входящие запросы валидируются по OpenAPI.
- Gateway проверяет сессию и права, берёт компанию и пользователя из сессии и передаёт их в сервисы.
- Ошибки gRPC преобразуются в HTTP-статусы и тело `{ code, message }` по `ai/rules/api-contracts.md`.
- Бизнес-логики, хранения бизнес-данных и прямого доступа к базам сервисов в gateway нет.

## Очереди

- Задачи BullMQ — через порт в `application`, продюсер — в `infrastructure/queue/`, обработчик — в `presentation/queue/`.
- Обработчик идемпотентен: повторная обработка той же задачи не меняет результат.
- У задачи есть ограниченное число повторов с нарастающей задержкой; задача, исчерпавшая повторы, не теряется и видна для разбора.
- Данные задачи — только идентификаторы и то, что нужно для обработки; без персональных данных сверх необходимого.
- Контракты событий между сервисами отложены до первых сервисов с очередями.

## Feature toggles

Общие правила — `ai/rules/architecture.md`, раздел «Feature toggles», пример кода — `specs/architecture/structure.md`, раздел «`@platform/feature-flags` — backend».

- **Код размечается только флагами из `design.md` и задачи.** Если задача требует флага, которого нет в дизайне, или флаг из задачи не описан в `design.md`, разработчик останавливается и спрашивает.
- **Реестр.** Флаг заводится в `application/feature-flags.ts` сервиса или в `src/feature-flags/` gateway, с JSDoc `@spec`, `@task`, `@remove`.
- **Порт и адаптер.** Сценарий получает флаги через порт `application/ports/feature-flags.port.ts`, реализация лежит в `infrastructure/feature-flags/`. `FeatureFlagsModule.forRoot({ appName })` подключается в `<service>.module.ts`.
- **Одна точка ветвления.** Флаг проверяется в сценарии: ветки «новое» и «старое» начинаются в одном месте. Домен о флагах не знает: если поведение домена меняется, сценарий выбирает нужный метод или объект.
- **Контекст** — пользователь и компания, которые gateway передал в gRPC metadata. Другие данные в контекст не кладутся.
- **Gateway** отдаёт `GET /v1/feature-flags`: имена флагов берутся из схемы `FeatureFlags` OpenAPI приложения, каждый флаг вычисляется с контекстом сессии. Отдельный список флагов frontend в коде не ведётся.
- **Старое поведение** не меняется и не удаляется, пока флаг не удалён отдельной задачей.

## Внешние системы

- Каждая внешняя система — порт в `application/ports/` и адаптер в `infrastructure/<external>/`.
- У каждого адаптера есть заглушка для локального окружения и тестов; выбор реализации — по конфигурации.
- Вызов внешней системы — с таймаутом; повтор — только для идемпотентных операций.

## Ошибки и логи

- Ошибки не глотаются: каждая либо обрабатывается осмысленно, либо пробрасывается.
- Тексты ошибок для людей — на русском; машинные коды — английские в lower_snake_case.
- Логи — только через `@platform/logger`. Уровни и запрещённые данные — `ai/rules/security.md` и раздел наблюдаемости в `specs/architecture/tech-stack.md`.

## Команды

| Команда | Что делает |
|---|---|
| `pnpm env:up` | поднять PostgreSQL, Redis и Unleash |
| `pnpm --filter @platform/<service> exec prisma migrate dev --name <name>` | создать и применить миграцию |
| `pnpm --filter @platform/<service> typecheck` | проверка типов |
| `pnpm --filter @platform/<service> test` | модульные тесты |
| `pnpm --filter @platform/<service> test:integration` | интеграционные тесты; нужен `pnpm env:up` |
| `pnpm --filter @platform/<service> build` | сборка |
| `pnpm --filter @platform/api test:contract` | контрактные тесты |
| `pnpm lint` | линтер по всему репозиторию |
