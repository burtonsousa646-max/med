# Frontend

Как писать код микрофронтендов и общих пакетов. Правило для frontend-разработчика и архитектора. Принципы архитектуры — `ai/rules/architecture.md`, контракты — `ai/rules/api-contracts.md`, тесты — `ai/rules/testing.md`, безопасность — `ai/rules/security.md`.

## Стек

React, TypeScript, Vite, TanStack Router, TanStack Query, TanStack Store, Vanilla Extract, Module Federation. Подробно — `specs/architecture/tech-stack.md`. Зависимости, которых нет в стеке, добавляются только через ADR.

## Структура приложения

```
src/
  routes/                     маршруты TanStack Router — файловый роутинг
  modules/
    <module>/                 функциональный модуль: одна бизнес-область приложения
      components/             компоненты модуля
      hooks/                  хуки модуля
      api/                    запросы и мутации TanStack Query
      store/                  клиентское состояние модуля
      model/                  типы и чистые функции модуля
      index.ts                публичный API модуля
  components/                 компоненты, общие для приложения
  store/                      клиентское состояние приложения
  main.tsx                    точка монтирования
```

- Модуль импортирует другой модуль только через его `index.ts`, а не из внутренних файлов.
- Маршрут в `routes/` собирает экран из модулей и не содержит логики сверх загрузки данных и параметров.
- Общее для нескольких приложений — в пакетах `web/packages/`, а не копированием.
- Микрофронтенды не импортируют код друг друга.

## Имена

- Компоненты — PascalCase, файл совпадает с именем: `CampaignCard.tsx`.
- Хуки — `useXxx`, файл `useXxx.ts`.
- Стили — рядом с компонентом: `CampaignCard.css.ts`.
- Тесты — рядом с кодом: `CampaignCard.test.tsx`; визуальные — `CampaignCard.visual.ts`.
- Экспорт — именованный. Экспорт по умолчанию — только там, где его требует инструмент.

## Компоненты

- Функциональные компоненты, пропсы описаны типом `<Name>Props`.
- Компонент делает одно дело. Компонент длиннее ~150 строк — повод разделить.
- Логика, не связанная с отображением, — в хуках и чистых функциях `model/`, а не в теле компонента.
- Списки — с устойчивым `key` из данных, не из индекса.
- Используются компоненты дизайн-системы `@platform/design-system`; свой базовый компонент (кнопка, поле, модальное окно) в приложении не создаётся.

## Данные с сервера

Запросы к API — через TanStack Query, а HTTP внутри него выполняет клиент openapi-fetch из `@platform/api-client`, типизированный по OpenAPI.

| Слой | Что делает | Где |
|---|---|---|
| openapi-typescript | типы из `api/openapi/*.yaml` | `web/packages/api-client/src/generated/` — генерируется, руками не правится |
| openapi-fetch | выполняет запрос, проверяет путь, параметры и ответ по типам | только внутри `queryFn` и `mutationFn` |
| TanStack Query | кеш, загрузка, ошибки, повторы, отмена, инвалидация | `modules/<module>/api/` |
| TanStack Router | загрузка данных до показа экрана | `loader` маршрута в `routes/` |
| компонент | показывает данные и вызывает мутации | `modules/<module>/components/` |

- Клиент `api`, функция `unwrap` и класс ошибки `ApiRequestError` — только из `@platform/api-client`. `fetch` напрямую и самодельные клиенты запрещены.
- `api.GET`, `api.POST` и другие методы клиента вызываются только внутри `queryFn` и `mutationFn`. Компоненты и маршруты работают только с TanStack Query.
- Результат запроса проходит через `unwrap`: ошибка из контракта `{ code, message }` становится исключением `ApiRequestError`, и TanStack Query переводит запрос в состояние ошибки.
- В `queryFn` передаётся `signal` из контекста, чтобы ненужный запрос отменялся.
- Серверное состояние — только в TanStack Query. В TanStack Store серверные данные не копируются.
- Запросы модуля — фабрики `queryOptions` в `modules/<module>/api/<module>Queries.ts`: `campaignQuery(id)`, `campaignsQuery(filter)`. Одна фабрика используется и в `loader` маршрута, и в компоненте.
- Мутации — хуки `useXxxMutation` в `modules/<module>/api/`.
- Ключи запросов — из фабрики ключей модуля `modules/<module>/api/keys.ts`, а не строками по месту.
- После мутации в `onSuccess` инвалидируются запросы, которые она меняет.

```ts
// modules/campaigns/api/campaignQueries.ts
export const campaignQuery = (campaignId: string) =>
  queryOptions({
    queryKey: campaignKeys.detail(campaignId),
    queryFn: async ({ signal }) =>
      unwrap(await api.GET('/v1/campaigns/{campaignId}', { params: { path: { campaignId } }, signal })),
  })

// routes/campaigns/$campaignId.tsx
loader: ({ context, params }) => context.queryClient.ensureQueryData(campaignQuery(params.campaignId))

// modules/campaigns/components/CampaignScreen.tsx
const { data: campaign } = useSuspenseQuery(campaignQuery(campaignId))
```

- Деньги приходят строкой копеек: в рубли переводятся только для показа функциями из общего пакета, вычисления над деньгами на клиенте не делаются.
- Операции с `Idempotency-Key` получают ключ, созданный один раз на действие пользователя, а не на каждую попытку.

## Состояние

| Что | Где |
|---|---|
| данные с сервера | TanStack Query |
| параметры экрана: фильтры, вкладка, страница | параметры маршрута TanStack Router |
| состояние формы и компонента | `useState` в компоненте |
| клиентское состояние модуля или приложения | TanStack Store в `store/` |

- Глобальное состояние — исключение: сначала маршрут, затем локальное состояние, и только потом стор.
- Подписка на стор — через селектор, возвращающий только нужное компоненту.

## Маршруты

- Файловый роутинг TanStack Router в `src/routes/`.
- Параметры пути и поиска типизированы и валидируются в определении маршрута.
- Данные, без которых экран не имеет смысла, загружаются в `loader` маршрута через TanStack Query.
- У каждого маршрута есть состояние загрузки и ошибки.

## Стили

- Только Vanilla Extract: файлы `*.css.ts` рядом с компонентом.
- Цвета, отступы, шрифты, радиусы, тени — только из токенов `@platform/design-system`. Значения в коде вроде `#ff0000` или `13px` запрещены.
- Варианты компонента — через `recipe` или `styleVariants`, а не склейку классов по условиям.
- Динамические значения — через CSS-переменные и `assignInlineVars`; атрибут `style` с готовыми значениями запрещён.
- Адаптивность — через брейкпоинты из токенов.

## Состояния экрана

Каждый экран и каждый блок данных обрабатывает:
- загрузку — скелетон или индикатор из дизайн-системы;
- пустое состояние — с объяснением и действием, если оно есть;
- ошибку — понятный текст и возможность повторить;
- нет прав — отдельное сообщение, а не пустой экран.

Ошибка рендеринга перехватывается границей ошибок маршрута, а не роняет приложение.

## Доступность

- Семантические элементы: кнопка — `button`, ссылка — `a`, заголовки по порядку.
- У каждого поля ввода есть подпись, у каждой кнопки-иконки — доступное имя.
- Всё доступно с клавиатуры, фокус виден.
- Тесты ищут элементы по ролям и доступным именам — это заодно проверяет доступность.

## Тексты

- Все тексты для пользователя — на русском, в тоне продукта.
- Текст ошибки с сервера (`message`) показывается как есть; машинный `code` — только для логики.

## Feature toggles

- Флаги — только через `@platform/feature-flags`.
- Проверка флага — в одном месте на экран или модуль, а не в каждом компоненте.
- Код старого поведения удаляется вместе с флагом.

## Микрофронтенд

- Микрофронтенд отдаёт через Module Federation корневой компонент `./App` и, если нужно, маршруты.
- Настройка Vite — только через `defineAppConfig` из `@platform/web-config/vite`.
- Общие библиотеки в одном экземпляре — только из списка пресета; приложение ставит их у себя в `dependencies`.
- Связь между микрофронтендами — только через адрес (маршрут) и общие пакеты, без прямых импортов и глобальных переменных.

## Команды

| Команда | Что делает |
|---|---|
| `pnpm --filter @platform/api generate` | генерация клиента из OpenAPI |
| `pnpm --filter @platform/<app> typecheck` | проверка типов |
| `pnpm --filter @platform/<app> test` | модульные тесты |
| `pnpm --filter @platform/<app> test:visual` | визуальные тесты |
| `pnpm --filter @platform/<app> build` | сборка |
| `pnpm --filter @platform/api test:contract` | контрактные тесты |
| `pnpm lint` | линтер по всему репозиторию |
