# Перенос фичи из прототипа

Как перенести фичу прототипа на новую платформу. Это та же новая фича по `ai/workflows/feature.md`, но с другим источником требований и дополнительной сверкой. Ниже — только отличия.

Прототип — `prototype/`, его описание — `docs/`. Прототип — эталон поведения, но не архитектуры: переносится поведение, описанное в требованиях, а не устройство кода.

## Выбор фичи

Фича для переноса — законченный для пользователя кусок прототипа, который можно проверить отдельно. Ориентиры — разделы `docs/`:

| Раздел прототипа | Описание |
|---|---|
| вход и сессии | `docs/auth.md` |
| компания, точки, участники, оферта | `docs/partners.md` |
| кампании, креативы, модерация, маркировка | `docs/campaigns.md` |
| показ, клики, результаты, статистика | `docs/serving.md` |
| баланс, пополнение, документы | `docs/money.md` |
| бэкофис | `docs/backoffice.md` |
| интеграции | `docs/integrations.md`, `docs/integration-map.md` |

Порядок переноса — от фич, от которых зависят другие: вход и компания раньше кампаний, кампании раньше показа и денег.

## 1. Требования — аналитик

```
/analyst восстанови требования к <фича> по прототипу: docs/<раздел>.md и prototype/
```

Отличия от новой фичи:
- в `requirements.md` — `source: prototype`;
- раздел «Отличия от прототипа» заполнен: что меняется и почему;
- поведение прототипа, похожее на ошибку или упрощение, вынесено в открытые вопросы, а не перенесено молча.

**K1 — дополнительно проверить:**
- требования описывают поведение прототипа полностью, включая ошибки и крайние случаи;
- каждое отличие от прототипа осознанное.

## 2. Дизайн — архитектор

```
/architect спроектируй перенос фичи NNN-slug
```

Отличия:
- фича проектируется в архитектуре платформы — микросервисы, gRPC, свои базы, — а не по устройству прототипа;
- раздел «Отличия от прототипа» в `design.md` описывает, как устроено иначе;
- если фича требует нового сервиса или микрофронтенда — ADR;
- если нужен перенос данных из базы прототипа — отдельные задачи и описание в разделе «Данные».

**K2 — дополнительно проверить:**
- устройство прототипа не перенесено: нет общего монолитного модуля, обращений к чужим данным, схемы базы прототипа «как есть».

## 3. План тестов — тестировщик

Раздел «Сверка с прототипом» в `test-plan.md` заполнен: какие сценарии сверяются с прототипом и где ожидаются отличия.

## 4. Разработка

Как в новой фиче. Разработчик сверяет поведение с прототипом и не переносит его код.

## 5. Проверка — тестировщик

```
/qa проверь фичу NNN-slug со сверкой с прототипом
```

Тестировщик запускает прототип из `prototype/` и сверяет сценарии из раздела «Сверка с прототипом». Расхождение, которого нет в «Отличиях от прототипа», — дефект или вопрос.

## После переноса

- Источник правды для фичи — `specs/features/NNN-slug/`. `docs/` и `prototype/` не меняются.
- Код прототипа не удаляется, пока прототип не будет заменён целиком.
