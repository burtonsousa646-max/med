# ADR 0002. Сервис подсказок suggestion-service на DaData с выбором адаптера при старте

## Контекст

Платформе нужны подсказки и автодополнение при вводе: пользователь вводит строку — ИНН, часть названия, адреса, БИК, email — и получает варианты из справочников. Первые виды подсказок:

| Вид | Что ищется | Пример ввода |
|---|---|---|
| `party` | организации и ИП | ИНН, ОГРН, название |
| `address` | адреса | часть адреса |
| `bank` | банки | БИК, название |
| `email` | адреса почты | начало адреса |

Список видов будет расти.

Источник данных — DaData. Она бывает в двух вариантах:

- **облачная** — сервис DaData в интернете;
- **внутренняя** — DaData, развёрнутая в контуре компании.

Платформа должна уметь работать с любым из них, а переключение не должно затрагивать потребителей подсказок.

Ограничения платформы:

- новый сервис — только через ADR (`ai/rules/architecture.md`);
- внешняя система — порт в `application/ports/` и адаптер в `infrastructure/<external>/`, у каждого адаптера есть заглушка, реализация выбирается по конфигурации (`ai/rules/backend.md`);
- конфигурация — только из переменных окружения, один образ на все окружения;
- у каждого внешнего вызова есть таймаут; перебираемые операции gateway ограничивает по частоте (`ai/rules/security.md`);
- пока подсказки нужны только web-приложениям через API Gateway.

Документации API внутренней DaData пока нет: неизвестно, совпадает ли её протокол с облачной, как она авторизует запросы и какие справочники в неё загружены.

## Варианты

### Где живут подсказки

#### Вариант 1. Отдельный сервис `suggestion-service`

- **Плюсы:**
  - интеграция с DaData, ключи, квоты и кеш — в одном месте; остальные сервисы и gateway о DaData не знают;
  - выбор облачной или внутренней DaData меняется в одном сервисе;
  - новые виды подсказок добавляются без изменения других сервисов;
  - сервис без собственной базы — простой, его легко масштабировать.
- **Минусы:**
  - лишний переход gateway → сервис на каждый запрос подсказки;
  - ещё один сервис в выкладке и мониторинге.

#### Вариант 2. Адаптер DaData в gateway

- **Плюсы:** на один переход меньше, нет нового сервиса.
- **Минусы:** gateway получает интеграцию с внешней системой, кеш и правила справочников — это противоречит правилу «в gateway нет бизнес-логики»; сервисам, которым понадобятся подсказки, придётся ходить в gateway или повторять интеграцию.

#### Вариант 3. Адаптер DaData в каждом сервисе, которому нужны подсказки

- **Плюсы:** нет нового сервиса.
- **Минусы:** интеграция, ключи и квоты дублируются; переключение на внутреннюю DaData нужно делать в нескольких сервисах.

### Как выбирается облачная или внутренняя DaData

#### Вариант А. Конфигурация при старте

Переменная `SUGGESTION_PROVIDER` выбирает адаптер при старте сервиса: `dadata-cloud`, `dadata-onprem` или `stub`.

- **Плюсы:** просто; соответствует правилу «окружения отличаются только переменными»; в процессе одно подключение к DaData.
- **Минусы:** переключение — перезапуск сервиса; без простоя, если перезапускать экземпляры по одному.

#### Вариант Б. Конфигурация и флаг Unleash `operational`

Настроены оба адаптера, флаг выбирает активный во время работы.

- **Плюсы:** переключение без перезапуска.
- **Минусы:** постоянный флаг; нужно держать настроенными и проверять оба подключения; сложнее тестировать.

#### Вариант В. Как Б, плюс автоматический переход на другой вариант DaData при сбое

- **Плюсы:** выше доступность подсказок.
- **Минусы:** неявное поведение: трудно понять, какая DaData ответила; квоты облака могут кончиться незаметно; нужен circuit breaker.

## Решение

**Отдельный сервис `suggestion-service` (вариант 1), адаптер выбирается при старте (вариант А).** Подсказки — самостоятельная возможность платформы со своей внешней системой, ключами и квотами. Выбор облачной или внутренней DaData — свойство окружения, а не пользователя или запроса, поэтому он задаётся конфигурацией. Если понадобится переключение без перезапуска, его добавит новый ADR (вариант Б), не меняя порт и адаптеры.

### Место в платформе

```
браузер ──POST /v1/suggestions/parties──► api-gateway ──gRPC──► suggestion-service ──┬─HTTPS──► DaData облачная
                                                                       │              └─HTTPS──► DaData внутренняя
                                                                       └── Redis: кеш ответов
```

- Пакет — `@platform/suggestion-service`, каталог — `server/apps/suggestion-service/`.
- Контракт — `api/proto/suggestion/v1/suggestion.proto`, пакет `platform.suggestion.v1`, сервис `SuggestionService`.
- Бизнес-данных сервис не хранит: PostgreSQL и Prisma ему не нужны. Своё состояние — только кеш в Redis.
- Вызывает сервис пока только gateway. Другие сервисы смогут вызывать его по тому же gRPC-контракту.

### Устройство сервиса

```
server/apps/suggestion-service/src/
  domain/suggestion/
    suggestion-kind.value.ts            вид подсказки: party, address, bank, email
    suggestion-query.value.ts           запрос: вид, строка, количество, фильтры вида; инварианты
    suggestion.value.ts                 подсказка: value, unrestrictedValue и данные вида — наша модель, не формат DaData
    suggestion.errors.ts
  application/
    suggest/suggest.use-case.ts         нормализует запрос → кеш → провайдер → кеш
    ports/suggestion-provider.gateway.ts  порт SuggestionProvider и токен DI
    ports/suggestion-cache.port.ts      порт кеша
  infrastructure/
    dadata/
      dadata-http.client.ts             протокол DaData: fetch, таймаут, отмена, разбор ошибок
      dadata.mapper.ts                  ответ DaData → доменная модель
      dadata-cloud.adapter.ts           облачная DaData
      dadata-onprem.adapter.ts          внутренняя DaData
    stub/stub-suggestion.adapter.ts     синтетические данные для локального окружения и тестов
    cache/redis-suggestion.cache.ts
  presentation/grpc/suggestion.controller.ts
  suggestion.module.ts                  связывает порт с адаптером по SUGGESTION_PROVIDER
```

Порт:

```ts
export const SUGGESTION_PROVIDER = Symbol('SuggestionProvider')

export interface SuggestionProvider {
  /** Имя адаптера — для логов и метрик. */
  readonly name: 'dadata-cloud' | 'dadata-onprem' | 'stub'
  /** Поддерживает ли адаптер вид подсказки: во внутренней DaData может быть не всё. */
  supports(kind: SuggestionKind): boolean
  suggest(query: SuggestionQuery, signal: AbortSignal): Promise<Suggestion[]>
}
```

- Сценарий знает только порт. Какая DaData отвечает, знает только `suggestion.module.ts`.
- Если протокол внутренней DaData совпадает с облачной, оба адаптера используют `dadata-http.client.ts` и отличаются адресом, авторизацией и списком поддерживаемых видов. Если протоколы разойдутся, разница остаётся внутри `dadata-onprem.adapter.ts` и маппера.
- Формат DaData не выходит за `infrastructure/dadata/`: в домене, gRPC и OpenAPI — своя модель подсказки. Поля данных каждого вида определяются в `design.md` фичи по требованиям.
- Вид, который адаптер не поддерживает, — доменная ошибка `suggestion_kind_unsupported`, в gRPC — `FAILED_PRECONDITION`.
- SDK DaData не используется: клиент написан на встроенном в Node.js `fetch`. Новых зависимостей нет.

### Конфигурация

Читается и проверяется при старте через `@platform/config`. Неверная конфигурация — сервис не стартует. Переменные выбранного адаптера обязательны, остальных — нет.

| Переменная | Что | Обязательна |
|---|---|---|
| `SUGGESTION_PROVIDER` | `dadata-cloud`, `dadata-onprem` или `stub` | да |
| `DADATA_CLOUD_URL` | адрес API подсказок облачной DaData | при `dadata-cloud` |
| `DADATA_CLOUD_API_KEY` | ключ API облачной DaData — секрет | при `dadata-cloud` |
| `DADATA_ONPREM_URL` | адрес API подсказок внутренней DaData | при `dadata-onprem` |
| `DADATA_ONPREM_*` | авторизация внутренней DaData — состав определяется по её документации | при `dadata-onprem` |
| `SUGGESTION_TIMEOUT_MS` | таймаут вызова DaData | нет, по умолчанию 1500 |
| `SUGGESTION_CACHE_TTL_SEC` | срок жизни записи кеша | нет, по умолчанию 86400 |

Локально и в тестах — `stub`: в DaData не ходим, ключи не нужны.

### Поведение при сбоях

- Вызов DaData — с таймаутом `SUGGESTION_TIMEOUT_MS` и отменой, если gateway отменил запрос. Повторов нет: пользователь продолжает вводить, и следующий запрос всё равно придёт.
- Таймаут, сетевая ошибка, ответ 5xx, а также 429 и 403 от DaData (лимит частоты, исчерпанная квота) — `UNAVAILABLE` в gRPC и 503 в gateway. Причина пишется в лог и метрику.
- Ошибка DaData не попадает в кеш.
- `/health/ready` не проверяет DaData: иначе сбой внешней системы снимет сервис с трафика. Проверяется Redis; если Redis недоступен, сервис работает без кеша и пишет `warn`.

### Кеш

- Redis, ключ — хеш от имени адаптера, вида, нормализованной строки и параметров запроса. Имя адаптера в ключе нужно, чтобы после переключения DaData не отдавались ответы прежней.
- Кешируется только успешный ответ, срок жизни — `SUGGESTION_CACHE_TTL_SEC`. Отдельные сроки для разных видов — в `design.md`, если требования их потребуют.

### Внешний API

- Отдельная операция на каждый вид: `POST /v1/suggestions/parties`, `/addresses`, `/banks`, `/emails`, `operationId` — `suggestParties`, `suggestAddresses`, `suggestBanks`, `suggestEmails`. У каждого вида свои фильтры и данные в ответе, и так они типизированы.
- POST, а не GET: строка ввода идёт в теле запроса и не попадает в адреса и access-логи.
- Gateway требует сессию и ограничивает частоту запросов (429). Frontend отправляет запрос с задержкой после ввода.
- Пути и схемы — в `api/openapi/<app>.yaml` того web-приложения, которому нужны подсказки, в `design.md` фичи.

### Данные и 152-ФЗ

DaData — российский сервис, данные хранятся и обрабатываются в России. По решению человека использование облачной DaData для подсказок не противоречит 152-ФЗ: DaData выступает поставщиком справочных данных. Строка ввода не пишется в логи, трассировки и метрики — в логах только вид подсказки, адаптер, длина строки и результат.

## Последствия

- В платформе появляется первый сервис без собственной базы. Правило «у каждого сервиса своя база» читается как «если сервис хранит данные — только в своей базе».
- Интеграция с DaData, её ключи и квоты — только в `suggestion-service`. Другие сервисы и gateway в DaData не ходят.
- Переключение между облачной и внутренней DaData — изменение `SUGGESTION_PROVIDER` и перезапуск сервиса. Код потребителей не меняется.
- Новый вид подсказки — значение `SuggestionKind`, его модель и маппинг в адаптерах, метод или поле в `.proto`, операция в OpenAPI. Порт не меняется.
- Адаптер внутренней DaData пишется по протоколу облачной и проверяется по документации, когда она появится. До этого внутренняя DaData в окружениях не используется.
- Нужны метрики: число запросов и ошибок по виду и адаптеру, длительность вызова DaData, доля попаданий в кеш. Нужны алерты: всплеск `UNAVAILABLE`, ответы 403 и 429 от DaData.
- Ключи DaData — секреты: только в переменных окружения стендов и production, в репозитории — только `.env.example`.

## Когда пересмотреть

- Появилась документация внутренней DaData, и её протокол заметно отличается от облачной — проверить, достаточно ли отдельного адаптера.
- Нужно переключать DaData без перезапуска или переходить на другой вариант при сбое — новый ADR по варианту Б или В.
- Подсказки понадобились другим сервисам по gRPC и нагрузка выросла — пересмотреть кеш и лимиты.
- Появился второй источник подсказок помимо DaData — проверить, что порт `SuggestionProvider` его покрывает.
