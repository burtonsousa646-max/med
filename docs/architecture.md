# Архитектура

Состояние на 30.10.2026, конец дня 3. Общая картина и план — в [plan.md](plan.md); здесь — как устроено внутри и почему.

## 1. Форма системы

Модульный монолит на TypeScript (Node 22, Hono, PostgreSQL 17). Один репозиторий, один язык, два процесса из одного кода:

Интерфейс кабинета — отдельное одностраничное приложение в `web/` ([web.md](web.md)), ходит только в `/api/cabinet` и `/api/auth` по типам из контракта.

| Процесс | Запуск | Что делает |
|---|---|---|
| **api** | `server/index.ts` | HTTP: кабинет, бэкофис, публичный API для поверхностей и партнёров, вебхуки |
| **worker** | `server/worker.ts` | исходящая очередь (проверка юрлица, модерация, ОРД, ЭДО, учёт, письма) и периодические задачи (`schedule.ts`): партиции показов, опрос выписки, закрытие месяца |

Модули вызывают друг друга функциями, не по сети. Граница модуля — папка `server/modules/<модуль>` и его таблицы. Модуль не пишет в чужие таблицы напрямую, только через функции модуля-владельца. Так любой модуль можно вынести в отдельный сервис, когда понадобится (первый кандидат — показ, под нагрузку).

```
 браузер партнёра ─┐                                    ┌─ поверхности билайна
 браузер сотрудника┤                                    ├─ сервер партнёра
                   ▼                                    ▼
          ┌──────────────────────── api (Hono) ─────────────────────────┐
          │ /auth  /cabinet  /admin                /public  /hooks       │
          │        └─ модули: identity, partners, campaigns, billing, …  │
          │                     │ port('ord').registerCreative(...)      │
          │                     ▼                                        │
          │        integrations: порт → адаптер (stub | beeline)         │
          └───────┬───────────────────────────────┬──────────────────────┘
                  │ транзакция: изменение + outbox│ integration_log
                  ▼                               ▼
              PostgreSQL ◄──── worker: берёт outbox в аренду, вызывает порт, ретраи
```

## 2. API

Четыре входа, у каждого свой контракт и своя авторизация:

| Префикс | Кто | Авторизация | Контракт |
|---|---|---|---|
| `/api/auth` | все | — | `api/cabinet.yaml`, `api/admin.yaml` |
| `/api/cabinet` | партнёр | cookie `sid`, участник выбранной компании | `api/cabinet.yaml` |
| `/api/admin` | сотрудник билайна | cookie `sid`, роль из SSO | `api/admin.yaml` |
| `/api/public` | поверхности, сервер партнёра | токен показа, ключ партнёра (день 3) | `api/public.yaml` |
| `/api/hooks` | внешние системы | HMAC-подпись тела | `api/public.yaml` |

Контракт — источник правды. `server/contract.test.ts` падает, если в коде есть маршрут без описания в контракте или в контракте есть операция без кода.

Ошибки — всегда `{ message }` с текстом для человека и статусом: 400 — не JSON, 401 — не вошёл, 403 — нет прав, 404 — нет такого, 409 — конфликт версий, 422 — неверные данные, 429 — слишком часто, 500 — сбой (подробности только в логе).

## 4. Ключевые решения

### 4.1 Интеграции через порты

У каждой внешней системы порт — интерфейс в терминах платформы (`server/integrations/ports.ts`). Ядро вызывает `port('ord')`, а какой адаптер за ним — решает переменная `INT_ORD`. Сейчас за всеми портами заглушки. Подробно — [integrations.md](integrations.md).

### 4.2 Исходящая очередь вместо прямых вызовов

Если изменение должно дойти до внешней системы (креатив — в ОРД, документ — в ЭДО), модуль в той же транзакции кладёт задачу в `outbox`. Изменение и задача сохраняются вместе или не сохраняются вовсе: нельзя записать креатив и потерять его регистрацию в ОРД. Воркер берёт созревшие задачи в аренду на 5 минут, вызывает порт и отмечает результат. Ошибка — повтор через 10 с, 40 с, 2,5 мин, 10 мин и так далее до часа; после 8 попыток задача `failed` и видна в бэкофисе.

Синхронные вызовы (геокодер, реестр юрлиц, DMP в момент показа) идут напрямую, без очереди: их результат нужен сразу.

### 4.3 Деньги — двойная запись в копейках

Все суммы — `bigint` в копейках. Любая денежная операция — запись в `transactions` и проводки в `entries`, сумма которых ноль; это проверяет триггер базы в конце транзакции, приложение обойти его не может. Баланс — сумма проводок по счёту, а не поле, которое можно испортить. У каждой операции обязательный ключ идемпотентности: повтор вебхука оплаты не зачислит деньги дважды. Подробно — [data-model.md](data-model.md#billing).

### 4.4 Изоляция компаний

Компания и роль берутся только из сессии (`c.var.partner.companyId`), никогда из параметров запроса. Каждый запрос кабинета фильтрует по этой компании. Тест `identity.test.ts` проверяет, что чужая компания недоступна.

Сейчас изоляция на уровне приложения. Следующий уровень — политики строк PostgreSQL (RLS) с `set local app.company_id` в транзакции запроса; включить до подключения реальных партнёров.

### 4.5 Данные абонентов

Номера телефонов абонентов платформа не хранит и не принимает. Ключ абонента — MED-ID: случайный ID из контура билайна. Пока DMP не подключён, поверхность передаёт обезличенный ID устройства, он играет роль MED-ID. Партнёр видит только агрегаты, не меньше 50 человек в ячейке.

## 5. Что сознательно не поставили и когда поставить

| Нет | Чем закрыто | Когда добавить |
|---|---|---|
| Kafka | `outbox` в PostgreSQL, `FOR UPDATE SKIP LOCKED` | больше ~2 тыс. событий в секунду или шина билайна: её адаптер читает тот же outbox |
| ClickHouse | `impressions` с партициями по дням, почасовые свёртки | отчёты по событиям медленнее 1 с |
| Redis | индекс кампаний и частоты в памяти процесса | больше одного экземпляра api |
| Kubernetes | systemd на VPS | переезд в облако билайна |
| ML-модель pCTR | априорный CTR места, сглаженный наблюдаемым | подключение Big Data |
| RLS | фильтр по компании в приложении + тест | до первых реальных партнёров |
| Склейка учётных записей по почте | не склеиваем | никогда без подтверждения почты на обеих сторонах, см. [auth.md](auth.md) |
